## 0. 总体结论

### 0.1 判定：**FAIL**（可修复型，建议一轮修订后复审）

不是方向性否定。两份文档的方向、产品骨架与写作纪律都在合格线以上；判 FAIL 的原因是**「最初版」的可验收性尚未闭环**：范围没有真正收敛、发布标准存在四个版本、三个核心价值（注意力管理、记忆注入、结构性冲突）在最初版没有端到端验收场景，且 req 自述「不规定具体实现方案」却用整章写技术选型。这些问题不推翻文档，但必须在下一轮修订内修掉，否则无法用这份需求判断「v0.0.1 是否可发布」。

### 0.3 三条判定理由

1. **验收体系接不上**：req §4.3 把「首次价值时间」定义到「第一个任务被接受 ≤30 分钟」，而 AC-03 要求一个真实需求走完 PRD→实现→测试→评审→G3；同一件事在 §4.4、§12.4、§15.8 和 tgt §15.1 有四种写法，且都自称发布标准。
2. **范围没有收敛**：P0 覆盖 14 个领域，§5.2 的 P1 又与 P0 功能大面积重复（简报、任务板保存视图、组织图/负载、成本与审计视图、记忆检查器、产出物评论、保存搜索），验收时无法判断某项到底做不做。
3. **三个核心机制缺可验收落点**：注意力管理缺「决策收件箱/审批中心」的信息架构与默认预算；记忆注入（「越用越懂你」）在 AC-05 里退化成「检索回忆」；跨团队辩论的「2 轮」与「死锁」不可数、不可观察，「领域 owner」在角色表里不存在。

## 2. P0 发现（必须修改，否则不可发布）

### P0-01 三个「30 分钟」互相矛盾，首次价值时间不可验收

**位置**
- req §4.3（L169）：首次价值时间 = 安装 → 助理 → 团队 → **第一个任务被接受** ≤ 30 分钟
- req §4.4（L183）：新用户按 Quickstart 完成安装、组队、**交付**，无需开发者协助
- req §0.1（L21）、§7.1（L334-345）：30 分钟内还包含 5–8 分钟引导、意图卡、G1、两支团队 provisioning、kickoff
- req AC-01（L1915-1937）、AC-03（L1962-1986）
- tgt §15.1（L1544、L1556-1563）：新用户 30 分钟内完成安装、组队、**第一个任务闭环**

**问题**
同一指标被写成三种口径。按 AC-03，一次「真实小需求」要经过产品写 PRD、研发实现、测试写用例/跑测试、挑战单与返工、主管核对 DoD、G3 验收；这在 30 分钟内不可能完成，也不该为了达标而被压缩。J1 的 30 分钟里排满了人类审批与两支团队的 provisioning，没有任何时间留给交付。

**影响**
发布门槛自相矛盾：团队要么砍掉人类闸门/评审来「达标」，要么指标造假。以它为北极星支撑指标（tgt §16.1）后，后续所有「是否更快」的判断都不可信。

**建议**
拆成三段时间并在全文统一引用：
- **T1 安装 → 助理可对话 ≤ 10 分钟**（对应 AC-01 前 3 步）
- **T2 → G1 批准 + 第一个任务创建 ≤ 30 分钟**（对应 AC-01 + AC-02；这才叫「首次价值」）
- **T3 → 第一个交付物被人类接受 ≤ 1 个工作日**（对应 AC-03）
req §4.3、§4.4、§7.1 与 tgt §15.1 改用 T1/T2/T3；AC-03 明确不计入 30 分钟指标。另建议把 §4.4「新用户 30 分钟完成交付」改为「按 Quickstart 走完 T1/T2」。

### P0-02 P0/P1 边界失效，P0 范围不可行

**位置**
- req §5.1 P0（L197-214）、§5.2 P1（L216-227）、§5.4 范围护栏（L245-251）、§12.2 里程碑（L1802-1811）
- 重复对照详见附录 B（8 组）

**问题**
1. **同一能力在两个优先级各写一遍**：简报（FR-ASST-05 P0 vs §5.2 P1「定时生成」）、任务板保存视图（FR-CHAT-07 P0 vs §5.2 P1）、组织图/负载（FR-CHAT-09 P0 vs FR-TEAM-07 P1）、成本/审计视图（FR-CHAT-12 P1 vs FR-OPS-05 + FR-OBS-03 + FR-SEC-06 P0）、记忆检查器（FR-CHAT-10 与 FR-MEM-09 同时 P0）、产出物评论（FR-ART-03 P0 vs §5.2 P1）、保存搜索（FR-SRCH-02 P0 验收内又标 P1）、决策收件箱/升级包（FR-ASST-06 与 FR-ESC-01 字段几乎相同）。
2. **P0 总量不可行**：14 个领域 + 7 条用户旅程 + 10 个端到端场景 + 四层记忆 + 跨团队辩论 + 备份恢复 + 审计 + 成本 + 导出导入 + 索引重建 + 可访问性。对「最初版」而言，这不是纵向切片。
3. **P0 与里程碑脱节**：§12.2 的 M0–M5 没有标出对应哪些 P0 FR；读完后无法回答「M2 结束时哪些 P0 必须过」。
4. **§5.4「P1 缺失时核心闭环仍能跑」无法验证**：没有「P1 关闭」的构建/配置，也没有对应验收。

**影响**
范围必然蔓延；评审/研发对「这版到底做什么」没有共同答案；P1 降级无法被证明安全。

**建议**
- 一条能力只保留一条 FR；P1 仅用于「P0 能力中的可降级子集」，并在 FR 内用 [P1 可降级] 标注，同时写明「缺失时的行为」。
- P0 拆三档：**P0a 闭环**（消息/助理/组队/任务/产出物/评审/G1-G3/记忆最小闭环）、**P0b 可靠性/安全**（先写后发、崩溃恢复、备份、loopback、审计数据）、**P0c 治理/体验**（组织图、成本视图、命令面板、导出导入、可访问性）。
- 首批降级建议（可直接执行）：FR-CHAT-09 的「负载/今日成本/最近行为」降 P1（保留 Agent 列表、角色卡、暂停 P0）；FR-CHAT-12 整体并入 FR-SEC-06/FR-OPS-05 后删除；FR-OPS-02 拆「导出 P0 / 导入 P1」；FR-ART-03 行级评论降 P1（保留 Markdown/代码 diff 呈现 P0）；FR-CHAT-07「保存视图」降 P1。
- 在 §12.2 每个里程碑的 Exit Criteria 里列出对应 P0 FR 号，形成「里程碑 → FR」映射。

### P0-03 发布标准有四个版本，且 P0 覆盖矩阵缺失

**位置**
- req §4.4 Exit Criteria（L180-191）、§12.4 DoD（L1827-1838）、附录 H 发布检查清单（L2301-2318）、tgt §15.1 Exit criteria（L1556-1563）
- P0 覆盖缺口详见附录 A

**问题**
四份「发布标准」互不一致：
- req §4.4 无「3 个真实用户」；§12.4 有「至少 3 个真实用户试用（Beta）」；附录 H 有「至少 3 个真实用户完成首个闭环」。
- tgt §15.1 有「无绕过平台的消息」；req 四份清单都没有。
- req 附录 H 有「中文 2 字/3 字/短语/中英混排通过」；§4.4 只有 Recall@10。
- tgt §15.1 有「一次跨团队挑战产生决策记录并可检索」；req §4.4 有，但附录 H 没有。
- req §12.4 有「P0 功能全部实现」，而 §5.1 的 P0 本身未收敛（见 P0-02）。

同时，P0 需求与 AC 的覆盖矩阵缺失：通知分级（FR-CHAT-06）、简报（FR-ASST-05）、助理边界（FR-ASST-09）、成员管理（FR-TEAM-04）、DoR 拒绝/依赖/WIP（FR-TASK-03..05）、不可逆动作审批的「一次/会话/始终」（FR-APPR-02）、记忆触发/额度/压缩/注入/失败（FR-MEM-03/04/06/08/11）、跨对象检索（FR-SRCH-03）等 P0 项没有任何 AC 步骤。

**影响**
「可发布」无法判定；实际发布必然退化为「演示跑通 + 清单勾选」。

**建议**
- 只保留**一份**《v0.0.1 发布标准》（建议放 §12.4），§4.4 与附录 H 改为引用；tgt §15.1 与本清单对齐。
- 增加 **FR → AC 覆盖矩阵**（附录 A 是起点），未覆盖的 P0 逐条给出验证方式（自动化 / 人工脚本 / 降级到 P1）；「未被任何 AC 覆盖」的 P0 不允许进入发布清单。
- 补两个场景（见 P0-07/P0-08）：**AC-11 记忆注入与跨会话复用**、**AC-12 主管核对表 + 人类抽检**。

### P0-04 人类在环的权责与默认值缺失

**位置**
- req §6.2 权限矩阵（L272-290）与附录 F 权限速查（L2264-2278）不一致（「组织级记忆写入」「验收」两行）
- FR-APPR-01（L1084-1095）「G3 未批准不能标记 done」vs §6.2「质量门/验收：主管 A」
- tgt §8.1 任务字段（L609）只有一个 approver
- req §6.3 G2（L299）「低风险任务可委托给主管 Agent」，但全文没有「高风险」的定义
- tgt §6.8（L494）「助理每天最多主动升级 N 次（可配置）」；req 无默认值、无超限行为
- FR-APPR-02（L1107）「超时未审批 → 暂停/升级」无 TTL；FR-ASST-06（L693）「批量审批」与 FR-APPR-02（L1106）「双钥匙」未解释如何共存
- FR-TEAM-05（L790）「人类确认章程后才进入 active」与 G1 蓝图（L294）的关系未定义；AC-02（L1946-1949）没有章程确认步骤

**问题**
1. **谁点 done 不唯一**：人类 G3、主管 DoD 核对、测试质量判定三方都像验收人，但任务模型只有一个 approver；AC-03「主管核对 DoD；用户 G3 验收」没有说明二者是「双签」还是「主管核对只是人类决策的输入」。
2. **G2 触发条件不可判定**：AC-03 步骤 3 写「高风险时用户 G2」，但「高风险」无定义，该步骤不可执行、不可审计。
3. **人类静默时没有产品行为**：用户 3 天不看、审批一直挂着，系统是继续跑、暂停、还是降级，均未定义；这与「人类主权」原则直接相关。
4. **批量审批与双钥匙冲突**：批量批准不可逆动作会绕过「作者之外的审批人」这一结构防线。
5. **组队前人类介入次数不清**：蓝图 G1 + 章程确认 + kickoff 待确认问题（≤3）叠在一起，可能在新用户第一天就产生 3 次以上的审批负担。

**建议**
- 定义**唯一验收人 = 人类（approver）**；主管只能「逐条核对并提交验收」，测试只能给「质量门通过/不通过」。任务增加 verification 子结构（AC 逐条 → 证据 → 主管结论 → 人类决定）。
- 给 **G2 风险分级表**（安全/数据/对外接口/发布 = 高；其余 = 低），与 FR-SEC-03 工具风险分级（L1373）对齐；所有「高风险时」引用该表。
- 给默认注意力预算：实时打扰 ≤ 3 次/天，只有「阻塞/不可逆」可打断，其余进收件箱；超限只提醒不推送。
- 定义**人类沉默策略**：审批 TTL（如 24h）到期 → 标记阻塞 + 提醒，不自动执行；人类连续 24h 未响应 → 团队自动降级为「只读/暂停接新任务」+ 一份日报（可配置）。
- 明确「批量审批不适用于双钥匙动作」；「授权给助理/主管」必须有范围与到期时间，到期自动回收并通知。
- 章程作为蓝图的一部分由 G1 一次批准，或明确「G1.5 章程确认」；AC-02 补该步骤，避免三处定义。

### P0-05 跨团队辩论不可执行、不可验收

**位置**
- FR-DEB-02（L1013-1022）、FR-DEB-03（L1024-1034）、FR-DEB-04（L1036-1046）
- tgt §8.6（L705-725）、AC-04（L1988-2010）
- req §6.1 角色表（L259-268）：没有「领域 owner」

**问题**
1. **「最多 2 轮」不可数**：FR-DEB-03 写「R1 立场 + 回应；R2 反驳」，FR-DEB-02 又要求「双方各提交一次」。按字面可产生「双方立场 + 双方回应 + 双方反驳」= 6 次提交；「2 轮」到底是 2 次提交、2 个往返，还是 2 轮双方发言，无法判定。
2. **死锁检测不可观察**：FR-DEB-03「立场不变且无新证据」——挑战单/决策包没有 stance 字段，也没有 evidence_ids 集合，主持人（或系统）无法判定「立场没变」。
3. **裁决人不存在**：FR-DEB-04 与 tgt §8.6 都把裁决权交给「领域 owner」，但 §6.1 角色表只有人类/助理/主管/产品/研发/测试/架构评审/系统，没有「领域 owner」；FR-DEB-04 又说「跨领域争议升级人类」，边界不清。
4. **反虚假共识全部降级**：tgt §8.6 的盲评、dissent、魔鬼代言人、评审人轮换、红队、抽检、审批率异常告警（L723-725），在 req 里只剩 FR-REV-03 的「可按配置启用」与「同一对 Agent 互审需第三人（P1）」。按最初版交付，无法证明「辩论不是演戏」。
5. **AC-04 依赖自然发生**：前置「平台团队发现交付团队的接口有兼容/安全问题」，没有任何机制保证它一定发生；如果双方一轮就同意，AC-04 仍会通过。

**建议**
- 给挑战单/决策包加结构化字段：stance（一句话立场）、evidence_ids[]、requested_ruling；「轮次」定义为**总提交上限**（建议 R1 双方各 1 条立场 + 各 1 条回应，R2 各 1 条反驳，总计 ≤ 6 条，超限即升级）。
- 死锁 = 连续两次提交 stance 相同且 evidence_ids 无新增；主持人只能记录与升级，不能自行裁决。
- 把「领域 owner」改成具体枚举（主管 Agent / 架构评审 Agent / 人类）+ 授权矩阵；跨领域 = 人类。
- AC-04 改为**脚本注入触发**（演示脚本里人为提交一个接口变更/挑战），保证可重复；补一条「虚假共识抽检」：人类随机抽 1 条 approve 裁决，检查证据与 dissent 记录（P0 最小化版本）。
- 「同步 15 分钟」在单用户本地产品里没有体验定义；建议 v0.0.1 只做异步 + 「立即运行」按钮，同步机制进 P1。

**影响**

### P0-06 实现细节泄漏，且与文档自述的性质矛盾

**位置**
- req L7：「本文只定义方向、范围、行为与验收标准，**不规定具体实现方案**」
- 但 req §9 整章（L1558-1631）：Go（L1581）、SQLite/WAL（L1585 附近）、SSE/Last-Event-ID（L1620 区域）、FTS5（§9.5）、OS keychain（L1613）、AgentBackend 的 spawn/prompt/cancel/close/events 契约（L1619）、MCP/ACP（L1601-1602、L1620-1621）
- 实现名词进入 FR 验收：FR-MEM-11「单飞锁」（L1238）、FR-TASK-02「状态是事件投影…不能直接改数据库状态」（L851）、FR-MEM-06「压缩后自校验字数」（L1179）、FR-OPS-06「幂等键」（L1494）

**问题**

**影响**

**建议**

1. 把 §9 移到《架构约束》文档（推荐），req 只保留可验收约束：单机/loopback/无外部服务/离线可用/性能/可移植/数据可导出。

### P0-07 记忆注入（「越用越懂你」）在最初版无法被验收

**位置**
- tgt 核心价值 2（L85）、原则 3.5（L123-127）、§9.5 触发式记忆（L851-906）、§9.6 档案（L908-944）、§9.9 注入预算（L986-1003）
- req FR-MEM-08（L1197-1207）、AC-05（L2012-2034）

**问题**
AC-05 的「记忆回忆」实际是**助理检索决策记录/辩论/任务**（等于搜索），不是「每次模型调用按预算自动注入档案」；注入机制本身没有验收步骤。删除/修改后的判定是自然语言「再问，确认不再注入」，不可复现；「四层可分别开关/配置」（FR-MEM-01）没有定义关闭后的产品行为。「记忆检查器可编辑」只证明能改，不证明改了会作用于调用。

**影响**
这是产品最关键差异（「越用越懂你」）的验收缺口。上线后最可能的用户反馈正是「还是每次都要解释背景」——而按现文档，验收会通过。

**建议**
新增 **AC-11 记忆注入与跨会话复用**：
1. 完成任务 A（含一条决策与一条约束）后，新开会话执行相似任务 B；
2. 助理**无需用户提醒**即引用 A 的决策与约束，并在「本次回答使用了哪些档案/来源」中可见（tgt 原则 3.3 已要求可解释视图，应提为 P0）；
3. 修改一条偏好 → 新会话第一轮即使用新版本，历史版本仍可查；
4. 删除一条记忆 → 后续注入日志显示命中数为 0（用可观察的注入记录断言，而不是问模型）；
5. 关闭某一层记忆 → 定义并验证其行为（例如关闭档案后，系统只注入任务与手册，并明确告知用户）。

**位置**

**位置**

**建议**

## 4. P1 发现（应改）

### P1-01 术语与对象重复，命名混用
- req §6.5（L315-328）与附录 G（L2280-2299）是两份几乎重复的术语表；tgt §20 是第三份。三份会漂移。
- 「决策包」（FR-DEB-02，L1015）、「升级包」（FR-ASST-06，L692；FR-ESC-01，L1079）、「决策记录」（FR-DEC-01）字段高度重叠但名字不同；读者无法判断「升级包」是否等于「决策包 + 推荐」。
- **建议**：术语表只保留 tgt §20 一份，req 引用；统一「立场包 → 升级包 → 决策记录」三层命名与字段继承关系。

### P1-02 指标不可度量或循环定义
- §4.3「单任务成本 | 在预算内」是循环定义；「记忆可纠正 100%」范围不明（是否包括自动抽取的低置信条目）；「端到端演示 100%」与 §4.4 重复。
- FR-CHAT-07「不卡顿」（L556）、NFR-PERF-07「不阻塞 UI」（L1647）无阈值；FR-SRCH-02「结果相关」（L1277）与 FR-SRCH-06 的 Recall@10（L1325）脱节，AC-06 只写「结果相关」。
- **建议**：每条指标给「定义公式 + 数据来源 + 达标线 + 抽样方法」；「相关」统一改为「金标准集 Recall@10 ≥ 0.8、nDCG@10 ≥ 基线」；交互响应给 p95 阈值。

### P1-03 反指标缺失
- tgt §16.3（L1648-1654）明确「消息数/Agent 数/无人干预/辩论轮次/记忆条数/团队数不是成功」，但 req §4.3 与 §5.4 没有任何反指标，也没有「反指标触发后怎么办」。
- **建议**：至少加四个反指标：每交付物人类干预次数、每任务 token/费用上限、返工率上限、人类打扰次数；超阈值触发「停工复盘」而不是继续加 Agent。

### P1-04 P1「可降级」没有工程含义
- §5.4（L251）「P1 功能缺失时核心闭环仍能跑」；但没有「P1 关闭」的配置/构建，也没有对应验收。
- **建议**：定义「P1-off 构建」与一组「P1 缺失下的最小闭环场景」，否则该承诺不可验证。

### P1-05 单机进程拓扑未定，崩溃验收含义不同
- tgt §5.5（L315-316）多进程是 v0.1+，v0.0.1 是「一个平台进程 + 一个核心进程/模块 + 0..N 后端」；req §9.1（L1564-1575）没有说清 v0.0.1 的进程形态。AC-07「强制终止进程」在同进程架构下等于全挂，在多进程下只挂一个 Agent，恢复范围完全不同。
- **建议**：在 req 明确 v0.0.1 的进程拓扑（同进程快路径/子进程），并把 AC-07 的「杀哪个进程、期望哪些状态保留」写清。

### P1-06 搜索相关性验收不足
- FR-SRCH-02（L1275-1279）定义「相关度 + 时间衰减 + 会话聚合 + 权威度」，但 AC-06（L2051）只写「结果相关」；FR-SRCH-06 的 Recall/nDCG 没有进入 AC。
- **建议**：AC-06 引用金标准查询集，给出 Recall@10、nDCG@10、p95 的可执行断言；排序规则变更必须回归。

### P1-07 蓝图 / 章程 / kickoff 三次人类介入关系未定义
- FR-ASST-03 蓝图（L651-660）、FR-TEAM-05 章程（L782-791）、G1（L294）、AC-02（L1946-1949）四者内容重叠（使命/成功标准/角色/质量门/预算），但 AC-02 只测 kickoff，没有章程确认。
- **建议**：合并为「团队蓝图 = 章程草案」，G1 一次批准；kickoff 只负责复述与风险，不再产生第二次审批；或明确 G1 与 G1.5 的先后与差异。

### P1-08 「发布」在 v0.0.1 没有定义
- FR-APPR-01（L1091）「未批准不能标记 done/发布」，但 §5.3（L238）明确不做自动发布；「发布」到底指交付、部署、还是对外可见，需定义。
- **建议**：定义「发布 = 用户自行部署到生产，系统只交付到工作区并给部署说明」；G3 只确认交付物完整与风险可知。

### P1-09 示例/演示数据与真实数据未隔离
- FR-ONB-04（L461）可用示例项目；FR-ONB-05（L471）提供「重置演示数据」；AC-01 要求在「全新数据目录」跑。
- **建议**：显式「演示 workspace」与真实 workspace 隔离；示例数据不得进入真实工作区/记忆/组织记忆；重置只影响演示区。

### P1-10 团队解散/归档的记忆移交不完整
- tgt §7.4（L557）、§7.6（L582）要求解散时移交产出与记忆、复盘写入组织记忆；req FR-TEAM-03（L767）只有「移交产出与记忆」一句。
- **建议**：定义「哪些进组织记忆、谁批准、如何检索、成员评价是否保留、私有档案是否随团队归档」；给一条 AC。

### P1-11 平台对象所有权冲突
- tgt §10.3「核心对象」在「对话平台」章下列出 Task/Artifact/MemoryEntry（L1077-1089），但 §5.2 说这些由 Agent 核心拥有（L265-269）；req §9.4（L1609-1612）也是核心拥有。
- **建议**：把 §10.3 改为「系统对象模型（跨模块）」，并标注「平台只存展示投影/引用」，避免研发把任务表建到平台库。

### P1-12 Agent 状态模型不完整
- FR-OBS-01（L1505）五态：运行/空闲/等待审批/暂停/失败；缺「崩溃/失联」「预算阻塞」「等待依赖」「被人类终止」。
- **建议**：状态与原因分离（state + reason），并给每种原因的用户操作入口（重启、追加预算、改派、解除依赖）。

### P1-13 审计保留与本地磁盘增长
- req §11.2（L1750）审计「默认永久保留」，NFR 无保留上限；本地单机长期使用会持续增长。
- **建议**：定义审计保留策略（按时间/大小）、归档格式、导出后清理；「不可 UI 删除」不等于「永不清理」。

### P1-14 「人类可查看全部」与四级可见性冲突
- FR-TEAM-06（L802）「人类可查看全部」；FR-MEM-10（L1227）有 agent-private / human-only；tgt §12.1（L1320）说助理不注入成员私聊原文。
- **建议**：明确「人类可读」与「可审计」的边界：默认不可读 Agent 私有会话内容，只能看摘要/事件；需要读时进入「审计模式」并留痕。否则 agent-private 名不副实。
