## 0. 总体结论

# **FAIL（有条件）**

方向是可信的：把"对话平台 + Agent 核心 + 可插拔执行后端"作为两个核心模块、三条边界、八条不变量，是本项目最有价值的架构决定；"日志全量、档案精选、提示词极简"的记忆主张、'视图即权限'、'证据优先'、'双时间 + 失效非删除'、'评审作者≠评审者'都落在正确的经验上。

但**作为 v0.0.1 的架构与验收基线，当前不能通过**。原因不是"想法不对"，而是五处关键承诺在现有表述下**既不可实现也不可验证**：

1. **B1** 平台/Core 声称拥有"上下文装配、压缩、会话日志"，而 v0.0.1 选定的 DSH-ACP 后端恰好把这些握在自己手里，且 ACP 只暴露标准语义（无 transcript 回放、无 fork/load、无系统提示词控制面）。这会让"每 turn 可回放/当时模型看到了什么"与"注入预算"落空，并产生双层压缩。
2. **B2** 任务/产出物/评审/决策/审计/成本**没有单一写者**：§5.2 说平台"只负责消息呈现"，但 §10.3/§10.6/§5.4/FR-CHAT-07/FR-SRCH-03 又要求平台拥有任务对象、任务板与跨对象索引；审计在 3 条边界里被 3 次分配；成本/用量**根本没有所有权行**。这直接违反文档自己写的"日志是事实、索引是派生"。
3. **B3** AgentBackend 契约缺**权限应答**（ACP 的 `session/request_permission` 是反向请求）、`resume`、用量回传、契约版本；`prompt()` 与 `events()` 双事件流语义未定义；"固定版本"没有任何版本号，也没有 Node/DSH 安装、降级、许可分发、备份范围的需求与验收。
4. **B4** 安全承诺与机制不匹配："Agent 进程不得直接打开平台数据库"（§5.2）在同 OS 用户子进程模型下无机制；"低风险自动应用"的自适应提示词常驻 system 末尾（§9.7）是一条**持久化提示注入通道**；"不可篡改"（FR-TASK-06）在本地可写 SQLite 上不可成立；"跨平台行为一致"的沙箱承诺不可兑现。
5. **B5** 协议与验收不可判定："高风险"被用作 20+ 处门控但**从未定义**；requirements 附录 A 把 `escalated` 当状态、正文又说它是正交标记、target 明确禁止这样做；返工环（`in_review ↔ changes_requested`）与"新证据重开"都无上限；P0/P1 有 5 处直接冲突；至少 6 个 P0 FR 没有任何验收场景。

**转 PASS 的最小条件**：B1–B5 在文档层面闭合（新增/改写条目），且按附录 A 的"闭合验证清单"能给出可核查证据。按当前进度（作者已在快速打补丁），我估计**一轮集中修订**可把其中 3 条降到 Major；B1/B2 需要架构层做决定，不是措辞问题。

## 2. Blocker（5）

### B1　"上下文装配/压缩/会话"的所有权声明与 ACP 后端现实冲突

**位置**
- target §5.2 L267（"上下文装配/压缩：Core 拥有策略；Backend 可提供 token 计数与压缩能力"）、L266（Core 拥有 session 生命周期）
- target §5.6 L326-333（AgentBackend 只有 spawn/prompt/cancel/close/events/capabilities）、L338（"复用其成熟的……会话日志、压缩与权限审批"）
- target §9.4 L854（"崩溃后能重建『当时模型看到了什么』"）、L866（成员 L1 用 DSH 式会话）
- target §11.4 L1241-1259（9 个分区 + token 预算 + 工具 schema 按需加载）、§11.6 L1273-1280（"逻辑会话由 Go 核心拥有"、压缩检查点三屏障、fork/恢复、中断工具标记"结果未知"）
- requirements FR-MEM-07 L1187-1198（L4 常驻 system 末尾）、FR-MEM-08 L1200-1211、§9.3 L1596、§9.5 L1624
- 交叉事实：`.research/dsh-runtime.md` §4.3（L95-98）——ACP v1 只给标准语义，**不支持 session/load、fork、删除、附加目录、transcript 回放**；控制面只有 `set_config_option`（model/reasoning）；§5（L128）指出 L4 要用 DSH **preset patch** 表达，不是 ACP 能力。

**问题**
文档把"策略所有权"当成了"执行能力所有权"。实际是：
1. 模型实际看到的上下文由 DSH 组装与压缩；平台既看不到组装结果（没有 `request/header` 等价物经 ACP 暴露），也无法控制分段/工具 schema。
2. 于是出现**双层压缩**：DSH 压它自己的会话，Core 再压自己的投影（§9.4 L861、§11.6 L1276）。两份检查点必然漂移，而 L1 的定义（"模型每次调用看到的窗口"）指向的是 DSH 的那一份——文档却在 Core 侧定义预算与检查点。
3. §9.4 L854 的"重建当时模型看到了什么"需要每 turn 的请求快照；全文没有任何对象/FR/存储承载它（FR-OBS-04 回放是 P1，且只要求"查看事件"，不要求请求快照）。
4. §11.6 L1279 的 fork 在 ACP 下不可用；§11.6 L1278 的"中断工具标记结果未知"依赖 DSH 内部 `TOOL_OUTCOME_UNKNOWN` 语义，ACP 不转发（研究备忘 §2.4）。
5. 作者刚加的 §11.6 L1274（"逻辑会话由核心拥有，后端原始日志只作内部调试/归档"）只解决了**归属声明**，没解决**可观测性与一致性**：核心无法凭 ACP 的 `session/update` 重建原始事件流（无 tool 参数、无 request header、无压缩边界）。

**影响**
- §3.3"工作可见"、§5.3 #6、§11.9、FR-OBS-04 的审计/回放承诺无法兑现；
- 注入预算（§9.9）与 L4 注入（§9.7 "常驻 system 末尾"）在 ACP 下没有执行点，只能退化为"首条 user 消息"（削弱指令层级与 KV cache 假设）；
- fork/恢复、崩溃后"结果未知"标记的验收（AC-07）会失败。

**建议（可执行）**
1. AgentBackend 增加 **`promptOwnership: platform | backend`** 与 **`contextSnapshot: bool`** 能力声明。v0.0.1 明确选 `backend`：装配与压缩归后端，Core 只做"注入包"（生成 DSH preset + 首条带来源的 user 上下文 + MCP resource），**停用 Core 侧 L1 压缩**（或仅用于自身投影展示，不进模型）。
2. 新增持久对象 `context.request`（每 turn 一条）：分区摘要、注入条目 ref（消息/档案/任务）、token 估算与来源、模型与超参、backend session/turn id。这是 ACP 下唯一能兑现"当时看到了什么"的手段；配 FR + AC。
3. 明确"backend 压缩事件 → Core 检查点"的可见性映射表：ACP 能看到什么、看不到什么、看不到的部分如何用前后 `context.request` 差分近似；把"漂移检测"做成可观测指标。
4. fork 在 v0.0.1 标注 **native/后续**；ACP 下用"新会话 + 交接包（§12.2）"实现"换个方案重试"。

### B2　任务/产出物/评审/决策/审计/成本缺少单一写者与投影契约（双重事实源）

**位置**
- target §5.2 L269（"任务板/产出物/评审/决策：平台**只负责消息呈现**"）↔ §10.3 L1094-1106（平台核心对象含 `Task`/`Artifact`/`MemoryEntry`/`Approval`/`AuditRecord`）↔ §10.6 L1152（检索范围含"任务、决策、产出物元数据"）↔ §5.4 L300（"平台更新任务投影"）↔ §7.4 L571（provisioning 在平台侧建"任务板/评审/决策视图"）
- **审计三分解**：§5.2 L273（平台=消息/事件审计；Core=行为/记忆/决策审计；Backend=工具调用审计）↔ requirements §9.4 L1614（"消息/事件/**审计**/通知 | 对话平台"）↔ requirements §9.3 L1596（"会话、记忆、任务、**审计**仍在核心框架内"）——同一份 requirements 内两行互相矛盾。
- **成本/用量无所有权**：§5.2 表 15 行中没有"成本/用量/预算消耗"；requirements §9.4 表也没有。但 FR-OPS-05 L1476、FR-OBS-03 L1526、AC-09 L2127 要求"成本数据与模型调用一致（抽样）"。
- requirements §9.4 L1617（任务等为 Core 元数据、平台只存消息/卡片）↔ FR-CHAT-07 L549-559（任务板 P0，含拖拽状态转换）↔ FR-CHAT-04 L513-523（任务卡含状态、可认领/提交/验收）↔ FR-SRCH-03 L1286-1295（跨对象检索）。

**问题**
同一事实（任务状态、verdict、审批结果、成本）至少有两个潜在写者与两个存储，且：
1. 卡片（Message.body_json）里带任务状态（§10.4 L1120、FR-CHAT-04），任务状态又是事件投影（§11.7 L1289）——卡片是投影还是快照？谁在状态变化时改卡片？`edited_at` 会不会造成"历史卡片被改写"？均未定义。
2. §5.4 L300"平台更新任务投影"与 §5.2 L269"平台只呈现"直接冲突。若投影由平台写，Core 又持有任务状态，就是双写；若由 Core 写，平台的"跨对象检索"就依赖 Core 推送，索引与消息索引不在同一事务，违反 §5.3 #2 的类比承诺。
3. 审计被切三份后，没有"单一可查询审计流"：§10.9 L1190 要求"不可 UI 删除、可整体导出"，FR-SEC-06 L1410 要求"审计可按对象/人/时间/动作查询"，但三份存储的合并查询、排序、去重、导出格式无任何定义。
4. 成本没有 owner，直接导致：重试/重放的重复计费无法判定（AC-09 抽样一比就对不上）、预算暂停（FR-OPS-05）依据哪份数据不明、成本视图与"模型调用次数"可能来自不同平面。

**影响**
- 违反不变量 #3（索引是派生，可重建且一致）与 #2 的"同一事务"精神；
- UI/搜索/通知与任务真相可能不一致，且无法判断谁对；
- 成本对账与预算暂停会误伤或漏管；审计无法作为事故取证的单一口径。

**建议（可执行）**
1. 采用 **CQRS-lite** 并写进 §5.2：Core = 任务/产出物/评审/决策/成本的**唯一写模型**；平台只存 `domain event` + 物化投影（`task_view`/`artifact_view`/`decision_view`），投影只能由 Core 通过**带幂等键的 API** 写入；平台不得存在第二条写路径（明确禁止改卡片改状态，卡片只能是投影渲染）。
2. 新增两行所有权：**成本/用量 → Core（per-call ledger：call_id 幂等键、provider/model、tokens、cost、retry_of、budget_scope）**，平台只读投影；**审计 → 平台（唯一 append-only 流）**，Core/Backend 通过 API 提交 audit event（`plane/source/actor/action/object/result/approval_id`），各平面明细日志降为二级证据。
3. 定义投影契约：投影延迟 SLO（如 p95 < 1s）、每日对账任务（事件数 vs 投影行数 vs 成本笔数）、UI 显示一致性状态、重建投影的命令与耗时目标。
4. 修 requirements §9.3 L1596 与 §9.4 L1614 的审计归属矛盾（二者只能留一处，其余引用）。

### B3　AgentBackend 契约不完整；运行时依赖/版本/许可/降级没有交代

**位置**
- target §5.6 L326-333；requirements §9.5 L1624（同一 6 方法清单）
- 缺失能力（逐条对照 ACP 事实）：
  - **权限应答**：ACP 用反向请求 `session/request_permission`（研究备忘 §4.3 L95）。契约里没有 `respondPermission(requestId, decision)`，所以 §5.2 L272"Backend 执行审批结果"、§11.5 L1267"高风险动作弹审批卡"在 v0.0.1 无闭环接口，AC-08 L2089 会失败。
  - **`resume`**：重启后恢复 agent 会话需要它（ACP 有 `session/resume`，研究备忘 §4.3）；没有它，§11.10 L1307"重启后从游标恢复"只恢复平台侧，Agent 侧重新开新会话。
  - **用量/成本回传**：没有 usage 事件，预算/成本只能靠猜。
  - **契约版本/健康检查/错误分类**：没有 `contractVersion`、`health()`、错误分类（transport/protocol/model/tool/permission），"固定版本 + 契约测试"（§5.6 L346）无落点。
  - **双事件流**：`prompt() -> stream<Event>` 与 `events(handle) -> stream<Event>`（L329/L332）语义重叠：谁权威、如何合并、如何背压、如何用幂等键去重，全未定义。
- **版本/依赖**：§5.8 L367 只写"固定版本"，全文无版本号；requirements §9.2 L1589"依赖透明"、§13.1 L1865"安装包可检测依赖"、NFR-COMPAT-03（"无需用户安装数据库/搜索引擎"）都没有覆盖 **Node/后端运行时**；§5.5 L315 允许"0 个执行后端进程"，但没有任何"无后端模式"的需求（0 个后端 = 无 agent，产品如何工作？）。
- **"单二进制"冲突**：§2.4 L87、§3.2 L107、§15.1 L1564 的"单二进制/少依赖"只在平台本体成立；v0.0.1 实际需要 Go 产物 + Node + npm 包（DSH 0.2.1-rc.5）。
- **备份/导出范围**：DSH 会话日志在 `DSH_HOME`（JSONL+Zstd，且**没有删除会话的接口**，研究备忘 §2.3 L44-50），不在平台数据目录；FR-OPS-01（备份）/FR-OPS-02（导出）/AC-10 L2134 的"全量"范围没有包含它。
- **许可/分发**：§5.8 L367 只说保留 MIT 声明；没有"随包分发 vs 用户自装"的决策，因此也没有 NOTICE/第三方许可清单、Node 许可、以及 NFR-SEC-08（依赖审计）在发布物上的落点。

**影响**
- 审批链断 → 高风险工具无法闭环（安全验收失败）；
- 重启后 agent 上下文丢失，与"崩溃恢复"承诺不符；
- 成本/预算不可信；版本升级会静默破坏；
- "30 分钟安装"（4.3 L171）在要用户另装 Node 时不可达；备份/导出"完整"是假承诺。

**建议（可执行）**
1. **契约 v1**：`contractVersion` / `spawn` / `resume` / `prompt` / `cancelPrompt` / `close` / `respondPermission` / `usage` / `health`；定义**单一事件流**（或明确两流合并规则），并给出"backend event → 平台 message/event → audit"映射表与幂等键 `(session_id, turn_id, seq)`。
2. **运行时基线附录**：DSH 精确版本（当前 0.2.1-rc.5）、Node 最低/固定版本、profile、`DSH_HOME` 位置与收归策略、启动自检（`--dump-config`）、契约测试套件与金标准任务在 CI 的位置、升级 canary/回滚流程。
3. **新增 P0 需求**："执行后端缺失/不可用/版本不匹配时，平台仍可启动、浏览、检索、导出、显示修复指引，不产生半队状态"；把 NFR-COMPAT-03 扩为"依赖检测清单（含 Node/内核/版本）"。
4. **备份/导出范围**：平台库 + Core 库 + 后端会话目录 + 附件 + 配置（密钥只存引用）；声明"后端日志因无删除/导出 API，只支持目录级快照与整包归档"。

### B4　安全承诺与机制不匹配；L4 自修改是持久化注入通道

**位置**
- target §5.2 L276（"Agent 进程不得直接打开平台数据库"）、§13.3 L1421（"禁止…直接写平台库"）——无机制。
- target §5.7 L356（密钥"OS keychain 或本地 0600 文件"）、§13.5 L1434（数据目录 0700）——POSIX 语义；Windows 无 0600/0700。
- target §9.7 L975（L4 注入 system 末尾）、L988（"主管/助理可以提议 + **自动应用**低风险修改"）——自动应用的文本进入 system 稳定区 = 持久化提示注入；§13.4 L1426 只把"外部内容"标不可信，**记忆/L4 没有被当作数据边界处理**。
- target §13.4 L1425 指令层级里"人类指令"高于角色卡；但人类偏好可由助理代记（§9.3 L842"人类拍板时助理代记"）→ "人类指令"与"Agent 转述"不可区分。
- requirements FR-TASK-06 L890-899"不可篡改"、FR-SEC-06 L1410"审计不可 UI 删除"；target §5.3 L287"会话日志不可变"——本地同用户可改 SQLite 文件，无哈希链/WORM。
- requirements FR-SEC-03 L1377"跨平台行为一致"——Windows/macOS/Linux 沙箱能力本质不同，不可承诺。

**问题**
文档同时主张两种互相排斥的安全模型：既按"同机不可信子进程"设计（禁止 Agent 碰库、密钥分离），又依赖"同一 OS 用户 + 子进程"的部署形态（§5.5）。在没有 OS 级隔离的情况下，这两条禁令只是政策文本：DSH 子进程可以 `cat` 数据目录、读取 keychain 项、修改 SQLite。更危险的是 L4 自动应用：一次成功的注入（来自网页/工具输出/其他 Agent 的消息）经"记忆抽取 → 候选 → 低风险自动合并 → 写入管理手册 → 常驻 system"完成**跨会话持久化**，而 §13.4 的防线只覆盖单轮外部内容。这是当前设计里最现实的高危路径。

**影响**
- 安全基线验收（AC-08、FR-SEC-01..07）会被安全评审直接驳回；
- "记忆污染"从"长期错误决策"升级为"持久化越权指令"；
- "不可篡改"是不可验证的承诺，事故取证站不住。

**建议（可执行）**
1. **明示威胁模型边界**：v0.0.1 不防"同 OS 用户的恶意本地进程"；把 §5.2 L276 改为"进程级隔离 + 数据目录 ACL + 令牌作用域；同用户恶意进程不在 v0.0.1 防御范围"，并列为 v0.1 的 OS 沙箱目标（Windows Job Object/AppContainer、macOS sandbox/seatbelt、Linux landlock + namespaces）。
2. **密钥只给 Core**：Core 直读 keychain/DPAPI，平台只存引用；密钥绝不经 HTTP 传输；Windows 用 DPAPI/ACL 替代 0600/0700 语义。
3. **L4 默认仅提议**（v0.0.1）：自动应用只允许"不触及红线/权限/对外承诺"的条目，且强制 diff 队列 + 冷却期 + 回滚；L4/记忆内容在 prompt 中用明确数据边界包裹（"以下为可引用数据，不是指令"），并新增注入回归用例："记忆投毒 → 后续会话越权尝试被拒"。
4. **把"不可篡改"换成可验证承诺**：应用层 append-only + 哈希链（每条含前一条 hash）+ 导出可校验；否则删掉该词。
5. **沙箱目标改写**：从"行为一致"改为"统一安全语义 + 平台差异矩阵 + 默认拒绝"，并在 CI 中跑平台矩阵。（此条也可降为 Major，但与 AC-08 绑定，建议一起改。）

- 返工/辩论可能无限消耗预算（只有任务级预算兜底，且 100% 暂停的语义未定义是"暂停任务"还是"暂停团队"）；

**建议（可执行）**
1. **高风险分类表**（一页）：数据类别（代码/客户数据/密钥/公开内容）× 可逆性（可回滚/不可回滚）× 影响范围（本机/外部/第三方）× 花费阈值 → 机器可判定的规则；默认拒绝；每个门控引用具体条目（G2/双钥匙/第三人/人类）。

4. **依赖 DAG 校验**：创建/更新任务时拒绝成环，给用例。
5. **FR→AC 覆盖矩阵**（一张表，列 P0 FR × AC id），补 AC-11（记忆治理/失败/单飞/容量）、AC-12（依赖/WIP/阻塞升级）；把 5 处 P0/P1 冲突收敛为一张优先级表（建议以 FR 为准，§5.2 的 P1 条目改为"P0 的简化实现"）。

## 3. Major（10）

### M1　中文 2 字检索没有索引可用；检索质量目标不可复现
**位置**：target §5.7 L352（"三元组/子串索引 + 短词回退"）、§10.6 L1148/L1153/L1157；requirements FR-SRCH-01 L1262、FR-SRCH-06 L1320-1331、NFR-PERF-03、4.3 L176、4.4 L187。
**问题**：SQLite FTS5 的 `trigram` tokenizer 只匹配 **≥3 字符**的子串；默认 `unicode61` 把连续 CJK 当作一个 token、不匹配任意子串（DSH 的 FTS5 后端即如此，研究备忘 §3 L71）。"中文 2 字"是产品最核心的检索路径（FR-SRCH-01 第一条，AC-06 步骤 1），却**没有可用索引**，只能表扫描 `LIKE '%限流%'`——这与"三元组索引"的叙事不符，也和 p95 150–300ms 的"常见过滤组合"没有绑定关系。另：Recall@10 需要 qrels，但没写谁标、标多少、如何仲裁、语料版本；没有机器规格（CPU/内存/盘型），p95 不可复现。
**建议**：明确三类索引（bigram 倒排覆盖 2 字 + trigram/FTS5 覆盖 ≥3 字 + 结构化列）；为 2 字路径单列 p95 预算（例如 100k 行 ≤150ms）与容量上限；把基准装置写进附录（机器规格、语料生成器、warm/cold、p50/95/99、查询混合比）；qrels 双人标注 + 仲裁 + 版本化，纳入仓库。

### M2　"已确认消息 0 丢失"与"p95<100ms"的持久化口径不一致
**位置**：target §5.3 L283、§10.5 L1138-1142、§14.1 L1483-1489；requirements NFR-REL-01、NFR-PERF-02、AC-07 L2065-2087。
**问题**：未定义"已确认"的 ack 点（HTTP 200 / commit 返回 / fsync 完成）；未声明 SQLite `synchronous` 策略与 WAL 行为；WAL+NORMAL 在断电时可能丢最近提交，而 100ms 可见性又在鼓励不 fsync。AC-07 只测进程被 kill（页缓存仍在），不测断电/磁盘满/DB 损坏。游标推进与"处理效果持久化"的先后未定义——若先推进游标再持久化，at-least-once 会退化成 at-most-once（丢消息）。
**建议**：定义 ack = "commit 返回且按配置同步"；给两档（性能档 NORMAL + 明确"断电可丢最近 X ms"；可靠档 FULL + 放宽 p95）；明确"游标仅在效果持久化之后推进"并写成不变量；补断电/磁盘满故障注入，或明确 v0.0.1 只承诺"进程崩溃零丢失"。

### M3　四层记忆范围过大；缺 agent 侧读取通道；缺每 turn 上下文快照
**位置**：target §9.2-§9.10 L816-1050；requirements FR-MEM-01..12 L1114-1258；矛盾点：requirements §9.5 L1625"v0.0.1 可延后 MCP" vs FR-MEM-08 L1205"默认稀疏……模型按需读取"、target §9.9 L1019 同。
**问题**：要实现"按需分页读取档案"，agent 必须有一个受权限约束的查询工具；v0.0.1 又允许延后 MCP，而 AgentBackend 没有 memory 工具面 → 该能力**无处安放**。同时双时间（3 类实体）、容量治理（渲染/存储双上限、压缩自校验、快照、墓碑）、读取留痕、注入预算 5 类机制全压在 M4 一个里程碑，验收只有 AC-05 一个场景，不覆盖 FR-MEM-06/11。
**建议**：v0.0.1 冻结"M-a 最小闭环"（档案 CRUD + 3 类事件触发抽取 + 注入 + 检查器 + 删除/纠正 + 渲染上限），把双时间扩到全实体、压缩自校验、快照保留、读取留痕批量化推迟到 v0.1；把 memory.read 作为 AgentBackend 一等能力或 v0.0.1 必做 MCP server（二选一写进 FR）；补 AC-11。

### M4　注入预算百分比与绝对尺寸/模型窗口不匹配；token 计数无定义
**位置**：target §9.7 L967（800–1500 字 ≈ 1.5–3K token）、§9.9 L1008-1015、§11.4 L1255；requirements FR-MEM-07 L1189-1198、FR-MEM-08 L1200-1211。
**问题**：作者已加"相对权重、归一化、合计不超过 100%"（L1008），但 5–8% 与"800–1500 字"隐含总窗口约 30–37K token：对 200K 窗口模型，8% = 16K token（手册远用不完，预算形同虚设）；对 32K 窗口又过紧。token 计数来源只说 backend"可提供"（§5.2 L267），没有时预算无法执行；也没说按模型 tokenizer 还是估算。
**建议**：预算公式 = `min(百分比 × 有效输入预算, 绝对上限)`；给 32K/128K+ 两套模型窗口预设；明确 token 计数来源与 5–10% 安全边际；给出超限时的确定性裁剪顺序（已基本有，补"同一分区内的先后规则"）。

### M5　跨进程 provisioning 的原子性/幂等/对账缺失
**位置**：target §7.4 L577、§5.4 L295-300；requirements FR-ASST-04 L665-675、FR-ONB-03 L443-452、AC-02 L1944-1966。
**问题**：团队/Agent/频道/任务板/记忆命名空间分布在两个进程与多个存储；没有 `provisioning_id` 幂等键、saga 补偿清单、孤儿检测。AC-02 只测"重复执行 provisioning"，不测"中途失败后重试"——而"失败不能留下半支团队"（L577）恰恰是中途失败语义。
**建议**：定义 provisioning 状态机（planned → platform_created → core_created → verified），每步幂等键 = `provisioning_id + step`；列补偿顺序与不可回滚项；启动/定时对账 + "孤儿报告"UI；AC-02 增加"每一步注入失败后重试"的用例。

### M6　三套 ACL 未统一（平台会话 / Core 资源 / 记忆四级）
**位置**：target §5.2 L272、§9.10 L1023-1028、§12.1 L1330-1340、§10.6 L1155；requirements §11.3 L1762-1770、FR-SRCH-04 L1297-1307、FR-TEAM-06 L796-806。
**问题**："先过滤再排序"的跨对象检索需要同时应用两套 ACL；任务/产出物可见性由团队派生而团队 ACL 在 Core；平台索引要么复制 ACL（需定义权限变更后的传播延迟），要么每次查 Core（需定义延迟预算）。"不泄漏数量/存在性"在跨平面 join 下更难保证，且错误消息也可能泄漏。

### M7　没有持久化定时器/任务队列的需求，但依赖大量时间语义

**建议**：新增"定时与到期"需求：`timer(due_at, kind, payload, idempotency_key, fired_at, attempts)`；启动补跑；错过窗口策略（立即/跳过/合并）；纳入 AC-07 与 AC-09。

## 6. 三条建议（不阻塞发布，但显著降低后期返工）

1. **先冻结"基准装置"再做检索与性能**：一个独立附录写清机器规格、语料生成器（10 万条中文/中英混排/代码标识符混合）、查询混合比、qrels 标注规范与仲裁、warm/cold 与分位数口径。M1/M2 的争议本质是"没有共同标尺"，先有尺子再谈 150ms 还是 300ms。
