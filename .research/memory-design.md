# 记忆架构研究：NeoBot 四层记忆 → 主管/助理 Agent 的团队管理记忆

> 任务：task-2｜作者：researcher-memory｜日期：2026-11-16
> 服务对象：`doc/target.md`、`doc/0.0.1 最初版/requirements.md`。本文只做设计研究与取舍建议，不含实现代码。
> 证据：外部来源见文末附录 B；本地证据的文件绝对路径见附录 A。

## 0. 一页结论

1. **四层记忆的本质不是"四张表"，而是三种时间尺度 + 一条自我修改通道**：短期上下文（本次会话）、触发式记忆（批处理把对话变资产）、档案记忆（跨会话的实体知识）、自适应提示词（Agent 自己改自己的系统提示词）。前两层解决"不失忆"，第三层解决"不重复问"，第四层解决"越用越懂"。
2. **NeoBot 最值得抄的不是分层，而是失败语义**：单飞锁、冷却、部分成功清账、压缩失败恢复原文、快照留痕、内部表豁免、关闭时冲刷、超限可观测。这些决定了记忆系统"敢不敢被信任"，比抽取算法更影响产品感。
3. **主管/助理 Agent 的记忆对象要换，机制几乎不用换**：把 `user/group/item` 换成 `人/团队/项目/任务/决策/争议`，四层仍成立；但**触发条件必须从"每 N 条消息"改成"按事件"**（任务关闭、返工、辩论裁决、人类拍板），消息量触发只保留为兜底水位。
4. **成员 Agent 应保持"DSH 式全量 session + 稀疏档案"**：session 是不可变的私有工作日志（可压缩、可回放），档案是组织资产；两者之间用"成员提交候选记忆 → 主管/助理审核晋升"连接，把"写组织资产"的权力收在管理层，天然形成去重与冲突的收敛点。
5. **建议分层：L0 事件日志 / L1 session / L2 候选记忆 / L3 档案 / L4 管理手册 + L5 检索与注入预算层**。前五层是存储，L5 才是体验；NeoBot 的"档案默认不全量注入、按需读取"应作为默认值继承。
6. **本项目相对 NeoBot 有一处结构性优势**：消息全量落库。NeoBot 的短期记忆是**进程内队列**，重启即丢；我们的 L1 可以直接是"从消息库按窗口投影"，L0（全量日志）天然存在，代价是要自己设计压缩与检索。

## 1. NeoBot 四层记忆的实际形态（a）

### 1.1 先纠正一个印象：它其实是"1 个队列 + 3 套落库机制"

`docs/04-功能文档/记忆系统.md` 自己写明：短期记忆**没有独立服务**，可用的只有进程内消息队列 + 已落库的档案/画像/好感度/自适应提示词；`packages/memory/service.py` 的 `MemoryService`（`remember`/`recall`）、`MemoryReader` 协议、`contracts/ports/memory.py` **目前没有任何调用方**，属于"应用启动时构造一个实例、但没有任何代码读写它"的规划接口。

> **设计含义**：这是本项目最该避免的坑——**先写 ports/接口、后接调用方，会留下无法验证的空壳**。MVP 阶段建议"存储 + 调用方"一起落地，接口等第二个消费者出现再抽。它同时说明：四层记忆是**文档层的能力叙事**，实现层是拼装出来的，不必迷信"每一层一个 service"。

### 1.2 L1 短期上下文 = 消息队列（无压缩、无摘要、进程内）

| 维度 | 事实 | 来源 |
|---|---|---|
| 数据模型 | 群聊/私聊各一条独立队列，元素是消息 + 发送者 + 时间 + 图片索引 | `04-功能文档/聊天与回复.md` |
| 容量 | `chat.max_group_chat_observations` / `max_friend_chat_observations`，默认 **200** | 同上 |
| 文档漂移 | 记忆文档写"上限约 100 条"，与配置/聊天文档的 200 不一致 | 记忆系统.md vs 聊天与回复.md |
| 生命周期 | 进程内；重启丢失，仅靠"启动预热历史"补 | 聊天与回复.md |
| 治理 | 无压缩、无摘要；图片只入索引（`[图片:tmp_xxx file:<路径>]`），需要时取回，队列不占上下文 | 同上 |

**对本项目**：我们的 L1 不该是内存队列，而应是"**从消息库按窗口投影出的工作上下文**"（可重建、可回放、多副本一致）。图片/附件同理：只入引用，不占上下文。文档漂移也提醒我们：**容量数字必须只有一个真相源**（建议写进配置 schema 的 description，文档引用它）。

### 1.3 L2 触发式记忆：一条"把对话变资产"的批处理管道（最值得抄）

| 维度 | NeoBot 的做法 |
|---|---|
| 触发条件 | 群聊每 `group_interval=500` 条、私聊每 `private_interval=200` 条消息；`0` 禁用 |
| 输入构造 | 待总结消息按 `[序号] 发送者: 文本` 注入，单条截断 `prompt_snippet_chars=120`；模型可用 `archive_crud__read_pending_messages(conversation_key, indices)` 按需读全文 |
| 预算 | `max_tool_rounds=20`（防工具失败反复烧 token）、`max_summary_seconds=300`（单轮总结总时长）、`model_call_timeout_seconds=0` 表示自动跟随该模型 `timeout_seconds` 再留 15 秒余量 |
| 为什么"自动+15 秒" | 思考模型单次调用常超 60 秒；固定短超时会形成"超时→重发完整上下文重试→再超时"的死循环（超时请求不计 usage，但服务端已按实际生成计费） |
| 写入方式 | 全量档案只用 `patch_archive` 增量（`append/prepend/replace/delete`），**不需先读全文、不重写整条**；只有定长摘要（`user_summary`/`group_summary`）允许 `save_archive` 整条重写，且仅当内容确实要变 |
| 失败语义 | 所有工具调用都失败→保留计数、下次重试；**已成功写入档案后才超时→按"部分成功"清账、不重试**（append 语义重跑会重复写同一批事实；重试还要重发全上下文且大概率再次中止），只留告警 `reason=model_call_timeout`/`budget_exhausted` |
| 并发控制 | 每个会话单飞锁；失败指数退避 + 冷却；写回只在计数器锁内合并冷却字段，不覆盖并发追加的消息 |
| 关闭冲刷 | `flush_all` 遍历"有未总结消息但未到阈值"的会话立即各触发一次；**并发 50、总预算 600 秒**；到点只停止启动新的、**不取消在途**；未总结消息保留，下次启动继续 |
| 可观测 | 用量归集到 `agent:memory`，面板可看；告警带稳定 reason 码 |
| 部分成功的安全阀 | 总结成功后只销账"本次已总结"的消息，总结期间新到的消息留到下一轮 |

**设计含义**：这一层的产品价值 = **让闲聊沉淀为可信资产**。三个判断值得直接继承：
- **"部分成功"必须被显式建模**。append 型写入天然不可幂等，"重试=重复写"是这类系统的第一性事实。我们若用 append/事件追加，也必须区分"没写成功"与"写了但超时"。
- **预算必须三层**（单次模型调用超时 / 单轮总时长 / 工具轮数），只设一层一定会踩死循环。
- **关闭路径也是记忆路径**。优雅关闭时冲刷未总结消息属于"数据不丢"的最低要求；本项目本地优先、进程随时被关，这条比 NeoBot 更重要。

### 1.4 L3 档案记忆：实体表 + 双上限 + AI 压缩 + 快照

- **实体划分**：`user_profile`（对某人的印象）、`group_profile`（对某群的印象）、`user_summary`/`group_summary`（定长摘要）、`item_archive`（以关键词为键的独立表，记录物品/事件/话题，总结时同步写入）。
- **两个上限必须分开**（最容易搞混、也最值得写进我们的文档）：
  - **渲染上限**：`max_chars=500`（个人）/ `group_profile_max_chars=1500`（群），只限制"注入提示词展示多少"，超出由模型分页查阅；
  - **存储上限**：`max_total_chars=15000`，单条档案硬上限。
- **溢出策略二选一**：`summarize`（**先完整落库**→异步触发一次压缩→工具立即返回 `over_limit/total_chars/compressing/hint`）或 `reject`（不落库，返回错误 + 压缩指引，模型自行压缩后重试）。压缩目标固定 `min(max_total_chars, 10000)`，压完留 5000 字余量，避免"严格按上限压完立刻又超"。
- **压缩不是截断**：由总结 Agent 读全文后**整条重写**（保留事实、合并重复、只丢冗余），共用私聊 compact 的结构化检查点章节。正文超 **60000 字符**时只保留首尾，**要求模型先用 `read_archive(mode=outline)` 定位、再用 `offset` 分页回读中间段**（每页 500 字，负 offset 从尾部读）后才允许写回；写完**必须核对返回的 `total_chars` ≤ 目标**，未达标不得声称完成。
- **失败兜底**：模型异常/超时/无有效写入/压缩后仍超目标 → **恢复压缩前原文**（走乐观锁，**不触发容量治理**，避免"回滚→再次超限→再压缩"循环），记失败退避，绝不静默留半成品。
- **快照与历史**：每次压缩**开始前**把原文写入 `archive_snapshots`（`table_name/key/value/total_chars/version/reason/operator_ip/created_at`）；同一 `(table,key)` 保留最近 10 份、全表 2000 份兜底；面板"压缩历史"**只读**，不提供"恢复到此快照"（恢复走人工编辑接口）。
- **容量治理的豁免名单**：内部表 `memory_counter`（存待总结消息 JSON）**永久豁免**——对它 reject 会让计数写不进去、整条总结管线断掉；对它 summarize 会让压缩器吃掉未总结消息。误伤的表现是"档案自动总结整体失效"。
- **手动/批量压缩**：目标字符数只对本次生效（不写回配置），下限 200；批量一次最多 20 条、逐条串行；目标 ≥ 当前字数直接 `skipped`（零 token）。
- **可观测**：服务层 `list_over_limit(table)`/`count_over_limit()`；`archive_stats` 跨条统计；`list_archive` 只返回每条开头 **500 字符**预览（默认 5、上限 20）+ hint 引导分页续读；面板预览 200 字符——**两处口径有意不同（人扫读 vs 工具预算），不要强行统一**。

**设计含义**：档案不是 KV，而是**有容量预算、有版本、有审计的可写文档**。"渲染上限 ≠ 存储上限"建议原样进入 target.md；"压缩必须基于全文 + 自校验字数"应成为档案治理规范；"内部表豁免"提醒我们：**治理规则一定要有白名单，否则会把元数据管线一起拧死**。

### 1.5 L4 自适应提示词：200 字的"自我修改通道"

- 载体：文件 `data/自适应提示词.txt`；工具 `update_adaptive_prompt(content, action=append|replace)` / `read_adaptive_prompt`。
- 限额：`adaptive_prompt_max_chars=200`（默认），超出**尾部静默截断**（返回体有 `truncated` 标记）；写入用 tmp 文件 + replace 原子替换，进程内 `asyncio.Lock` 串行。
- 注入：注册为 `adaptive_prompt` 块，阶段 `system_append`（system 末尾、"稳定内容，利于上下文缓存"），**每轮注入**。
- 写入规则写在 Skill instructions 里：只记"经过对话确认的、可信的信息"；不记推测/一次性内容；简洁；信息过时时主动更新或删除。

**设计含义**：L4 的经济学是"**最贵的几十个 token 放什么**"。200 字对聊天人格够用，对"管理者"远远不够（见 2.4）。它的三个缺口正是我们的机会：**无版本、无审计、无冲突检测，且截断静默**。L4 必须被当成"系统提示词中受预算管辖的一个分区"，而不是 Agent 的便签。

### 1.6 检索与注入：真正决定体验的部分

| 机制 | 做法 | 对我们的启示 |
|---|---|---|
| 群聊注入 | 默认**只注入群档案**（`group_summary` 优先、缺失回退 `group_profile`，超长截断+引导）；群员档案默认**不注入**（`chat.inject_member_archives=false`），成员列表只保留昵称/QQ/好感度/印象等轻量信息，并附"用 `read_archive` 按需读取"的提示块 | **默认稀疏、按需拉取**是正确默认值；全量注入成员档案 = token 灾难 + 隐私风险 |
| 私聊注入 | 注入对方档案，超长截断到 `max_chars`，附分页/大纲读取引导 | "先给摘要 + 给取数路径"优于"给全文" |
| 增量注入 | 新出现的群友档案在 3 处增量注入（挂起恢复块 / `wait` 等待期间的工具结果 / 循环中途新消息之前），渲染成功后登记 uid，失败下次重试 | 档案注入是**事件驱动的增量**，不是每轮重算 |
| 工具输出压缩 | 重新构建提示词前只保留最近 `tool_result_full_keep=10` 条完整工具结果，其余按类压缩：基础回复类只留"调用成功"，其它留 200 字摘要；按 `tool_call_id` 去重，不改消息顺序以保证 assistant tool_calls 与 tool 结果一一配对 | 长会话里**工具输出是最大的垃圾来源**；压缩必须保结构（配对），否则 API 直接报错 |
| 私聊超限 compact | `private_chat_max_tokens` 达到后不结束会话，把较早历史压成一条 **DSH 风格 compact 检查点**（`<compacted-summary>` + 8 个结构化章节：Primary Request / Key Technical Concepts / Files and Code / Errors and Fixes / Pending Jobs / Current Work / Next Step / Critical Context），保留最近 **8** 条；只替换管线内存中的历史，**原始消息队列不变**；失败保留旧行为 | 压缩用**结构化检查点**而非自由摘要，可显著降低"摘要丢关键标识"；压缩只改投影、不改日志——与我们 L0/L1 的分离同构 |

补充：NeoBot 明确写了 compact 指令"借鉴自 DSH compaction"，复用 `app/src/neobot_app/runtime/compact.py` 的模板（preamble 与 DSH 一致、要求"空章节写 (none)、不得丢章节、不得编造"）。这是"跨项目复用提示词资产"的好先例。

### 1.7 三个坑（反面清单）

1. **空壳接口**：`MemoryService`/`MemoryReader`/ports 无调用方（见 1.1）。
2. **废弃配置与文档漂移**：`archive.auto_compact_chars` 标注"已废弃、从未接线"；队列上限 100 vs 200。
3. **静默截断/静默失败**：自适应提示词尾部截断、档案超限降级为"保留原文 + WARNING + 超限标记"——降级本身合理，但**必须可观测**（NeoBot 用 `list_over_limit` 补上这一环，值得学）。

## 2. 从"聊天机器人"改成"主管/助理 Agent"（b）

### 2.1 换对象，不换机制：记忆对象矩阵

| 实体 | 键 | 典型内容 | 写者 | 读者 | 时间性要求 |
|---|---|---|---|---|---|
| member（成员 Agent） | agent_id | 能力域与置信度、偏好、历史产出质量、返工率、擅长/不擅长的任务类型 | 主管/助理（系统观察）、成员自述 | 主管（派单）、助理（排期） | 能力分需衰减 + 证据计数 |
| human（人类主管/用户） | user_id | 目标与偏好、决策风格、红线、沟通节奏、已授权范围 | 助理（高权威） | 主管、助理、成员（受限） | 决策与红线永久；偏好可过期 |
| team | team_id | 章程、目标、成员名单、阶段、共识与分歧、例行节奏 | 主管 | 全团队 | 阶段/名单 upsert |
| project | project_id | 范围、里程碑、约束、依赖、风险 | 主管 | 主管/成员 | 里程碑可改，历史保留 |
| task | task_id | 目标、验收标准、指派人、状态、返工原因、产出物引用 | 主管 | 主管/成员 | 状态 upsert，返工原因追加 |
| decision（ADR 式） | decision_id | 决策、备选、理由、影响面、推翻条件、时间 | 主管/助理（人类拍板时由助理代记） | 全员 | **强制双时间**（何时生效 / 何时失效） |
| dispute（跨团队争议） | dispute_id | 双方立场、证据、裁决人、裁决、遗留风险 | 主管 | 主管、人类 | 双时间 + 双方立场不可覆盖 |
| capability（能力标签） | (agent_id, domain) | 分数、证据数、最近验证时间、失败案例 | 系统统计 + 主管校正 | 主管（派单） | 衰减 + 可申诉 |

**关键映射**（NeoBot → 本项目）：`user_profile` → member/human；`group_profile` → team；`item_archive`（关键词键）→ decision/dispute/capability 这类"以业务键为主键"的表；`favorability` → trust（见 2.3）；`user_summary` 的"定长摘要"角色 → 由 team/project 的"当前叙事摘要"承担（供注入用，可整条重写）。

### 2.2 四层在新语境下的重定义

| 层 | 新载体 | 触发 | 预算/注入 | 与 NeoBot 的差异 |
|---|---|---|---|---|
| L1 短期上下文 | 会话（DSH session）+ 当前任务工作区 | 每次模型调用 | 压缩阈值 + 保留尾窗 | 从"内存队列"改为"可回放投影" |
| L2 触发式记忆 | **事件驱动的总结/抽取管道** | 任务关闭、返工、辩论裁决、人类拍板、成员产出被拒、里程碑达成、成员入队/离队；**兜底**：每 200 条消息或 24 小时 | 单轮预算 + 单飞 | **触发源从"量"变"事件"** |
| L3 档案记忆 | 上表八类实体 | L2 产出 + 管理层直接写 | 渲染上限 vs 存储上限分离 | 增加**双时间**与**证据引用** |
| L4 自适应提示词 | **管理手册**（Manager Playbook） | Agent 自主 + 人类可编辑 | 800–1500 字，分区注入 system 末尾 | 额度放大、要求分章节、要版本 |
| L5 检索/注入 | 查询路由 + 预算分配 + 降级 | 每次组 prompt | 见 4.4 | NeoBot 没有独立一层，本项目必须补 |

**为什么必须"事件触发"**：团队场景里消息量与信息量严重脱钩——一场长辩论可能 300 条消息只产出 1 个决策，而人类主管一句"以后都用 pnpm"只有 1 条消息却价值最高。按条数触发会同时**漏掉高价值单句**、**放大低价值长聊**。建议双通道：事件通道（高优先、立即）+ 水位通道（兜底、批处理、失败冷却）。

### 2.3 好感度 → 信任度 + 能力置信度（慎用数值化）

NeoBot 的 favorability 是关系亲密度（-1000~1000，每次总结最多 ±5，影响提示词中的互动倾向）。管理者需要的不是"亲密度"，而是**可解释的可靠性判断**：

- `trust(0..1)`：该成员/团队产出被接受的比例（滑动窗口），带衰减；
- `capability{domain: (score, evidence_count, last_validated)}`：领域能力，必须**同时有证据数与最近验证时间**，否则分数无意义。

**风险与取舍**：数值化会固化偏见、形成"标签自证"（低分成员拿不到好任务 → 分数更低）。三条护栏：
1. 数值**只用于派单排序提示**，不把分数原文注入提示词（注入"最近 3 次验收记录"这类证据更好）；
2. 必须衰减 + 允许人工校正 + 允许成员申诉（申诉记录写 decision/dispute）；
3. 禁止把 trust 用于对外可见的评价或作为唯一淘汰依据。

NeoBot 的头像视觉分析（从非任务数据推断性格印象）在团队成员场景**建议默认关闭**：收益低、伦理与隐私风险高。

### 2.4 自适应提示词 → 管理手册（Manager Playbook）

NeoBot 的 200 字适合"说话风格"，但主管 Agent 的 L4 要装的是**可复用的管理判断**。建议：

- 额度 **800–1500 字**（约 1.5–3K token），按**固定章节**组织，便于审计与 diff：
  `# 角色与目标` / `# 管理原则（派单、验收、返工）` / `# 红线与升级规则` / `# 人类主管的偏好` / `# 团队现状速记（≤200 字，滚动更新）`。
- 注入位置：system 末尾稳定区（利于前缀缓存），**不要**混进上下文 user 块。
- 写入规则：只允许"经过事件验证的教训"（如"该团队在无验收标准时会返工"），并要求每条带来源事件 id；**禁止写一次性任务细节**（那属于档案）。
- 与档案的**边界**：L4 是"判断规则"，L3 是"事实"。写进 L4 的内容必须能指导**未来的多次**决策；只对一次任务有用的写 L3。

### 2.5 三种视角：权限即视图

| 角色 | 注入什么 | 绝不注入 |
|---|---|---|
| 主管 Agent | 团队档案 + 进行中任务 + 待裁决争议 + 成员能力摘要（证据式）+ 管理手册 | 成员私聊原文、人类隐私偏好细节 |
| 助理 Agent | 人类主管的偏好/红线/日程/待办 + 跨团队待协调项 + 管理手册 | 技术细节全文（按需检索） |
| 成员 Agent | 本人任务上下文 + 该任务需要的档案片段（按需）+ 项目约束 | 其它团队档案、成员评价、争议对方立场 |

**不要给所有 Agent 同一份记忆视图**。这既是 token 经济，也是权限模型：**视图即权限**，比"读到再靠提示词约束别说"可靠得多（后者对提示注入无抵抗力）。

### 2.6 跨团队辩论：交换"决策包"，不交换档案

辩论的记忆风险是**污染**：一方把自己的推断写进公共记忆，另一方读到后当事实。建议：

- 辩论只交换**决策包**（claim / evidence（消息 id、文件路径、命令输出）/ 立场 / 请求裁决点），不共享整份档案；
- 裁决结果写一条 dispute 档案（双时间 + 双方立场原文 + 裁决 + 遗留风险 + 后续观察点），**双方立场不可被覆盖**，只能追加"已裁决"状态；
- 辩论期间**禁止互相写对方档案**；写入权只在主管/助理/人类。这样"记忆"永远是裁决的产物，而不是辩论的武器。

## 3. 成员 Agent：session 记忆 + 选择性档案（c）

### 3.1 DSH 式 session 记忆的真实形态（本地可核查）

从本机 DSH 包的 README（附录 A）可确认它不是"聊天历史数组"，而是：

- **append-only 事件日志 + 投影**：会话是持久事件日志（JSONL 后端），UI/模型看到的是投影；**压缩把较早历史替换为一条摘要消息、近期逐字保留**，被遮蔽内容**仍留在日志中**，因此回放能确定性重现同一份压缩后对话。
- **压缩的锁与标记**：`compaction/start` 在摘要让出控制权前追加、`compaction/end` 释放；每次失败恰好一次闭合尝试，闭合失败留下未匹配 start 作为**有意的 busy 信号**；摘要用稳定标记（`<compacted-summary>` 包裹）让任何消费方在持久化/克隆后仍能识别"这段是压缩出来的"。
- **阈值与预算**：默认触发 `floor(min(W×0.8, W−O−65536))`（W=窗口、O=输出上限）；逐字保留 `(W−O)` 的 **16%**；`compactionRetries=1`、`maxOverflowRetries=1`（溢出错误先压缩再重试一次）；工具输出修剪器可在阈值触发后先修剪，修剪够了就**省掉一次摘要模型调用**。
- **崩溃安全**：策略插件在**模型请求前、顶层工具产生外部副作用前、每步开始前**三个屏障 flush；检查点失败按**失败即阻止**（"持久写入成功前，模型适配器或工具正文不会运行"）；中断的工具调用以"未知结果"恢复，**不自动重试**。
- **工作区指令**：`AGENTS.md`/`CLAUDE.md` 从项目根到 cwd 由宽到窄加载，去重（复制来的 `CLAUDE.md` 不会重复注），字节预算 `maxBytes` 默认 65536，超预算**先丢宽泛文件、再截断最具体的**并给出可见告警；注入为带 source 的**普通 user/message**，因此可回放、可压缩、可恢复。

**对本项目的直接含义**：
1. session 是**不可变的审计根**，压缩只是投影——事件日志（L0）应独立于 L1 存在，L1 可随时重建。
2. 成员 Agent 的"记忆丢失"多数不是模型忘了，是**压缩丢标识**。结构化检查点（精确路径/命令/错误串/待办）比自由摘要稳。
3. **工具副作用前的持久化**对"Agent 会改文件/发消息"的团队框架是刚需：否则崩溃后重试会重复产生副作用（正是 NeoBot 在 append 档案上遇到的同一问题，只是换了层）。

### 3.2 写入边界：四道门槛

成员把信息写入档案前，必须**同时**满足（建议写进 target.md 的"记忆写入契约"）：

1. **可复用性**：未来任务会用到吗？（一次性上下文 → 不写）
2. **可验证性**：有证据吗？（消息 id / 文件路径 / 命令输出 / 验收记录；模型推断 → 不写，或标 `confidence=low` 且需复核）
3. **决策相关性**：会改变未来的派单/验收/沟通吗？
4. **归属明确**：属于哪个 `(entity, key)`？归属不清 → 不写（宁可留给 L2 候选池）。

### 3.3 "不写"清单（建议直接进 requirements）

- 完整对话记录、原始转录（那是 L0 的职责，不是档案）；
- 模型的自我叙述/推理过程（"我认为用户可能…"）；
- 临时调试输出、日志、可再生成的计算结果；
- 涉及第三方隐私的内容（他人私聊、未授权的个人信息）；
- 无法归因的推断与传闻（若必须保留，只能进 dispute 并标注"未证实"）。

### 3.4 候选记忆的格式与额度

成员写档案应走"**候选**"而不是直接写（示意 JSON）：

    { "scope": "member|team|project|task|decision|dispute",
      "key": "<entity_id>",
      "claim": "一句话事实/结论",
      "evidence": [{"kind": "message|file|command|verdict", "ref": "..."}],
      "confidence": "high|medium|low",
      "valid_from": "ISO8601", "supersedes": ["mem_id"], "ttl_hint": "30d|never" }

额度建议：**每任务 ≤ 5 条候选、每条 ≤ 200 字、至少 1 条 evidence**。没有额度，Agent 会把"我觉得"写满整个档案——这是记忆系统退化的第一因。

### 3.5 晋升路径：propose → review → merge（谁裁决是待决策问题）

- 成员：写自己的 `member_notes`（低风险、私有、可随意）+ 提交候选记忆；
- 主管/助理：在**任务关闭**时审核合并（去重、补证据、必要时升级为 decision）；
- 人类拍板/红线类：**助理直接写**（高权威，不需审核）；
- 所有晋升留一条 audit（谁、何时、依据、合并到哪条）。

**为什么这样切**：把"写组织资产"的权力收在管理层，就得到一个天然的**串行收敛点**——去重、冲突裁决、权限过滤都在同一处发生，不需要分布式共识。代价是管理层 Agent 成为瓶颈（可用批处理 + 规则化合并缓解）。

### 3.6 去重与冲突：三条路线，按实体类型选

| 路线 | 代表 | 机制 | 优点 | 代价 | 适用 |
|---|---|---|---|---|---|
| ADD-only | mem0 v3 | 抽取只增不改，冲突在检索期用多信号排序 + 时间解决 | 省 token/低延迟、不丢历史 | 档案膨胀、靠检索兜 | 闲聊事实、观察记录 |
| 失效而非删除（双时间） | Zep/Graphiti | 新事实与语义相关旧事实比对，矛盾则把旧值置失效区间，保留四时间戳 | 可审计、能做时间推理 | 需要"边"模型与 LLM 比对成本 | 决策、成员能力、争议（**建议采用**） |
| upsert + 版本号 | 传统 | 覆盖 + version 乐观锁 | 简单 | 丢历史、无法回答"当时为什么" | 任务状态、进度、名单 |

**建议**：同一系统内**混合使用**，按实体类型选路线（上表最后一列）。最低要求：`(entity, key)` + version 乐观锁（NeoBot 的 `patch_archive` 已证明可行），并对"决策/能力"强制保留旧值有效期，不物理删除。

### 3.7 隐私与权限

- **可见性四级**：`agent-private`（成员自己的 session/notes）/ `team`（团队档案）/ `org`（跨团队决策包、共享约定）/ `human-only`（人类主管的偏好、评价）。
- **跨团队共享只给决策包与结论**，不给过程与原始消息；
- **读取留痕**（谁读了哪条档案，用于事后解释"它为什么这么判断"）；
- **人类可读、可导出、可删除**（本地优先框架的信任基础）；删除时保留"已删除"墓碑，避免快照/缓存复活；
- **敏感字段 redaction**（密钥、身份证号等）在写入前过滤，而不是注入前。

### 3.8 成本控制

写入不是免费：每次抽取/总结都是一次模型调用。建议继承 NeoBot 的三层预算思想：**条数额度 + 字数上限 + 证据要求**，配合"事件触发 + 批处理 + 失败冷却"，避免"记忆洪水"把成本推高一个数量级。另：**失败不重放**——append 型写入重试会产生重复事实（NeoBot 的"部分成功"就是为此）。

## 4. 横向对比与建议的检索/注入策略（d）

### 4.1 对比表

| 方案 | 核心机制 | 得 | 失 | 对本项目 |
|---|---|---|---|---|
| **MemGPT / Letta** | OS 分层隐喻：主上下文 / 可检索历史 / archival，靠工具调用"换页"；新版本演进为 **MemFS**（git 版本化的记忆文件系统）：根文件**每轮进 system prompt**，子目录靠 `MEMORY.md` 索引**按需读**；`/remember` 显式写入；**dreaming** 后台 subagent 在"完成 N 步或上下文压缩时"整理记忆，可要求 Agent 二次复核再应用；`/doctor` 审计放置/重复/系统提示词 token；**shared memory repo** 给多 Agent 共享团队约定 | 自我管理灵活；**git 版本 = 天然可回滚/可审计**；按需读目录 = 上下文极省；共享仓库正好对应"团队共享记忆" | 依赖 Agent 自律（不写就没了）；无强 schema；检索弱（默认无向量索引，靠文件搜索）；token 成本随根目录膨胀 | **MemFS 结构 + dreaming + /doctor 三者建议直接借鉴**：L3 可用"Markdown 文件 + 索引 + 版本"实现，而不是一上来搞图数据库 |
| **Generative Agents** | memory stream 全量追加自然语言记忆；检索 = 相关性（embedding）+ 重要性（LLM 打 1–10）+ 新近性（**每小时指数衰减 0.995**）；**反思**：近期事件重要性之和 > **150** 时生成高阶问题并回答，反思本身也存回 stream | 纯 append，写入无冲突压力；打分可解释、可调；反思阈值是廉价且有效的"该总结了"信号 | 全量增长无上限；重要性打分是额外调用；无冲突消解、provenance 不外显 | **重要性阈值值得借**：把"该不该记"变成可调分数而非拍脑袋规则；但必须补容量治理与失效 |
| **mem0** | 抽取 + 合并；v2 支持 ADD/UPDATE/DELETE/NOOP；**v3 改为单遍 ADD-only**（不覆盖不删除，冲突交给检索期多信号排序 + 内置图记忆）；论文报 LOCOMO 上比 OpenAI 记忆高 26%（LLM-as-judge）、p95 延迟 -91%、token -90%，图记忆再 +2% | 成本/延迟极优；"agent 自己说过的话"也是一等记忆（确认类事实可召回） | 只增会让档案单调膨胀；"当时的事实"与"现在的事实"要靠检索区分 | 适合**成员观察类**记忆；不适合需要"当前唯一定论"的决策档案 |
| **Zep / Graphiti** | 时序知识图：episode（摄入事件）→ 实体/边，**双时间**（事件时间 T 与摄入时间 T′，四时间戳）；新事实与语义相关旧事实比对，矛盾则**失效旧边而非删除**；检索三路（cosine / BM25 / BFS 邻域）+ 重排（RRF、MMR、episode-mentions、节点距离、cross-encoder）；DMR 94.8% vs MemGPT 93.4%，LongMemEval 最高 +18.5% 且延迟 -90% | 时间推理与**可追溯性最强**（每条事实可回溯到 episode）；"失效非删除"完美匹配决策审计 | 工程重（需图库）；抽取成本与幻觉；三元组对"团队/任务"需定制 ontology | **取思想不取实现**：用关系表 + 有效时间区间实现"失效非删除"，用 provenance 字段实现 episode 追溯，暂不引入图数据库 |
| **LangMem** | 记忆类型三分：语义（事实）/ 情节（经历）/ 程序性（行为规则）；语义又分 **collection（无界、需合并/失效）** 与 **profile（单文档、覆盖式）**；写入分 **hot path（对话中，立即可用但加延迟）** 与 **background（对话后，召回高但延迟）**；prompt optimizer 把"行为规则"当可训练记忆 | 概念分类最清晰，可直接当档案 schema 骨架；hot/background 取舍讲得最透 | 依赖 LangGraph；偏库而非产品 | **hot path 写候选、background 做合并**——正是 3.5 的建议；profile vs collection 直接对应"定长摘要 vs 无界档案" |
| **DSH / Claude Code 谱系** | session 事件日志 + 压缩检查点 + `AGENTS.md` 层级指令（预算内、由宽到窄、去重、注入为可回放消息）；工具结果修剪；崩溃安全检查点；会话检索独立 | 工作上下文管理最实用；可回放、崩溃安全、成本可控 | **没有跨会话的实体化长期记忆**——这正是 L3 的职责 | 成员 Agent 的 L1 就用它；L3 是我们相对这一谱系的增量 |

### 4.2 五条反复出现的取舍轴

1. **写期消解 vs 读期消解**：写时合并（NeoBot/mem0 v2/LangMem）→ 档案干净但要额外 LLM 调用且有并发冲突；读时排序（mem0 v3/Generative Agents）→ 便宜但档案膨胀、依赖检索质量。**建议：写期做"轻消解"（同 (entity,key) 内合并 + 版本），读期做"重排序"（时间衰减 + 权威度）。**
2. **结构化 vs 文件**：结构化表（NeoBot/Zep）可查询可治理；文件（Letta MemFS）可读、可 diff、可回滚。**建议：结构化存事实，Markdown 存叙事（团队/项目摘要），二者用同一 entity key 关联。**
3. **append vs 覆盖**：append 不丢历史但不可幂等；覆盖简单但丢"当时为什么"。**建议：append 事件 + 覆盖式"当前视图"，视图可随时从事重构。**
4. **自我管理 vs 系统托管**：Agent 自己决定写什么（Letta/自适应提示词）灵活但不可保证；系统确定性抽取（NeoBot 触发式记忆）保证覆盖但笨。**建议：分层——L4 自我管理 + L2/L3 系统托管 + 管理层审核。**
5. **常驻注入 vs 按需检索**：常驻稳定（缓存友好、必然可见）但占预算；按需省 token 但依赖 Agent 会去查。**建议：只把"手册 + 当前任务"常驻，其余按需；并在系统提示词里显式给出取数路径（NeoBot 的 hint 块做法）。**

### 4.3 建议的分层记忆模型

| 层 | 名称 | 载体 | 写入者 | 读者 | 预算 | 生命周期 |
|---|---|---|---|---|---|---|
| L0 | 事件日志 | 消息/事件全量落库（不可变、可回放） | 平台自动 | 所有人（受权限） | 无上限（分页） | 永久（可归档） |
| L1 | 工作上下文 | 会话投影 + 压缩检查点 | 运行时自动 | 单个 Agent | 窗口 80% 阈值 / 保留尾窗 16% | 会话级 |
| L2 | 候选记忆 | 事件触发的抽取管道输出（待审） | 成员/运行时 | 管理层 | 每任务 ≤5 条 | 天级（复核或过期） |
| L3 | 档案 | 八类实体表（结构化）+ 叙事摘要（Markdown） | 管理层（晋升）+ 人类 | 按视图授权 | 渲染上限 vs 存储上限分离 | 长期（双时间 + 快照） |
| L4 | 管理手册 | 分章节文本（≤1500 字） | 主管/助理自助 + 人类可改 | 自己 | 常驻 system 末尾 | 长期（带版本） |
| L5 | 检索与注入 | 查询路由 + 预算分配 + 降级 | 运行时 | — | 见 4.4 | 每次调用 |

### 4.4 检索与注入策略（只写策略，不写实现）

**检索三步**：
1. **结构化优先**：按 `(entity, key)` 精确取"当前视图"（任务状态、成员能力、团队章程）——绝大多数问题不需要语义检索。
2. **全文兜底**：本地优先用 SQLite FTS5 做关键词/实体名/路径检索（Zep 的 BM25 一路证明其价值；NeoBot 的 `list_archive` 也先给关键词预览）。
3. **语义可选**：仅当配置了 embedding 时启用向量召回，且**必须与全文结果融合重排**，不要单独用向量。
4. **重排打分（建议公示公式）**：`score = w1·相关性 + w2·权威度(层级/来源) + w3·新近性(指数衰减) + w4·证据强度`，并对"红线/决策"给硬优先级（不参与衰减、永不被挤出预算）。

**注入预算（默认值建议，配置可调）**：

| 分区 | 占比 | 内容 | 超预算时 |
|---|---|---|---|
| 系统/人设/手册 | 5–8% | L4 + 红线 | 手册必须完整，宁可砍其它 |
| 当前任务 | 35–45% | 任务目标、验收标准、上下文、产出要求 | 保留验收标准与目标 |
| 相关档案 | 25–30% | 成员/团队/项目/决策片段 | 先丢最旧、最低权威 |
| 近期会话 | 20% | L1 尾窗 | 按时间截断 |

**降级链**：检索失败 → 只用 L4 + 当前任务（保证能干活）；档案超限 → 只注入"标题 + 更新时间 + 取数提示"；上下文不足 → 先压缩 L1，再缩减档案预算，最后才砍任务说明（任务说明是最后防线）。

**可解释性**：每条注入内容带**来源标签**（表/key/时间/证据 id），这样"Agent 为什么这么做"可事后复盘——既是调试手段，也是用户信任的来源（Zep 的 episode provenance 与 Letta 的 /doctor 是两种实现路径）。

### 4.5 治理清单（建议原样进 target.md）

1. 每个 `(entity, key)` 一个**单飞锁**（防并发写/压缩打架）；
2. 失败**指数退避 + 冷却**，冷却失败后允许下次重试；
3. **部分成功**单独记账（append 语义不重试）；
4. 压缩失败**恢复原文**，不静默留半成品；
5. 压缩前**快照**（每 key N 份 + 全表上限）；
6. **内部/元数据表豁免**容量治理；
7. **渲染上限 ≠ 存储上限**；
8. 列表/预览**分页**，全文按需读；
9. 超限**可枚举**（`count_over_limit` 类接口）；
10. 用量**按子系统归集**（如 `agent:memory`）；
11. 关闭时**冲刷**未处理队列；
12. 权限开关（允许删除/允许写哪些表）+ 读取留痕。

- 一句原则：**"日志全量、档案精选、提示词极简"**。

### 5.2 `doc/0.0.1 最初版/requirements.md` 建议写（需求，不写实现）

- 人类主管与助理 Agent 对"人/团队/项目/任务/决策/争议"的**记忆需求清单**（每条给验收判据，如"能回答某决策当时的备选与理由"）；
- 成员 Agent 的**写入边界与额度**（3.2/3.3/3.4 的产品化表述）；
- **权限与可见性四级**（3.7）与"人类可导出/可删除"；
- **失败与降级的产品行为**（超限、压缩失败、检索失败时用户看到什么）；
- 明确**首版不做**：图数据库、跨设备同步、自动性格画像、基于非任务数据的成员评价、自动遗忘策略（先只做 TTL 提示与人工删除）。

### 5.3 首版建议明确"不做"（避免过度设计）

- 不做通用语义记忆层（先结构化 + FTS；向量作为可选插件）；
- 不做自动图抽取（用关系表模拟"实体-关系"）；
- 不做多 Agent 共享记忆仓库的实时同步（Letta 的 shared memory 是云侧能力，本地优先用"文件 + 显式同步"更稳）；
- 不做"记忆市场/记忆交换协议"。

## 6. 仍需决策的问题

1. **写入权归谁**：成员提交候选后，由主管 Agent **自动**合并，还是必须人类主管**确认**？（自动 → 吞吐高但污染风险；确认 → 干净但人类成瓶颈。折中：低风险实体自动、决策/争议类需确认。）
2. **L4 管理手册由谁维护**：Agent 自主改写（Letta 风格、越用越懂）还是只允许"Agent 提议 + 人类批准"？这决定它是"能力"还是"风险源"。
3. **是否需要双时间与失效语义**：决策/能力档案是否强制 valid_from/valid_until + supersedes（可审计但实现与 UI 成本上升），还是首版先用 upsert + 快照（简单但难回答"当时为什么"）。
4. **检索技术选型**：SQLite FTS5 + 结构化是否足够，还是首版就要向量/图？（本地优先下，向量索引带来 embedding 模型分发与更新成本。）
