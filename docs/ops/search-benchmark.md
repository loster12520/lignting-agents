# 检索基准（10 万消息，AC-06/NFR-PERF-03）

## 环境与方法

- 命令：`go test -tags=perf ./tests/bench -run TestSearchPerf100k -v -timeout 60m`
- 环境：WSL2（Linux 6.18.33.2-microsoft-standard-WSL2）/ Intel i7-14700F（28 线程）/ 15GB RAM /
  Go 1.27.4 / modernc.org/sqlite（纯 Go，无 CGO）/ 本地 ext4 磁盘。
- 种子：`tests/bench/seed.go` 批量写入 100,000 条消息（中文/英文/代码标识符混合，4 部门 × 20 会话），
  与生产同一 `search.Indexer` 在写入事务内同步倒排；为基准速度省略事件/审计（索引/消息表与生产一致）。
- 查询：`internal/search.Search`（与 HTTP /api/search 同一函数），每 query 预热 3 次后计时 20 次，
  报告 p50/p95；阈值：中文 2 字 p95 ≤150ms，普通 ≤300ms；写入后 ≤100ms 可搜；Recall@10 ≥0.8。
- 重建：`search.Rebuild` 全量重建消息索引，校验文档数与重建后可搜。
- 热点定位：`BENCH_MESSAGES=<n>` 可缩小规模做增长曲线（发布基准必须用默认 10 万）。

## 已知限制

- 种子省略 audit_log/events 写入；生产写入还包括审计哈希链与 SSE 事件（单条消息额外 ~0.5–1ms）。
- 仅覆盖消息检索；任务/决策/产出物检索需后续索引更多 doc kind。
- SQLite 为本地文件，基准受磁盘影响；CI 机器与开发机数值可能不同。
- 「过滤作者」p95 137ms 已接近 150ms 阈值：当前按 `messages.sender_id` 走 EXISTS 子查询，
  数据再增长会超；v0.0.2 按 P1 清单给 `search_docs` 补作者列后可直接列过滤（见 p1-backlog）。
- 10 万消息库 313MB 偏大（倒排词条 3 个 B 树 + 正文），属正常量级；如成问题可考虑压缩/分区。

## 历史问题（已修复，2026-11-18）

上一轮本基准跑 >20 分钟不结束，不是数据库/磁盘慢，而是写入路径的 O(N²)：

- `search.indexDocTx` / `DeleteTx` 用 `DELETE FROM search_terms WHERE doc_id=?` 清旧词条，
  而 `search_terms` 只有 `(term, doc_id)` 主键 + `term` 索引，没有 `doc_id` 索引 →
  SQLite 只能 `SCAN search_terms` 全表扫，每写 1 条消息扫一遍全表。
- 实测曲线：1 万条 seed 50s、2 万条 186s（翻倍变 3.7 倍），按此外推 10 万条约 80 分钟。
- 修复：迁移 v3 增加 `idx_search_terms_doc`；10 万条 seed 从 ~80 分钟降到 24s。
- 同时修掉基准自身的两个假通过：基准库现在注入生产同款 indexer（此前「写入后能搜到」没走生产路径），
  过滤会话用例改为选真实含目标词的会话并断言至少 1 条命中。
