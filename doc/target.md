## 0. 一句话

**让每个人在自己的电脑上，拥有一支会记忆、会协作、会争论、可管理、可审计的 AI 组织。**

Lignting Agents 是一个本地优先的协作式 Agent 框架。人类以「项目主管」身份进入对话平台，系统自动分配一名助理 Agent；人与助理共同商定目标，按需组建产品、研发、测试等多个部门；每个部门由自己的部门主管 Agent 运营，部门主管管理本部门员工，跨部门由主管对接、助理协调；所有对话、任务、产出、决策与记忆都留在本地，可检索、可追溯、可干预。

它不是「更聪明的聊天机器人」，而是**把一支虚拟组织运行起来的工作环境**。

## 1. 为什么做

### 1.1 单 Agent 的三堵墙

今天的编码 Agent、研究 Agent、办公 Agent 已经能独立完成不少任务，但一旦进入真实工作，很快撞上三堵墙：

1. **上下文墙**：一个会话装不下一个项目的全部背景。人需要反复解释「我们为什么这么设计」「上次那个坑别再踩」。
2. **角色墙**：一个 Agent 同时扮演产品、开发、测试、评审，等于让一个人既写需求又写代码又给自己打分。它缺少真正的视角冲突与质量闸门。
3. **信任墙**：Agent 做得越多，人越难检查。没有任务边界、产出物版本、评审记录与决策依据，所谓「自动化」最后变成「黑箱赌博」。

### 1.2 现有工具的断点

| 现有形态 | 它解决了什么 | 它缺什么 |
|---|---|---|
| 聊天机器人（ChatGPT、Claude、NeoBot 等） | 单轮/多轮问答、人格与记忆 | 没有组织、任务、产出物与长期协作 |
| 单机编码 Agent（Claude Code、Codex 等） | 在一个仓库里读代码、改代码、跑测试 | 单人单会话，缺少部门分工、评审与跨部门协作 |
| 多 Agent 框架（LangGraph、CrewAI、AutoGen 等） | 用代码编排多个角色 | 是「库」而不是「工作场所」；缺少持久消息、任务板、记忆治理与人机界面 |
| 团队聊天工具（Slack、Mattermost、飞书等） | 人与人的沟通与检索 | Agent 只是被 @ 的机器人，不是有职责、有记忆、有产出责任的成员 |
| 项目管理工具（Jira、Linear 等） | 任务与流程 | 不承载 Agent 的推理、上下文与记忆 |

**断点在于**：沟通、任务、产出、决策、记忆被拆在五个工具里，Agent 只能在其中一个格子里工作。人则被迫做「人肉总线」，不断复制粘贴、转述、核对。

### 1.3 我们的判断

- **协作的最小单元不是一次对话，而是一个有角色、有任务、有产出、有记忆的组织。**
- **组织的生产力不只来自模型能力，更来自信息结构**：谁该看到什么、任务如何验收、分歧如何收敛、经验如何沉淀。
- **本地优先不是情怀，而是这类产品的前提**：代码、需求、决策、客户信息都在本机；用户需要随时能打开、能搜索、能导出、能拔网线。
- **人类不应该被 Agent 包围，而应该被 Agent 保护**：助理的核心职责之一是替人过滤噪音、聚合信息、只在真正需要判断时打扰人。

## 2. 产品定义

### 2.1 它是什么

Lignting Agents 由两个核心模块和一组支撑能力组成：

1. **对话平台（Conversation Platform，Go）**：部署在用户本地，提供人类与 Agent、Agent 与 Agent 之间的沟通界面；所有消息、任务事件、评审意见、决策记录都持久化在平台本地服务；提供高效的消息检索服务。
2. **Agent 核心框架（Agent Core，Go）**：定义 Agent 如何接收消息、装配上下文、调用模型与工具、维护会话记忆、执行任务、参与评审与辩论；提供部门编排、任务调度、权限与预算控制。

支撑能力包括：记忆服务、产出物与工作区、DeepSeek 客户端、5 个工具与沙箱、检索索引、可观测性与审计、备份与导出。

### 2.2 它不是什么

- **不是一个通用聊天机器人**。对话是工作界面，不是产品目的。
- **不是一个「全自动公司」**。人类保留目标设定、关键审批、预算与终止权。
- **不是一个模型**。它接入模型，但不训练模型；v0.0.1 只接 DeepSeek，默认 deepseek-flash。
- **不是一个 IDE**。它可以调用编辑器/终端/代码工具，但核心是组织协作与工作流，不是代码编辑体验。
- **不是 Slack 的克隆**。频道与消息只是表层；真正的差异在任务、评审、辩论、记忆与 Agent 治理。
- **不是多 Agent 演示框架**。它必须以「每天能用、敢用、可恢复」为标准。

### 2.3 目标用户

| 用户 | 典型场景 | 最在意什么 |
|---|---|---|
| 技术型独立开发者 / 小项目组 Tech Lead | 一个人带一个项目，需要产品、开发、测试的虚拟分工 | 交付速度、代码质量、不重复解释背景 |
| 研究者 / 写作者 / 咨询顾问 | 多角色协作完成报告、方案、调研 | 资料检索、观点碰撞、版本与引用 |
| 个人知识工作者 | 长期项目、日常运营、个人助理 | 记忆连续性、低打扰、本地数据 |

**最初版聚焦**：技术型独立开发者/小项目组 Tech Lead，以软件交付为主场景；其他场景作为通用协作能力的外溢，不为其做专门优化。

### 2.4 核心价值主张

1. **一个组织，而不是一个聊天框**：部门、角色、任务、评审、辩论、决策都在同一个工作空间里发生。
2. **越用越懂你**：四层记忆让助理与部门主管记得目标、偏好、决策、教训；员工 Agent 只沉淀重要事实，避免上下文膨胀。
3. **质量来自结构性冲突**：产品挑战需求、测试挑战实现、其他部门挑战接口；争论有格式、有轮次、有证据、有裁决。
4. **数据与权力都在你手里**：本地存储、单二进制、可导出、可审计；Agent 的工具权限、预算、记忆写入都可管。

## 3. 设计原则

以下原则用于裁决后续所有产品与技术取舍。原则冲突时，优先级从上到下。

### 3.1 人类主权（Human Sovereignty）

人设定目标、批准项目章程与预算、处理升级决策、拥有最终否决权。Agent 可以建议、执行、争论，但不能替人做不可逆的重大决定。

**这意味着**：关键操作有审批；Agent 不能修改自己的权限；部门不能自行扩编；高风险的删除/发布/支付必须 human-in-the-loop。

**反例**：让助理 Agent 自动创建十个部门并自动批准所有工具调用，只在日报里告诉人。

### 3.2 本地优先（Local-first）

默认单机运行，数据本地存储；除模型调用与用户显式启用的外部工具外，不依赖云服务；断网时仍可浏览、搜索、编辑、导出。

**这意味着**：单二进制/少依赖、SQLite/文件存储、内嵌 Web UI、可离线检索、备份简单。

**取舍**：初期不做多端实时同步、不做云端多租户；v0.0.1 只承诺单用户本地体验。

### 3.3 工作可见（Visible Work）

Agent 的每一步——收到什么、读到什么、调用了什么工具、写了什么记忆、做了什么决定——都应可查看、可回放、可追责。

**这意味着**：消息、任务事件、工具调用摘要、评审意见、决策记录全部持久化；界面提供「为什么这么答」的上下文视图；不把关键逻辑藏在黑箱里。

### 3.4 证据优先于口才（Evidence over Assertion）

Agent 的结论必须尽量链接到证据：需求条目、代码行、测试结果、消息、文档、历史决策。评审与辩论中，「我觉得」不如「这是失败用例/这是接口契约/这是成本数据」。

**这意味着**：产出物与消息支持引用；评审 finding 必须带位置与理由；辩论必须带证据；决策记录保留依据。

### 3.5 记忆是产品表面（Memory as a Surface）

记忆不是藏在提示词里的神秘上下文，而是用户能看见、能搜索、能修改、能删除、能导出的数据。

**这意味着**：记忆检查器、来源链接、待确认记忆、版本与快照、敏感信息过滤、按部门/项目隔离。

### 3.6 结构优于闲聊（Structure beats Chatter）

Agent 之间的协作不能靠无限对话。任务、评审、辩论、决策都应有结构化载体；聊天用于澄清与建立关系，不用于承载所有状态。

**这意味着**：任务板、产出物版本、评审单、辩论轮次、决策记录是 first-class objects；消息只是它们的传播层。

### 3.7 小核心，可插拔边缘（Small Core, Composable Edges）

核心协议保持稳定：消息、任务、产出物、评审、决策、记忆、Agent 生命周期。模型、工具、运行时、界面、存储后端尽量可替换。

**这意味着**：模型客户端、工具注册表、可扩展边界；v0.0.1 只接 DeepSeek 与 5 个工具，不把复杂度提前引入。

### 3.8 优雅降级（Graceful Degradation）

模型超时、工具失败、网络断开、进程崩溃时，系统不能丢数据、不能卡死、不能假装一切正常。

**这意味着**：消息先落库再投递；Agent 每步 checkpoint；失败可重试/可回滚；离线可读；错误对人可见且有恢复路径。

### 3.9 成本是一等约束（Cost is a Constraint）

Agent 部门很容易烧钱。预算、上下文、并发、重试都要有上限；便宜模型用于记忆整理、摘要、初筛，贵模型用于关键推理。

**这意味着**：按部门/任务/日预算；token 与费用仪表盘；超预算暂停而非静默继续；上下文压缩与工具输出裁剪。

### 3.10 无聊的可靠性（Boring Reliability）

这类产品每天都在用。崩溃恢复、幂等、迁移、备份、日志、测试比「多一个炫酷 Agent」重要。

**这意味着**：事件溯源、事务性 outbox、幂等键、数据库迁移、端到端测试、故障演练。

## 4. 最终形态：一个下午的使用叙事

> 这一节不是需求，而是用来对齐「产品最终应该是什么感觉」。

**09:00　安装与第一次见面。**
用户下载一个可执行文件，运行 `lignting`，浏览器打开 `http://127.0.0.1:<端口>`。首次向导只问四件事：工作目录、模型供应商与密钥、预算上限、希望怎么被称呼。完成后，一个助理 Agent 出现在私聊里，自我介绍，并说明三件事：我能帮你做什么、我不会做什么、你可以随时暂停我。

**09:10　把想法讲清楚。**
用户说：「我想在两周内把现在这个 CLI 工具做成一个有 Web 界面的产品，先做最小可用版。」助理不急着写代码，而是用几个问题澄清：目标用户、必须有的三个功能、不能接受的取舍、预算、上线时间。它把答案整理成一页「项目意图卡」，请用户确认。

**09:30　组建部门。**
助理提出项目蓝图与部门蓝图：产品部门（1 主管 + 1 产品员工）、研发部门（1 主管 + 前端页面/接口对接/数据流 3 名员工）、测试部门（1 主管 + 1 测试员工）；说明各部门职责、接口、群聊、评审关系、预算与第一周里程碑。用户删掉一个员工、把测试改成兼职，批准。系统创建项目群聊、部门群聊、任务板、产出物空间与记忆命名空间；各部门主管做部门 kickoff，助理做项目 kickoff。

**10:00　第一轮交付。**
研发部门主管把「用户登录 + 项目列表」拆成任务，并在每个任务上写明分工视角：A 负责页面、B 负责接口对接、C 负责数据流。三人先在部门群里确认各自视角与计划；A 和 B 对接口字段有分歧，按部门内讨论规则各自陈述「怎样更方便自己开发」，主管拍板接口契约后进入实现。产品写 PRD、测试写用例；用户可以在任务板看进度，也可以点开任意群聊围观。

**14:00　一次真正的争论。**
后端部门提出把接口改成 GraphQL；前端部门认为这会拖慢首版。两位部门主管在跨部门评审群聊提交结构化立场：现状、提案、影响、证据、替代方案。双方各最多 5 条、总计最多 15 条；仍未一致。助理没有和稀泥，而是整理出一页决策简报：两个方案的交付时间、风险、可逆性、成本，附双方最强论据，反馈给用户。用户选择 REST，并记录「首版后重新评估」。决策记录自动链接到相关任务与产出物。

**16:00　返工与验收。**
测试部门发现一个边界条件失败，提交 blocker 级 finding。研发部门修复，测试复跑，研发部门主管核对验收标准，标记任务完成。产品把这次踩坑写成一条部门记忆：「导入大文件时必须流式处理，否则内存峰值不可接受」。这条记忆不是聊天记录，而是一条带来源链接的档案，之后相关任务会自动注入。

**一周后　记忆与检索开始复利。**
用户问助理：「上次为什么没上 GraphQL？」助理在几秒内找到决策记录、辩论原文与相关任务，而不是重新猜。用户搜索「登录 限流」，能按部门、群聊、时间、消息类型过滤，直接跳到当时的讨论与代码变更。用户打开记忆检查器，发现一条过时的偏好，改掉；助理在下一轮对话中立刻使用新版本。

**一个月后　组织在长大。**
用户新建第二个项目做移动端，复用部门模板、接口约定与项目记忆，但不会把上一个项目的私有争论带过去。新项目的部门通过跨部门评审与共享决策记录协作。用户可以随时暂停某个部门、降低预算、查看每个 Agent 的最近行为，或导出全部数据。

这就是 Lignting Agents 的终局：**不是让 AI 替代人，而是让人拥有一个可管理、可解释、会成长的 AI 组织。**

## 5. 系统全景

### 5.1 两个核心模块与外部依赖

Lignting Agents 只有两个核心模块：**对话平台**与 **Agent 核心框架**。DeepSeek API 与本地工作区是外部依赖，不作为「第三个模块」。

    项目主管
       │
       ▼
    本地 Web 工作台 ──HTTP/SSE──> 对话平台（Go）
                                    │ 消息 / 群聊 / 部门 / Agent 管理
                                    │ 事件流 / 检索 / 通知 / 审计
                                    ▼
                              Agent 核心框架（Go）
                                    │ 部门与员工编排 / 任务 / 评审 / 辩论
                                    │ 上下文装配 / 压缩 / 四层记忆
                                    │ 共享写工具 / 变更时间线
                                    ▼
                         DeepSeek API（deepseek-flash / web search）
                         本地工作区（读文件 / 写文件 / Bash / Git）

### 5.2 模块职责边界

| 能力 | 对话平台 | Agent 核心框架 |
|---|---|---|
| 人类登录与本地身份 | **拥有** | 消费 |
| 私聊 / 群聊 / 部门频道 / 线程 | **拥有** | 消费 |
| 消息、事件、审计持久化 | **拥有（人类可见消息与审计的唯一事实源）** | 写「要进入对话的事件」与审计事件 |
| 消息/群聊检索 | **拥有** | 通过 API 使用 |
| 通知 / 未读 / 提及 / 用户观察者视图 | **拥有** | 触发 |
| Agent 创建/启动/暂停/停止/配置 | **拥有操作入口与状态投影** | **拥有执行与生命周期** |
| 部门 / 员工名册 / 角色卡 | 只存展示投影 | **拥有** |
| Agent 会话 / 上下文 / 压缩 | 不拥有 | **拥有** |
| 四层记忆 / 档案 | 只提供消息检索源 | **拥有** |
| 任务 / 产出物 / 评审 / 决策 | 只存读模型投影 | **拥有统一状态机** |
| 文件写入 / 变更时间线 | 不拥有 | **拥有共享写工具、串行化与时间线** |
| 模型调用 / 工具执行 | 不拥有 | **拥有**（DeepSeek API + 5 个工具） |
| 权限 / 预算 / 审批 | 身份与消息级权限 | **拥有策略引擎** |
| 审计 | **拥有唯一 append-only 审计流** | 提交审计事件 |
| 成本 / 用量 | 只读投影 | **拥有 per-call 账本** |
| 通信隔离 / 临时桥接 | **拥有会话路由与用户观察者权限** | 提供角色/部门关系 |

**关键边界**：

- **平台是消息与审计的唯一事实源**；**核心是 Agent 状态、任务状态、记忆、文件变更时间线的唯一事实源**。两者用消息/事件/对象 ID 关联，不互相复制权威状态。
- **任务/产出物/评审/决策采用「统一状态机」**：核心是唯一写入方，平台只存读模型投影；卡片动作调用核心 API。这是**状态记录**的单一权威，不等于文件写入的单一写者。
- **文件写入不使用单一写者**：所有 Agent 共用一套 WriteTool，以「写入事件」串行化；同一文件有未消费写入时，其他 Agent 不得写该文件；每次写入进入时间线。详见 5.6 与 8.11。
- **Agent 生命周期由核心执行**；平台提供启动/暂停/停止/配置的 UI 与 API，满足「所有 Agent 经由对话平台启动、对话和管理」。
- **通信默认隔离**：部门内自由沟通；跨部门由部门主管对接；部门主管与用户之间经助理转接。用户可在平台查看所有群聊消息（观察者），也可临时开通直连桥（有范围与到期）。
- **DeepSeek-only**：v0.0.1 只接 DeepSeek 官方 API，默认 deepseek-flash；不接其他模型供应商、不接 DSH/ACP/Node 运行时。
- **审计只有一个 append-only 流：平台**；核心提交审计事件，详细日志为二级证据。
- **上下文快照**：核心每 turn 记录 context.request（注入了什么、来源、token 估算、模型/超参、turn id）。

### 5.3 必须成立的不变量

1. **消息有全序**：每条消息/事件在 workspace 内有一个单调递增的 seq。排序、断线重放、幂等、审计都从它派生。
2. **先持久化，再投递**：消息写库与索引在同一事务边界内完成；提交成功后才通知订阅者。
3. **日志是事实，索引是派生**：检索索引可删除、可重建；重建后结果必须与源数据一致。
4. **投递至少一次，消费端幂等**：平台不承诺 exactly-once；Agent 用游标 + 幂等键获得「效果上恰好一次」。
5. **权限先于检索**：可见性过滤发生在查询/排序之前。
6. **会话日志不可变，压缩只改投影**：Agent 原始事件日志是审计根；压缩摘要不能删除历史。
7. **人类决策有记录**：不可逆动作、范围变更、质量豁免、预算调整必须产生决策记录。
8. **没有进程绕过平台写消息**：所有人类可见消息必须经过平台。
9. **统一状态 + 共享写工具**：任务/产出物/评审/决策由核心统一状态机管理；文件写入必须走共享 WriteTool，**默认全局串行**（一个写入事件未消费前，其他 Agent 不得写入），不允许静默覆盖。
10. **单一审计流**：平台持有唯一 append-only 审计流；核心只提交事件。
11. **每 turn 有上下文快照**：核心记录 context.request，否则「当时模型看到了什么」不可回放。
12. **用户观察者**：用户可查看所有群聊消息；通信隔离只限制 Agent 之间的默认路由，不限制用户的读取权。

### 5.4 数据流

**人类发消息 / 群聊：**

1. 浏览器发送消息/群聊消息（带幂等 ID）。
2. 平台分配 seq、写消息、索引、提及、事件；提交后 SSE 通知，并唤醒相关 Agent。
3. 核心按部门/角色/群成员路由；被路由的 Agent 拉取消息，装配上下文并记录 context.request。
4. 核心调用 DeepSeek API；需要工具时执行读/写/Bash/Web Search；写文件走共享 WriteTool。
5. 核心把回复、工具摘要、任务/评审/决策事件写回平台；平台更新投影、通知用户。
6. 群聊中多个 Agent 的发言由「发言队列 + @提及 + 轮次上限」控制，避免同时刷屏。

**部门工作：**

1. 部门主管把任务拆给员工，并在任务上写明每个人的**分工视角**（页面/接口/数据流等）。
2. 员工先提交自己的视角与计划；有冲突则进入部门内讨论；部门主管拍板全局取舍。
3. 执行完成后提交评审；测试/同部门评审给出 verdict；部门主管核对；需要时走跨部门/人类闸门。
4. 任务关闭触发记忆抽取；文件写入进入时间线。

### 5.5 部署形态

| 形态 | 组成 | 适用阶段 | 说明 |
|---|---|---|---|
| **本地单机（默认）** | **一个 Go 二进制**承载平台 + 核心（逻辑模块分离）+ 本地数据目录 | v0.0.1 | 仅绑定 127.0.0.1；浏览器即客户端；DeepSeek API 是唯一默认外联 |
| **本地多进程** | 平台与核心拆进程 | v0.1+（可选） | 崩溃隔离/资源限制；不是 v0.0.1 必需 |
| **覆盖网络** | 通过 SSH 端口转发 / Tailscale 等访问本机 | v0.1+ | 不自建公网 TLS；不把数据放到网络盘 |

**硬约束**：SQLite/WAL 数据目录不能放在 NAS、OneDrive 等网络/同步盘；平台默认仅本机可访问；v0.0.1 不引入 Node/DSH/ACP/外部 Agent 运行时。

### 5.6 原生 Go Agent 内核与最小工具

v0.0.1 **不使用 DSH、ACP 或任何外部执行后端**。Agent 核心是一个原生 Go agent loop：

    接收消息/任务 -> 路由 -> 装配上下文 -> 调 DeepSeek
    -> 解析工具调用 -> 执行工具 -> 回填结果 -> 循环
    -> 写回消息/任务 -> 触发记忆

**模型**：只接 DeepSeek 官方 API；所有角色默认 deepseek-flash。联网搜索使用 DeepSeek 的 deepseek_web_search 能力；文件输入/阅读链接等能力由 DeepSeek 服务端处理，**不增加本地工具**。v0.0.1 不做多供应商、不做模型路由抽象。

**工具（v0.0.1 只有这 5 个）**：

| 工具 | 作用 | 备注 |
|---|---|---|
| read_file | 读文件 | 路径限制在工作区；大文件分页/截断 |
| write_file | 写文件 | **共享写工具**；提交写入事件；默认全局串行；冲突检测；返回变更 ID |
| bash | 执行命令 | 工作区 cwd；超时/输出上限；危险命令审批 |
| web_search | 联网搜索 | DeepSeek 搜索能力；返回引用 |
| view_change_history | 查看文件变更时间线 | 最近 N 次（默认 30，可配置）；支持按文件/分支/提交查看 |

**共享写工具（WriteTool）**：

- 所有 Agent 共用；每次写入提交一个 write event（agent、path、base_hash、diff/content、reason、task、branch）。
- **默认全局串行**：任一写入事件未消费前，其他 Agent 的写入被拒绝/排队；后续可配置按文件并行；分支切换/提交/批量重构使用全局锁。
- 写入前校验 base_hash；文件已被改动则拒绝并提示重新读取/变基，绝不静默覆盖。
- 每次成功写入记录一条变更；**每个文件只保留最近 30 次**（配置项 write_timeline_limit），超出淘汰最旧。
- 监听 Git 分支切换/提交：提交时把自上次提交以来的多次改动合并为一个「commit 组」；分支切换后时间线标注 branch；已提交改动仍可在时间线查看（受保留上限）。
- 时间线模仿 VSCode Timeline：文件、时间、Agent、diff、任务、分支、commit、原因；view_change_history 可查。

**上下文**：核心自己装配/压缩；使用结构化检查点（目标、关键文件/路径、错误、待办、下一步）；每 turn 记录 context.request。没有第二层压缩，没有后端。

**为什么不用 DSH/ACP**：会引入 Node/子进程/协议/版本兼容/权限反向请求等复杂度，而 v0.0.1 只需要「读、写、Bash、搜索、看变更」五个工具。原生 Go 内核更小、更可控、可单二进制交付。若未来确实需要外部 Agent 运行时，再作为可选扩展，不影响 v0.0.1。

**风险**：DeepSeek API 的可用性/限流/价格是主要外部风险；核心要有重试、超时、预算与降级（只读/暂停），不能把 API 故障变成数据丢失。

### 5.7 技术方向（非最终选型）

- **语言**：平台与核心使用 Go；前端 TypeScript + 现代框架，go:embed 内嵌；v0.0.1 单二进制。
- **模型**：DeepSeek 官方 API；默认 deepseek-flash；不接其他供应商。
- **存储**：SQLite WAL + 文件存储；消息写入与索引同事务；索引可重建。
- **检索**：中文优先；短词索引（2 字）+ trigram/全文（≥3 字）+ 结构化过滤 + 时间衰减 + 会话聚合。
- **实时**：UI 用 SSE（Last-Event-ID 续传）；Agent 用游标长轮询。
- **投递**：at-least-once + 幂等键 + 每消费者游标。
- **文件写入**：共享 WriteTool + 默认全局串行 + 变更时间线（默认 30 条/文件）+ Git 分支/提交监听。
- **附件**：内容寻址 + MIME 白名单 + 权限校验。
- **密钥**：DeepSeek API Key 存 OS keychain 或本地安全存储；不入消息/日志/检索。
- **安全**：默认 loopback、Origin/Host、SameSite Cookie、Agent 独立 Token、工具白名单、审批门。
- **可移植**：Windows/macOS/Linux；平台本体尽量无 CGO；数据可备份/导出。

### 5.8 明确不采用的方案

- **不使用 DSH / ACP / Node 执行后端**：v0.0.1 原生 Go agent loop，避免外部运行时复杂度。
- **不做多模型供应商**：只接 DeepSeek；默认 deepseek-flash。
- **不做 MCP / 插件市场 / Agent 市场**：v0.0.1 只有 5 个内置工具。
- **不做 fork/多方案并行会话**：v0.0.1 用「新会话 + 交接包」替代。


## 6. 角色与组织

### 6.1 指挥链：用户 → 助理 → 部门主管 → 员工

Lignting 的组织单元是**部门（Department）**，不是「一个主管管整个项目」。每个部门有自己的**部门主管 Agent**，主管再管理本部门员工。

    项目主管（Owner）
          │ 目标、预算、最终裁决、不可逆审批
          ▼
    助理 Agent（Chief of Staff）
          │ 全局协调、组队、注意力过滤、跨部门/用户接口
          │ 可选：把全局产品/计划职责交给 PM 部门
          ▼
    部门主管 Agent（Department Lead）× N
          │ 本部门拆解、分派、部门内讨论、产出核对
          ▼
    部门员工 Agent（Employee）
          │ 页面 / 接口 / 数据流 / 测试 / 研究等具体分工

**全局职责归谁**：

- 默认由**助理 Agent**承担全局目标澄清、部门划分、跨部门协调、向用户汇报。
- 也可以设一个独立的 **PM 部门**（产品/项目管理），由 PM 部门主管承担全局产品判断、优先级、范围与验收口径；助理负责协调与对用户接口。
- **不再设「一个统管所有部门的主管 Agent」**。部门主管只对本部门负责；跨部门由部门主管之间对接，必要时助理主持、用户裁决。

### 6.2 角色卡

每个 Agent 的契约必须写清「我是谁、我站在什么角度、我能和谁说话」：

| 字段 | 说明 |
|---|---|
| id / name | 稳定标识与显示名 |
| kind | assistant / pm_lead / dept_lead / employee |
| department | 所属部门；助理不属于业务部门 |
| mission | 一句话使命 |
| perspective | **固定分工视角**：页面实现 / 接口对接 / 数据流 / 测试验证 / 架构约束等 |
| responsibilities / non_goals | 必须做 / 明确不做 |
| inputs / outputs | 需要的上下文与必须产出的产物 |
| tools / permissions | 5 个工具的白名单、路径/命令/网络范围 |
| communication_scope | 默认能跟谁说话：本部门 / 部门主管 / 助理；跨部门与对用户默认禁止 |
| decision_rights | 本部门内可决定什么、必须请示什么 |
| memory_scope | 可读/可写记忆命名空间与写入额度 |
| model_policy | 默认 deepseek-flash；预算与超时 |
| escalation | 何时升级给部门主管/助理/人类 |

### 6.3 职责与权限矩阵

| 事项 | 项目主管 | 助理 | 部门主管 | 员工 |
|---|---|---|---|---|
| 设定目标/优先级 | **A** | R | C | I |
| 批准项目章程/预算 | **A** | R（准备） | C | I |
| 创建/解散部门 | **A** | R | C | I |
| 增减部门员工/改角色 | **A** | R | R（提议） | I |
| 部门内任务拆解/分派 | C（可干预） | C | **A/R** | C |
| 跨部门任务协调 | C | **A/R** | R（对接） | I |
| 技术方案（本部门） | I | I | A | **R** |
| 质量门/验收 | **A**（G3 最终） | I | R（核对/部门内小任务） | R（测试质量判定） |
| 部门内讨论裁决 | I | I | **A** | C |
| 跨部门争议 | A（不可逆/高风险） | R（主持） | C | I |
| 组织级记忆写入 | A | **A/R** | R（提议） | R（候选） |
| 暂停/终止 Agent | **A** | R（可紧急暂停，通知人类） | R（本部门内） | I |
| 不可逆工具动作 | **A** | I | R（申请） | R（申请） |

A = 最终负责；R = 执行；C = 被咨询；I = 被通知。

### 6.4 助理 Agent：全局幕僚与用户接口

助理的职责：

1. **澄清**：把用户想法变成目标、范围、约束、验收、预算。
2. **划分部门**：决定需要哪些部门（产品/研发/测试/平台等）、每个部门要什么角色与员工。
3. **管理主管**：创建/暂停/调整部门主管；查看各部门状态、预算、风险；不直接越过主管指挥员工。
4. **跨部门协调**：部门主管之间的接口、争议、资源冲突，由助理主持；无法收敛时升级用户。
5. **用户接口**：部门主管不能直接找用户；所有对用户的汇报、审批、升级都经助理整理。
6. **注意力过滤**：聚合状态、只升级真正需要用户判断的事；维护决策收件箱。
7. **记忆策展**：维护用户偏好、项目决策、跨部门约定；审核员工候选记忆。
8. **单次问答**：不需要组队的问题直接回答。

助理的边界：不能代替用户批准预算/章程；不能修改自己权限；不能删除审计；不能绕过部门主管直接给员工派活（紧急情况除外，需留记录）；不能把「我觉得」写成用户偏好。

### 6.5 部门主管 Agent：本部门的操作系统

部门主管负责：

- 接收助理/PM 部门下达的目标与接口，拆成本部门任务。
- 给员工写明**分工视角**（页面/接口/数据流/测试等）与验收标准。
- 组织**部门内讨论**：员工从各自开发便利出发争论；主管负责全局取舍与拍板。
- 分派、跟踪、解阻、核对产出；控制本部门 WIP 与预算。
- 管理部门记忆；把任务关闭/返工/讨论结论沉淀为档案。
- 代表本部门与其他部门主管对接；不能直接找用户。
- 向助理汇报结构化状态。

部门主管的边界：不能改用户目标/项目预算/部门结构；不能批准自己的产出；不能绕过测试质量门；不能跨部门直接指挥别的部门员工；不能以部门利益为由伪造证据。

### 6.6 员工 Agent：带角度的专家

员工按分工承担具体工作：

| 分工示例 | 视角 | 关键产出 | 不能做什么 |
|---|---|---|---|
| 页面开发 | 页面结构/交互/样式实现的便利 | 页面代码、组件、样式 | 替接口/数据流做全局决策 |
| 接口对接 | 接口契约/联调/错误处理 | API 适配层、联调记录 | 擅自改后端契约 |
| 数据流 | 状态管理/数据一致性/性能 | 数据层、状态流、缓存 | 擅自改页面交互 |
| 测试 | 可验证性/边界/回归 | 用例、报告、缺陷 | 无证据放行 |
| 架构评审 | 接口/安全/可维护性 | 评审意见、约束 | 越权改业务实现 |

员工可以并且应该从「方便自己开发」的角度参与部门内讨论；但不能伪装成全局中立，也不能直接联系其他部门或用户。**部门内讨论的全局权衡由本部门主管拍板**；涉及项目级约束时主管可向 PM/助理索取约束，但不把裁决权交给员工；跨部门冲突升级助理/用户。

### 6.7 组织形态

| 形态 | 结构 | 适用 |
|---|---|---|
| **三部门交付（v0.0.1 默认）** | 助理 + 产品部门 + 研发部门 + 测试部门，每部门 1 主管 + 1–3 员工 | 单项目、小项目组 |
| **加平台部门** | 上述 + 平台/架构部门（主管 + 架构评审） | 有接口/安全/质量挑战 |
| **PM 部门制** | 助理 + PM 部门 + 交付部门；PM 部门管全局产品判断 | 需求复杂、需要独立产品线 |
| **项目制** | 按项目临时组部门，结束解散 | 咨询、研究、一次性交付 |

v0.0.1 默认「三部门交付」；验收可加平台部门制造跨部门挑战。

### 6.8 人类注意力预算

- 助理每天最多主动升级 3 次（默认，可配置）；其余进决策收件箱。
- 通知分级：FYI / 需要知道 / 需要决定 / 阻塞；只有后两级实时打扰。
- 决策包一页可读：争议点、选项、证据、推荐、不决策的后果。
- 支持批量审批、稍后处理、授权给助理/部门主管（有范围与到期）。
- 每日/每周简报：进展、风险、花费、待决事项；不转发原始聊天。
- 部门主管不能直接找用户；所有打扰经助理。

### 6.9 人类闸门

v0.0.1 默认三道人类闸门：

| 闸门 | 时机 | 人类确认什么 | 可否委托 |
|---|---|---|---|
| G1 项目蓝图 | 组部门前 | 目标、部门、角色、人数、预算、节奏、风险 | 否 |
| G2 技术方案/范围 | 高风险需求开工前 | 方案、接口、依赖、风险、范围变更 | 低风险可委托部门主管 |
| G3 最终验收 | 功能/里程碑/高风险交付前 | 验收核对表、证据、遗留风险、是否交付 | 否 |

外加不可逆动作审批（删除、force push、对外发布、付款、权限变更）。

**高风险分类表**：

| 维度 | 高风险条件 | 默认处理 |
|---|---|---|
| 数据 | 客户数据、密钥、隐私、生产数据 | G2 + 双钥匙 |
| 可逆性 | 不可回滚、force push、删除、对外发布、付款 | 人类审批 + 双钥匙 |
| 影响范围 | 跨部门接口、对外承诺、第三方系统、公开发布 | G2 + 平台部门评审 |
| 成本 | 单任务/单次动作超过人类阈值 | 人类审批 |
| 合规/伦理 | 法律、隐私、安全、歧视/误导风险 | 人类审批 |

低风险 = 未命中上表、可回滚、仅影响本部门工作区；可由部门主管在授权范围内决定，但必须留审计。


## 7. 部门组建

### 7.1 从目标到部门

    用户提出目标
      -> 助理/PM 部门澄清目标、范围、约束、预算、期限
      -> 提出「项目蓝图 + 部门蓝图」（哪些部门、各要什么角色/员工、接口、节奏、成本）
      -> 用户 G1 审批
      -> 系统 provisioning：部门、主管、员工、群聊、任务板、记忆空间
      -> 各部门 kickoff；助理做项目级 kickoff
      -> 运行、复盘、扩张/收缩/解散部门

### 7.2 助理/PM 的访谈维度

| 维度 | 要问什么 | 不问的后果 |
|---|---|---|
| 目标 | 交付什么？给谁？成功长什么样？ | 部门做错方向 |
| 范围 | 必须有 / 明确不做 / 以后再说 | 范围蔓延 |
| 约束 | 技术栈、合规、现有系统、期限 | 方案不可落地 |
| 质量 | 什么必须测试？什么可以接受技术债？ | 质量门缺失或过度 |
| 预算 | 模型/时间/人力上限；超支怎么办 | 成本失控 |
| 风险 | 最怕什么？哪些不可逆？ | 关键决策无人拍板 |
| 协作 | 用户想多深地参与？多久看一次？ | 打扰过多或失控 |
| 现有资产 | 仓库、文档、设计、历史决策 | 重复造轮子 |

### 7.3 项目蓝图与部门蓝图

项目蓝图包含：

- 项目目标、成功标准、范围、非目标、约束、预算、期限。
- 需要哪些部门（产品/研发/测试/平台/PM），每个部门的使命、接口、依赖。
- 部门之间的默认沟通规则、跨部门评审对象、升级路径。
- 工作节奏、质量门、人类闸门。

每个部门蓝图包含：

- 部门使命、职责边界、输入/输出。
- 部门主管角色卡；员工数量与分工视角（页面/接口/数据流/测试等）。
- 部门内讨论规则、裁决权、WIP、预算。
- 与其他部门的接口与对接人。
- 部门记忆范围与候选写入门槛。

### 7.4 审批与 Provisioning

用户批准项目蓝图（G1）后，系统执行 provisioning：

- [ ] 创建项目、项目群聊、部门记录、生命周期状态。
- [ ] 创建部门主管与员工，写入角色卡、视角、权限、模型（默认 deepseek-flash）、预算。
- [ ] 创建部门群聊、任务板、产出物空间、评审/决策视图。
- [ ] 创建记忆命名空间与初始档案（项目意图卡、约束、术语表、部门约定）。
- [ ] 建立部门间接口、跨部门群聊/评审关系、默认通信隔离。
- [ ] 设置审批门、预算、告警、暂停开关。
- [ ] 生成部门 kickoff 议程与第一里程碑建议。

Provisioning 必须幂等、可重试、可回滚；失败不能留下半个部门或孤儿群聊。

### 7.5 Kickoff

- **项目级 kickoff**：助理/PM 部门复述目标、部门划分、接口、风险、第一里程碑；需要用户确认的问题不超过 3 个。
- **部门级 kickoff**：部门主管复述本部门目标、分工视角、讨论规则、验收标准、依赖；员工确认自己的角度。

### 7.6 部门生命周期

draft -> provisioning -> active -> paused -> disbanding -> archived

- **paused**：用户/助理/预算触发；停止接新任务，保留状态与记忆。
- **disbanding**：完成收尾、移交产出与记忆、关闭权限；部门记忆按规则移交项目/组织记忆。
- **archived**：只读；可检索/导出；不再消耗模型。
- **复盘**：部门解散/里程碑结束时，主管与助理产出「什么有效、什么无效、下次怎么改」。

### 7.7 部门模板

| 模板 | 结构 | 适用 |
|---|---|---|
| 三部门交付（默认） | 产品部门 + 研发部门 + 测试部门 | 单项目小项目组 |
| 加平台部门 | 上述 + 平台/架构部门 | 有接口/安全/质量挑战 |
| PM 部门制 | 助理 + PM 部门 + 交付部门 | 需求复杂、需要独立产品判断 |
| 研究/写作 | 研究部门 + 写作部门 + 事实核查 | 报告、方案、调研 |

v0.0.1 至少实现「三部门交付」与「加平台部门」两种。


## 8. 工作协议

### 8.1 任务是一等对象

任务不能只存在于聊天里。最小字段：

| 字段 | 说明 |
|---|---|
| id / project_id / department_id | 稳定标识与归属 |
| title / goal | 一句话标题与目标 |
| acceptance_criteria | 可测试的验收标准，逐条编号 |
| owner / reviewers / approver | 执行者、评审者、最终验收者；作者不能自审 |
| perspective | **该任务的分工视角**（页面/接口/数据流/测试等） |
| priority / estimate / budget | 排序、估算、成本上限 |
| dependencies / blocks | 依赖与阻塞关系 |
| artifact_refs | 关联产出物版本 |
| state / version | 状态与乐观锁版本 |
| created_by / created_at / due_at | 来源与时限 |
| evidence | 完成证据（测试日志、评审记录、命令输出） |

### 8.2 任务状态机

    [*] -> proposed
    proposed -> ready: 接受/补齐 DoR
    proposed -> canceled: 拒绝/重复/超范围
    ready -> discussing: 主管分派并写明分工视角
    discussing -> in_progress: 视角确认/讨论收敛
    discussing -> changes_requested: 需要补方案
    in_progress -> in_review: 提交产出物
    in_progress -> blocked: 缺依赖/信息/决策
    blocked -> in_progress: 解除阻塞
    in_review -> approved: 评审通过
    in_review -> changes_requested: 要求返工
    changes_requested -> in_review: 重新提交
    approved -> done: 验收通过
    in_progress -> failed: 不可恢复
    blocked -> canceled: 放弃
    done -> [*]
    canceled -> [*]
    failed -> [*]

**正交标记**：escalated（已升级，记录 from_state / escalated_at）、at_risk（超时/超预算）、waived（人类豁免，需决策记录）。不要把升级做成一个普通状态。

**返工/重开上限**：同一任务返工最多 2 轮；同一 blocker 复现 2 次即升级；任务完成后重开最多 1 次，第二次必须人类批准。

**discussing 状态**：主管分派任务时必须为每个执行者写明分工视角；执行者先提交「我的视角 + 计划 + 风险」。有冲突进入部门内讨论；无冲突由主管确认后进入 in_progress。

### 8.3 DoR 与 DoD

**Definition of Ready（DoR）**：

- 目标与背景清楚。
- 验收标准可测试。
- owner、reviewers、approver 已定。
- 每个执行者的分工视角已写明。
- 依赖已识别。
- 预算与时限已给。
- 需要的产出物类型明确。

**Definition of Done（DoD）**：

- 每条验收标准都有证据。
- 产出物已登记为不可变版本。
- 评审通过；无未决 blocker。
- 测试证据可复现。
- 需要的人类闸门已签。
- 相关决策/风险/遗留问题已记录。
- 记忆候选已提交（如有可复用经验）。

### 8.4 产出物注册表

聊天是过程，产出物是契约。所有验收、评审、返工都针对某个不可变版本。

| 产出物 | 最小内容 | 关联 | 证据 |
|---|---|---|---|
| 意图卡 / PRD | 问题、用户、范围、用户故事、验收标准、非目标 | 需求 ID、决策 | 产品确认 + 人类闸门 |
| 技术方案 | 架构、接口、数据、风险、回滚 | PRD 版本 | 研发评审 + 可测试性确认 |
| 代码 | commit SHA、diff、测试 | 任务/PRD | CI 日志 + 评审 |
| 测试报告 | 用例、环境、结果、缺陷 | 代码 SHA、环境 | 可复现命令/日志 |
| 评审记录 | 挑战、证据、裁决 | 产出物版本 | 评审人签字 |
| 决策记录 | 背景、选项、决定、理由、异议 | 任务/产出物 | 决策人 + 人类确认 |

**规则**：版本只增不改；修正产生新版本并用 supersedes 关联；注册表保存内容哈希与不可变 URI；代码优先放 Git，文档可放 Git 或内容库。

### 8.5 评审协议

**触发**：PRD、技术方案、代码、测试报告、范围变更、质量豁免。

**角色**：作者（回应）、评审人（质疑，不能是作者）、主持人（部门主管/助理，管流程不管对错）、裁决人（领域 owner）、人类（最终）。

**挑战单**：

- from_department / to_department / artifact_id / artifact_version
- severity：blocker / major / minor / question
- stance：一句话立场
- claim：一句话说明问题
- evidence_ids：产物版本 + 章节/行号/commit/测试运行 + 可复现命令与观察
- impact / proposed_resolution
- owner / due_at / status / thread

**裁决**：

- verdict：approve / approve_with_comments / request_changes / escalate
- checked：实际验证了什么
- rationale / conditions / residual_risk
- reviewer（≠作者）/ decided_at / decision_record_id

**证据标准**：blocker 必须指向被违反的验收标准、回归或可复现缺陷；没有证据的质疑自动降级为 question。豁免的举证责任在申请方。

### 8.6 讨论协议

#### 8.6.1 部门内讨论（Intra-department discussion）

**触发**：同一部门内，员工对实现方案、接口、数据流、验收标准有分歧。

**规则**：

- 每个员工在任务分派时已有明确的 perspective；讨论时以**「方便自己开发」为第一原则**，不得假装全局中立。
- 员工可以陈述「为什么这样对我这部分更方便/更安全/更省时」，并给出证据（接口、性能、测试、依赖）。
- **全局权衡由部门主管拍板**；部门主管可以要求 PM/助理提供全局约束，但不能让员工互相替全局做决定。
- 讨论有轮次上限：每人最多 5 条、单部门讨论总计最多 15 条（两人参与时实际最多 10 条；多人参与时可用到 15）；超过后部门主管直接裁决或升级。
- 讨论记录进入任务线程与部门记忆候选；裁决写决策记录（如果影响接口/范围/质量）。

**为什么这样设计**：模拟真实公司里「前端希望接口简单、后端希望契约稳定、数据流希望状态集中」的局部最优冲突；让每个角色从自己的开发便利出发，再由主管做全局取舍，比让所有 Agent 都假装「客观中立」更容易暴露真实取舍。

#### 8.6.2 跨部门讨论/辩论

**触发**：接口冲突、需求歧义、质量争议、资源冲突、架构分歧、范围变更。

**角色**：双方部门主管（代表部门）、主持人（助理）、裁决人（领域 owner / 人类）、记录者（系统）。

**轮次（可数定义）**：

- 每人最多 5 条提交，总提交上限 15 条；双方各 1 人时实际最多 10 条，多代表/多轮时可用到 15 条。
- R1：双方各 1 条立场 + 各 1 条回应；R2：双方各 1 条反驳；仍有分歧可继续，但累计到 15 条即停止。
- 每条提交必须带 stance 与 evidence_ids；没有新证据的重复提交不计入轮次，由主持人退回。
- 超过 15 条：员工级争议由本部门主管裁决；**主管之间/跨部门争议交给助理，助理整理后反馈用户**。

**硬停止**：总提交达到 15 条、时间盒（异步 24h）、或预算耗尽。达到任一条件即升级。

**死锁判定**：连续两次提交 stance 相同且 evidence_ids 无新增 -> 判定死锁，主持人记录并升级，不自行裁决。

**反虚假共识**：评审人先独立盲评再对表（P1）；裁决要求显式填写 dissent；高风险变更设「魔鬼代言人」；裁决人不能是作者；用 rubric 而非「感觉不错」；v0.0.1 至少提供人类抽检入口。

**反串谋**：评审人轮换、作者/审批人分离、同一对 Agent 互审需第三人、随机人类抽检、审批通过率异常告警、红队 Agent、验证者使用不同提示词/会话。

#### 8.6.3 沟通隔离与临时桥

- **部门内**：员工之间可以正常群聊、讨论。
- **跨部门**：默认由部门主管对部门主管；员工不能直接找其他部门员工。
- **部门主管 ↔ 用户**：默认必须经助理转接；主管不能直接私聊用户。
- **用户观察者**：用户可以在平台查看所有群聊消息，但默认不参与部门讨论。
- **临时桥**：用户可以临时开通「跨部门直连」「主管直连用户」「某两个 Agent 直连」，必须指定范围与到期时间；到期自动关闭并通知；所有桥接消息留审计。
- **隔离只限制沟通路由，不限制用户读取**；用户始终可以查看所有群聊记录。

### 8.7 决策记录

每个不可逆或跨部门决策一条不可变记录：

    id / title / status（proposed / accepted / superseded / rejected）
    context
    options[]
    decision
    rationale
    evidence[]
    dissent[]
    deciders[] / consulted[] / informed[]
    affected_tasks[] / affected_artifacts[]
    revisit_trigger
    supersedes / superseded_by
    human_ack
    created_at

规则：范围变更、质量豁免、架构选择、跨部门裁决必须写决策记录；异议必须保留；修正用新记录 supersede，不能改旧记录；决策记录可检索，并在任务与产出物页面双向链接。

### 8.8 升级阶梯

| 级别 | 触发 | 处理者 | 建议 SLA | 输出 |
|---|---|---|---|---|
| L0 | 自检、单测、DoD 清单 | owner | 即时 | 证据 |
| L1 | 部门内冲突、优先级、返工 | 部门主管 | 4h | 任务更新 |
| L2 | 跨部门接口/范围/质量争议 | 双方主管 + 助理主持 | 24h | 选项 + 建议 |
| L3 | 预算、范围、不可逆、质量豁免、伦理 | 项目主管 | 24h | 决策记录 |
| L4 | 死锁、无决策、重大风险 | 项目主管 | 尽快 | 决策记录 + 风险确认 |

升级包必须包含：争议点、双方证据、选项、推荐、不决策的后果、需要谁在什么时间前决定。人类不是默认收件箱，而是异常通道。

**主管间争论**：部门主管之间的争论由助理主持；超过 15 条或无法收敛时，助理整理成一页决策简报反馈用户，由用户裁决。

### 8.9 反模式与机制防线

| 反模式 | 表现 | 机制防线 |
|---|---|---|
| 微观管理 | 主管重写每个产物，所有事排队 | 权限矩阵；只评论产物版本；分派预算；WIP 限制 |
| 上下文爆炸 | 把全部消息/产物塞进上下文 | 结构化交接包；按任务检索；摘要；token 预算；分层记忆 |
| 虚假共识 | 一轮全票通过，无人异议 | 盲评；dissent 字段；魔鬼代言人；rubric；人类抽检 |
| 串谋/互捧 | 两个 Agent 互相批准低质产物 | 作者≠审批者；轮换；第三人复核；异常审批率告警；红队 |
| 越权/过度代理 | 自行改范围、合并代码、花钱、对外承诺 | 最小权限；能力令牌；双钥匙；不可逆动作人类审批；工具白名单 |
| 单点瓶颈 | 所有决策等主管 | 例外升级；异步队列；有限 fan-out；部门内自治 |
| 规格/角色漂移 | 忽略约束、跑偏、重复劳动 | 任务契约；DoR；角色卡；固定产物版本；验收测试 |
| 验证缺失/表演 | 「测试通过」但无日志、无复现 | 独立验证者带工具；证据产物；禁止自报通过；测试签字 |
| 死锁/无终止 | 反复争论、永不结束 | 轮次上限；时间盒；死锁检测；外部终止；DoD |
| 信息囤积/断链 | 关键上下文不共享，接口对不上 | 共享产物注册表；强制交接包；消息总线；接口契约 |
| 评估偏差 | 裁判偏好冗长/自己的输出 | 盲评；多裁判；位置随机化；人类校准 |
| 成本/延迟失控 | 任务越做越贵，收益不足 | 任务价值门槛；DeepSeek 档位；预算上限；停止条件 |

### 8.10 SLA 与预算

- 任务：in_progress 超过估算 50% 提醒；in_review 超过评审 SLA 升级；blocked 超时自动升级。
- 评审：blocker 24h 内响应；major 48h；minor 可批量。
- 部门：每部门每日/每周预算；超 80% 告警，超 100% 暂停接新任务。
- 人类：决策收件箱每日汇总；只有阻塞/不可逆实时打扰。
- 所有 SLA 可配置；默认值应保守。

### 8.11 文件写入与变更时间线

所有 Agent 共用一套 **WriteTool**，而不是各自直接写文件。

- **写入事件**：agent_id、path、base_hash、diff/content、reason、task_id、branch；提交后进入写入队列。
- **串行化**：默认全局串行——任一写入事件未消费前，其他 Agent 不得写入；后续可配置按文件并行；分支切换/提交/批量重构使用全局锁。
- **冲突检测**：base_hash 不匹配则拒绝，要求重新读取/变基；绝不静默覆盖。
- **时间线**：每个文件保留最近 30 次变更（配置项 write_timeline_limit，用户可调），记录 diff、Agent、时间、任务、分支、commit、原因；工具 view_change_history 可查。
- **Git 监听**：分支切换/提交时记录事件；提交把自上次提交以来的多次改动合并为「commit 组」；时间线仍保留最近 30 条。
- **审计**：所有写入事件可追溯；不能通过 Bash 绕过 WriteTool 写文件（Bash 写文件需审批或标记为不受管变更）。


## 9. 记忆体系

### 9.1 为什么记忆是部门基础设施

一个组织真正的资产不是某次对话，而是**可复用的判断**：为什么选这个方案、谁擅长什么、这个部门的接口约定是什么、上次踩过什么坑、项目主管的红线是什么。没有记忆，每个任务都要重新解释；有了坏记忆，部门会自信地重复错误。

Lignting 的记忆设计遵循一句话：

> **日志全量，档案精选，提示词极简。**

- **日志全量**：所有消息、任务事件、评审、决策、工具痕迹都可追溯，不依赖模型「记得」。
- **档案精选**：只有可复用、可验证、与决策相关的事实进入长期档案，避免把聊天垃圾固化。
- **提示词极简**：每次模型调用只注入当前任务真正需要的片段，其余按需检索。

### 9.2 四层能力，六个实现层

用户与产品文档使用「四层记忆」；实现上拆成六个层，便于分别治理：

| 用户可见的四层 | 实现层 | 载体 | 作用 |
|---|---|---|---|
| **短期上下文** | L0 事件日志 | 平台消息/事件库 + Agent 会话日志 | 不可变事实源，可回放 |
| | L1 工作上下文 | 会话投影 + 压缩检查点 | 当前模型看到的窗口 |
| **触发式记忆** | L2 候选记忆 | 抽取管道输出、待审队列 | 把事件变成候选事实 |
| **档案记忆** | L3 档案 | 结构化实体表 + 叙事文档 + 快照 | 跨会话长期知识 |
| **自适应提示词** | L4 管理手册 | 分章节文本，注入 system 稳定前缀 | Agent 自我维护的判断规则 |
| **（支撑层）** | L5 检索与注入 | 查询路由 + 预算分配 + 降级 | 决定每次调用看到什么 |

四层能力不是四张表，而是**三种时间尺度 + 一条自我修改通道**：本次会话、跨会话、长期组织知识、Agent 自己的判断规则。

### 9.3 记忆对象：八类实体

部门主管/助理的记忆对象不是「用户/群」，而是组织管理中的八类实体：

| 实体 | 键 | 典型内容 | 主要写者 | 主要读者 |
|---|---|---|---|---|
| 项目主管 | `user_id` | 目标、偏好、决策风格、红线、授权范围 | 助理 | 助理、部门主管（受限） |
| 员工 Agent | `agent_id` | 能力域、分工视角、证据化产出记录、返工原因 | 部门主管/助理（观察）、员工自述 | 部门主管（派单）、助理（排期） |
| 部门 | `department_id` | 使命、目标、员工、视角、阶段、共识与分歧、节奏 | 部门主管 | 全部门 |
| 项目 | `project_id` | 范围、里程碑、约束、依赖、风险 | 助理/PM 部门 | 部门主管/员工 |
| 任务 | `task_id` | 目标、验收标准、状态、视角、返工原因、产出引用 | 部门主管/系统 | 部门主管/员工 |
| 决策 | `decision_id` | 决策、备选、理由、影响、推翻条件 | 部门主管/助理（人类拍板时代记） | 全员 |
| 争议 | `dispute_id` | 双方立场、证据、裁决、遗留风险 | 部门主管/助理 | 部门主管、人类 |
| 能力标签 | `(agent_id, domain)` | 分数、证据数、最近验证时间、失败案例 | 系统统计 + 部门主管校正 | 部门主管（派单） |

**关键差异**：决策与争议必须**双时间**（何时生效 / 何时失效）+ **证据引用** + **立场不可覆盖**。聊天记忆可以模糊，决策记忆不能。

### 9.4 短期上下文（L0 + L1）

**L0 事件日志**是审计根：

- 每个 Agent 的会话是 append-only 事件流：用户/Agent 消息、工具调用、工具结果、任务状态、评审、决策、压缩标记。
- 日志不可变；压缩只改「模型看到的投影」，不删历史。
- 崩溃后能重建「当时模型看到了什么」；这是调试、审计与信任的基础。
- 平台消息与 Agent 会话日志是两个实体：平台消息是「对外事实」，会话日志是「执行轨迹」。二者用消息 ID / 事件 ID 关联，不混为一张表。
- 因此 L0 不是一张表，而是两段日志：**平台对话日志**（人类可见事实）+ **Agent 执行日志**（模型行为事实）；二者以消息/事件 ID 关联，共同构成可回放的审计根。

**L1 工作上下文**是模型每次调用看到的窗口：

- **v0.0.1 的所有权**：核心自己装配/压缩最终 prompt；使用结构化检查点，不依赖外部运行时。
- **`context.request` 是每 turn 的持久快照**：分区摘要、注入条目 ref（消息/档案/任务）、token 估算与来源、模型/超参、turn id。它是「当时模型看到了什么」的审计手段。
- **压缩不变量**：达到阈值时，把较早历史替换为结构化检查点（目标、关键概念、文件/路径、错误与修复、待办、当前工作、下一步、关键上下文），保留最近一段逐字历史；检查点必须保留路径、命令、错误串、接口名等标识；固定注入红线/当前目标/验收标准；工具输出只保留最近 N 条完整结果，并保持 tool_call/result 配对。
- **fork 在 v0.0.1 不提供**；需要「换方案重试」时用「新会话 + 交接包」。

**员工 Agent 的 L1**：事件日志 + 投影 + 压缩 + 恢复；每个员工一个独立会话；跨部门只通过消息/决策包引用，不合并会话。

### 9.5 触发式记忆（L2）

**触发源以事件为主，消息量只作兜底**：

- 任务关闭 / 返工 / 取消。
- 评审裁决（通过、拒绝、豁免）。
- 跨部门争议裁决。
- 人类拍板、偏好表达、红线变更。
- 员工入队/离队、角色变更。
- 里程碑达成/失败。
- 事故/故障复盘。
- 兜底：每 N 条消息或每 24 小时对活跃会话做一次轻量扫描。

**为什么不用「每 N 条消息」做主触发**：部门场景里消息量与信息量严重脱钩。一场 300 条消息的辩论可能只产出一个决策；人类一句「以后都用 pnpm」只有 1 条消息，却价值最高。

**抽取管道**：

1. 收集触发窗口内的事件与引用。
2. 用便宜模型抽取候选事实：`claim`（一句话）、实体/键、证据引用、置信度、敏感度、有效期。
3. 去重/冲突检查：同一 `(entity, key)` 是否存在；是补充、修正还是矛盾。
4. 写入候选队列（L2），不直接写 L3。
5. 审核/晋升：低风险自动合并；决策/争议/敏感信息需主管或人类确认。
6. 失败处理：单飞锁、指数退避、冷却、超时预算；**部分成功要单独记账**（append 型写入重试会重复写同一批事实）。
7. 可观测：抽取任务、token 成本、写入数、冲突数、拒绝数、失败原因。

**写入四道门槛**（员工与自动抽取都必须满足）：

1. **可复用**：未来任务会用到吗？一次性上下文不写。
2. **可验证**：有证据吗？消息/文件/命令/验收记录；模型推断不写，或标低置信且需复核。
3. **决策相关**：会改变未来的派单、验收、沟通吗？
4. **归属明确**：属于哪个 `(entity, key)`？归属不清不写。

**不写清单**：

- 完整对话记录、原始转录（L0 的职责，不是档案）。
- 模型自我叙述/推理过程（「我认为用户可能…」）。
- 临时调试输出、日志、可再生成的计算结果。
- 第三方隐私、未授权的个人信息。
- 无法归因的推断与传闻（如必须保留，只能进争议档案并标注「未证实」）。

**候选记忆格式（示意）**：

```json
{
  "scope": "employee|department|project|task|decision|dispute",
  "key": "<entity_id>",
  "claim": "一句话事实/结论",
  "evidence": [{"kind": "message|file|command|verdict", "ref": "..."}],
  "confidence": "high|medium|low",
  "valid_from": "ISO8601",
  "supersedes": ["mem_id"],
  "ttl_hint": "30d|never"
}
```

**额度**：员工每任务 ≤ 5 条候选、每条 ≤ 200 字、至少 1 条证据；部门主管/助理的自动抽取也受每日条数与 token 预算约束。没有额度，记忆系统一定会被「我觉得」淹没。

### 9.6 档案记忆（L3）

档案不是 KV 表，而是**有容量预算、有版本、有审计的可写知识库**。

**结构**：

- 结构化事实：按八类实体存储，字段包括 `entity/key/value/summary/tags/confidence/evidence/sensitivity/valid_from/valid_until/supersedes/version/status`。
- 叙事文档：部门/项目的「当前叙事摘要」，Markdown 存储，可 diff、可回滚；用于注入与人类阅读。
- 快照：每次压缩/重大修改前保存原文，支持审计与恢复。
- 索引：结构化检索 + 全文检索；语义检索作为可选。

**两个上限必须分开**：

- **渲染上限**：单条档案注入提示词的最大长度（例如摘要 500–1500 字），超出只给「标题 + 更新时间 + 取数路径」，模型按需分页读取。
- **存储上限**：单条档案的硬上限（例如 15,000 字）；超出触发压缩或拒绝，不能静默截断。

**容量治理**：

- 超限先完整落库，再异步压缩；或拒绝并返回压缩指引（可配置）。
- 压缩必须基于全文，保留事实、合并重复、只丢冗余；压缩后自校验字数，未达标不能声称完成。
- 压缩失败恢复原文，不静默留半成品；压缩前快照；同一 key 单飞。
- 内部/元数据表永久豁免容量治理（否则会把抽取管线自己拧死）。
- 超限条目可枚举、可观测、可人工处理。

**冲突策略**（按实体类型选择）：

- 决策/争议/能力：**失效而非删除**（双时间 + `supersedes`），保留「当时为什么」。
- 任务/进度/名单：upsert + 版本号。
- 观察类事实：ADD-only + 检索期时间/权威度排序，接受一定冗余。

**检索**：

- 结构化优先：按 `(entity, key)` 取当前视图。
- 全文兜底：实体名、路径、关键词、决策标题。
- 语义可选：配置 embedding 时启用，必须与全文融合重排，不能单独用向量。
- 重排：相关性 + 权威度 + 新近性（指数衰减）+ 证据强度；红线/决策有硬优先级，不参与衰减。
- 每条注入内容带来源标签（表/key/时间/证据 ID），支持「为什么这么判断」。

### 9.7 自适应提示词（L4）

自适应提示词是 Agent 的「管理手册」，不是便签。

**内容分章**（建议 800–1500 字，约 1.5–3K token）：

1. `# 角色与目标`
2. `# 管理原则`（派单、验收、返工）
3. `# 红线与升级规则`
4. `# 项目主管的偏好`
5. `# 部门现状速记`（≤200 字，滚动更新）

**注入位置**：注入 system 稳定前缀（核心自己组装 prompt）；每轮把实际注入内容记录到 `context.request`。

**写入规则**：

- 只写「经过事件验证的教训」，每条带来源事件 ID。
- 不写一次性任务细节（那属于 L3）。
- 不写推测、不写会削弱安全策略的内容、不写秘密。
- 有大小上限；超限必须压缩/拒绝，不能静默截断。
- 每次修改产生版本与 diff；人类可编辑、可回滚、可禁用。
- 与系统提示词/角色卡冲突时，优先级：系统安全策略 > 人类指令 > 角色卡/部门章程 > 自适应提示词 > 档案。

**谁可以改**：

- **v0.0.1 默认仅提议**：修改进入待审队列，人类批准后生效；只有「非红线、非权限、非对外承诺」的低风险修改可以配置为自动应用，且必须有 diff、冷却期、回滚与审计。
- 高风险（红线、权限、对外承诺）只能提议，需人类批准。
- L4 内容在 prompt 中必须被视为**数据**而不是系统指令；新增「记忆投毒 → 后续会话越权尝试被拒」回归用例。
- 员工 Agent 默认只读；可维护自己的小型「个人笔记」，不进入组织级手册。

### 9.8 员工 Agent 的记忆边界

员工 = **不可变会话日志 + 稀疏档案**：

- **会话日志**：完整保留，用于恢复、调试、审计；可压缩投影，不删原始事件。
- **档案写入**：只能提交候选，不能直接写组织级档案；每任务 ≤5 条、≤200 字、至少 1 条证据。
- **档案读取**：本人任务上下文 + 该任务需要的项目/部门档案片段 + 公开决策；默认不读其他部门私有档案、员工评价、争议对方立场。
- **晋升路径**：`propose → review → merge`；部门主管在任务关闭时审核合并；人类拍板/红线由助理直接写。
- **禁止**：把完整对话、工具日志、其他 Agent 的私聊、未授权个人信息写入档案。

### 9.9 检索与注入（L5）

**检索三步**：

1. **结构化优先**：任务、部门、员工、决策、项目约束，按 key 精确取当前视图。
2. **全文兜底**：消息、档案、产出物、决策标题；中文支持 2 字及以上片段。
3. **语义可选**：仅在配置 embedding 时启用；与全文融合重排。

**注入预算（默认建议，可配置）**：预算 = `min(百分比 × 有效输入预算, 绝对上限)`；按模型窗口预设（32K / 128K+）归一化，合计不超过 100%；核心自己计数/估算，保留 5–10% 安全边际。

| 分区 | 占比 | 内容 | 超预算时 |
|---|---|---|---|
| 系统/人设/管理手册 | 5–8% | L4 + 红线 | 手册必须完整，宁可砍其它 |
| 当前任务 | 35–45% | 目标、验收标准、上下文、产出要求 | 保留验收标准与目标 |
| 相关档案 | 25–30% | 员工/部门/项目/决策片段 | 先丢最旧、最低权威 |
| 近期会话 | 20% | L1 尾窗 | 按时间截断 |

**降级链**：检索失败 → 只用 L4 + 当前任务；档案超限 → 只给标题 + 更新时间 + 取数提示；上下文不足 → 先压缩 L1，再缩档案预算，最后才砍任务说明。

**默认稀疏**：档案默认不全量注入；先给摘要与取数路径，模型需要时再读。全量注入员工档案 = token 灾难 + 隐私风险。按需读取必须通过受权限约束的「记忆读取」工具；工具不可用时降级为摘要注入，并在 `context.request` 标注。

### 9.10 记忆治理与失败模式

**可见性四级**：

- `agent-private`：员工自己的会话/笔记。
- `department`：部门档案。
- `org`：跨部门决策包、共享约定。
- `human-only`：人类偏好、评价、敏感信息。

**治理规则**：

- 每个 `(entity, key)` 单飞锁；失败退避 + 冷却；部分成功单独记账。
- 压缩失败恢复原文；压缩前快照；快照有保留上限。
- 渲染上限 ≠ 存储上限；列表/预览分页；全文按需读。
- 超限可枚举；用量按子系统归集；关闭时冲刷未处理队列。
- 人类可读、可导出、可删除；删除留墓碑，避免快照/缓存复活。
- 读取留痕：谁读了哪条档案，用于事后解释。
- 敏感字段写入前 redaction；密钥/令牌绝不入记忆。

**失败模式**：

| 失败 | 表现 | 对策 |
|---|---|---|
| 记忆污染 | 把推断/谣言写成事实 | 证据门槛；候选审核；来源标签；人类可删 |
| 记忆膨胀 | 什么都记，检索变差 | 额度；四道门槛；定期压缩；低价值过期 |
| 上下文过载 | 注入太多，模型失焦 | 预算表；默认稀疏；按需读取；压缩 |
| 事实陈旧 | 旧决策仍被当作现行 | 双时间；失效标记；定期复核；冲突提示 |
| 隐私泄漏 | 跨部门/第三方信息被注入 | 权限即视图；redaction；审计；删除 |
| 成本失控 | 抽取/压缩调用过多 | 事件触发；批处理；便宜模型；预算；冷却 |
| 静默截断 | 内容被截断但没人知道 | 拒绝/告警/可观测；禁止静默失败 |

### 9.11 与 NeoBot 的差异

- **NeoBot**：面向聊天机器人的「用户/群/物品」记忆；触发以消息条数为主；自适应提示词约 200 字。我们保留其失败语义（单飞、冷却、部分成功、快照、容量治理、关闭冲刷），但把对象换成部门管理八实体，把触发改为事件驱动，把管理手册扩到 800–1500 字。
- **本项目的增量**：消息全量落库、事件驱触发、部门/项目/决策双时间、权限即视图、人类可纠正；不依赖外部 Agent 运行时。
- **本项目的结构性优势**：平台消息全量落库。NeoBot 的短期记忆是进程内队列，重启即丢；我们的 L1 可以从消息库重建，L0 天然存在。

## 10. 对话平台

### 10.1 设计目标

对话平台不是「Slack 克隆」，而是**Agent 优先的本地工作内核**：

- 人-Agent、Agent-Agent 的所有沟通都在这里发生。
- 所有人类可见消息、任务事件、评审、决策都持久化。
- 检索快、准、可过滤；断线可补；重启不丢。
- 默认只在本机；数据可备份、可导出；不依赖云。

### 10.2 信息架构

```text
工作区（Workspace）
├── 助理私聊（Assistant DM）
├── 项目群聊（Project Group）
│   ├── 部门群聊（Department A / B / C）
│   ├── 跨部门评审（Cross-department Review）
│   ├── 临时讨论组（Ad-hoc Group，用户/主管可建）
│   ├── 决策日志（Decisions，只读流）
│   └── 任务线程（Task threads，自动创建）
├── 收件箱（Inbox：待决定 / 稍后 / FYI）
├── 审批中心（Approvals：等待中 / 已处理 / 超时）
├── Agent 管理（Agents：启动 / 暂停 / 停止 / 配置）
├── 产出物（Artifacts）
├── 任务板（Tasks）
├── 记忆（Memory Inspector）
├── 组织（Org / Departments）
├── 搜索（Search）
└── 设置 / 审计 / 成本（Settings / Audit / Cost）
```

- **群聊**承载部门日常沟通与多 Agent 讨论；**线程**承载任务/产出物具体讨论；**任务板**承载状态；**产出物**承载契约；**决策日志**承载不可变结论。
- 所有 Agent 都经由平台启动、对话与管理；平台不是单纯聊天入口，而是 Agent 能力的操作面。
- 任务线程与产出物线程自动创建、自动关联，不要求人手动整理。
- 群聊支持多 Agent 发言队列、@提及、轮次上限；跨部门群聊只允许结构化评审/决策消息，避免信息污染。
- 用户可查看所有群聊（观察者）；部门内/跨部门隔离只限制 Agent 的默认路由。

### 10.3 系统对象模型（跨模块）

> 平台只拥有消息/事件/审计/索引；Task/Artifact/MemoryEntry/Approval 的**写模型在 Agent 核心**，平台保存只读投影用于展示与检索。

| 对象 | 说明 |
|---|---|
| Principal | 人/Agent 统一主体，`kind` 为 human 或 agent |
| Conversation | DM / 部门群聊 / 项目群聊 / 临时讨论组 / thread 容器；带 visibility 与成员 |
| Message | 人类可见的消息，带 `seq`、类型、正文、引用 |
| Event | 系统/任务/评审/决策事件，驱动 UI 与 Agent |
| Task | 任务对象（见 8.1） |
| Artifact | 产出物注册表条目（见 8.4） |
| MemoryEntry | 档案条目（见 9.6） |
| Approval | 审批请求与结果 |
| ContextRequest | 每 turn 的上下文快照（注入条目、来源、token 估算、模型/超参、turn id） |
| AuditRecord | 审计记录（平台唯一 append-only 流） |

### 10.4 消息模型

```text
Message
  id                稳定 ID
  seq               workspace 内单调递增，全序权威
  conversation_id   所属会话
  thread_root_id    线程根（两级线程）
  sender_id         人/Agent
  kind              text | card | tool_summary | task_event | review |
                    decision | approval | artifact | system
  body_text         人类可读、可检索的文本投影
  body_json         结构化内容（卡片、引用、字段）
  refs              task_id / artifact_id / decision_id / parent_message_id
  mentions[]        写入时算好
  visibility        private | department | project | org
  client_msg_id     幂等键
  created_at / edited_at / deleted_at
```

**消息 vs 事件 vs 轨迹**：

- **消息**：人类可见的沟通与结构化卡片；全部落库、默认进检索。
- **事件**：状态变化（任务、评审、决策、审批）；全部落库，驱动 UI/Agent，可按类型进检索。
- **轨迹**：模型 token 流、工具调用细节、调试日志；作为审计事件保留，**默认不进检索索引**，避免「搜部署搜出 shell 输出」。人类可在消息详情中展开查看。

这个边界必须在产品上写清楚：**「所有消息都存」不等于「所有模型思考都进搜索」。**

### 10.5 实时与投递

- **UI**：SSE + `Last-Event-ID` 断线续传；事件回放来自数据库，不来自内存缓冲；断线 3 天与 3 秒走同一条路径。
- **Agent**：HTTP 游标长轮询（`after_seq`）；每个 Agent 独立游标；不依赖会话级广播确认。
- **投递语义**：at-least-once；消费端用 `client_msg_id` / 事件 ID 幂等；不承诺 exactly-once。
- **多端**：每个客户端独立游标；已读用 `last_read_seq`，不做逐条回执。
- **背压**：慢消费者只影响自己；事件保留期可配置；超期需重建/补拉。

### 10.6 检索

**能力**：

- 全文检索：中文 2 字及以上片段、英文、代码标识符、路径、中英混排。
- 结构化过滤：部门、群聊、会话、作者、Agent、时间、消息类型、任务、产出物、决策、标签、附件。
- 排序：BM25/相关性 + 时间衰减 + 会话聚合 + 权威度（决策/钉住消息加权）。
- 结果：高亮片段、上下文跳转、按会话聚合、保存搜索。
- 范围：消息、任务、决策、产出物元数据；任务/决策/产出物来自核心投影，平台不拥有写模型；默认不含原始轨迹。中文 2 字查询走 bigram/短词索引并单列 p95 预算。
- 性能目标：10 万条消息下 p95 < 150–300ms；写入后 <100ms 可检索。
- 索引：与消息写入同事务；可重建；重建期间有状态提示；删除消息不可被任何路径搜到。
- 权限：先过滤再排序；不泄漏不可见会话的存在与数量。

**检索质量评估**：维护 40–60 条金标准查询（中文 2 字词、短语、中英混排、代码标识符、人名、过滤组合、空结果），每次改索引/排序跑 Recall@10、nDCG@10、p95。没有评估集，讨论「检索好不好」只能靠感觉。

### 10.7 通知与注意力

- 通知分级：FYI / 需要知道 / 需要决定 / 阻塞。
- 只有后两级实时打扰；其余进摘要/收件箱。
- 提及、任务分配、审批、阻塞、预算告警是主要触发。
- 支持静音、免打扰、批量审批、稍后处理。
- 助理负责聚合与升级，不直接把部门所有消息推给人类。

### 10.8 界面形态

- **左侧**：工作区、项目/部门群聊、Agent 管理、任务入口、收件箱、审批中心。
- **中间**：消息流；Agent 流式回复；工具卡片；任务/评审/决策卡片；审批卡。
- **右侧**：上下文面板（任务、产出物、Agent 资料、记忆、引用）。
- **顶部**：搜索、状态、预算、暂停/紧急停止。
- **收件箱/审批中心**：待决定/稍后/FYI；等待中/已处理/超时；支持批量（非双钥匙）、稍后处理、授权到期回收。
- **任务板**：看板/列表/时间线；按部门/状态/owner 过滤。
- **产出物**：Markdown、代码 diff、测试报告、版本对比、评论。
- **记忆**：按实体浏览、搜索、编辑/删除/钉住、待审队列、管理手册编辑器、来源链接。
- **组织**：组织图（用户 → 助理 → 部门主管 → 员工）、Agent 状态/预算、启动/暂停/停止、角色卡与视角；负载/最近行为为增强项。
- **成本**：按部门/任务/模型/日期的 token 与费用。
- **命令面板**：键盘优先；常用操作可搜索。
- **可访问性**：键盘导航、对比度、屏幕阅读器基本支持；中文优先，文案可国际化。

### 10.9 本地部署与安全

- 默认绑定 `127.0.0.1`，随机/固定端口，启动打印 URL；可选自动打开浏览器。
- 单用户：首次启动创建本地 owner；不做注册、邮箱验证、OAuth/SSO。
- 远程访问：推荐 SSH 端口转发或 Tailscale 等覆盖网络；不自建公网 TLS。
- 本地 Web 安全：校验 Origin/Host；Cookie `SameSite=Strict` + `HttpOnly`；写操作要求自定义 Header；GET/SSE 同样校验 Origin/Host；默认不返回 CORS 头；不假设 localhost 是安全边界。
- Agent 身份：每个 Agent 独立 Token，可撤销；模型 API Key 只给核心，平台只存引用，不入消息/日志/检索。
- 数据目录：可配置；POSIX 0700 / Windows ACL + DPAPI；不得放在网络/同步盘（WAL 约束）；备份用数据库在线备份或导出，不能直接复制运行中的文件；备份包含数据库、附件、会话/记忆/任务/变更时间线。
- 附件：内容寻址、MIME 白名单、大小上限；下载强制 `Content-Disposition: attachment` + `nosniff`；SVG/HTML 不在同源渲染；解压上限；导出包二次脱敏。
- 审计：登录、会话创建/删除、消息、工具调用、配置/密钥变更、索引重建；审计不可 UI 删除，可整体导出。

### 10.10 平台不做什么

- 不调用模型、不执行工具、不维护 Agent 长期记忆（由核心执行）。
- 不拥有任务/评审/决策写模型（只存核心投影与消息/事件载体）。
- 但平台**是 Agent 启动、暂停、停止、配置与群聊的统一入口**，不是单纯聊天框。
- 不做多租户、公网 SaaS、移动端原生、E2EE、联邦协议（v0.0.1）。
- 不做逐条已读回执、typing/presence 落库、三级以上线程、富文本编辑器。

## 11. Agent 核心框架

### 11.1 运行时架构

    平台事件/任务
        │
        ▼
    收件箱 / 路由（按部门、角色、群成员、@提及）
        │
        ▼
    上下文装配（角色卡、部门章程、任务、视角、档案、会话尾窗）
        │
        ├──> DeepSeek API（默认 deepseek-flash）
        │
        ├──> 工具执行：read_file / write_file / bash / web_search / view_change_history
        │        └── write_file 走共享 WriteTool（串行 + 时间线）
        │
        ▼
    会话日志 / context.request / 平台消息 / 任务投影 / 记忆抽取

### 11.2 Agent 定义

见 6.2 角色卡。补充：

- **模型策略**：默认 deepseek-flash；超时、最大输出、预算；v0.0.1 不做多模型路由。
- **工具策略**：5 个工具的白名单、路径/命令范围、危险命令审批。
- **记忆策略**：可读/可写命名空间、写入额度、是否允许自适应提示词。
- **预算**：每任务/每日 token 与费用上限；超限行为（暂停/降级/升级）。
- **生命周期**：创建、激活、暂停、归档；名字永久，不复用。
- **视角**：每个员工必须有固定 perspective，并在任务分派时再次明确。

### 11.3 收件箱与路由

- 每个 Agent 一个收件箱 + 游标；路由规则：直接提及、任务分配、部门群聊、评审请求、审批结果、系统通知。
- **默认最小可见**：员工只看到本部门任务/群聊；跨部门通过部门主管转接；部门主管与用户通过助理转接。
- 路由去重：同一消息最多投递一次到同一 Agent；重复投递由幂等键处理。
- 唤醒策略：批处理、优先级、静默时段、预算；避免「消息一来就全员唤醒」。
- 群聊发言队列：多个 Agent 被 @ 时按顺序发言，避免同时刷屏；每轮有上限。
- **用户观察者**：用户可读所有群聊；不因路由隔离而丢失可见性。

### 11.4 上下文装配

**分区**（稳定 -> 动态）：

1. 系统安全策略与平台身份。
2. 角色卡（使命、职责、边界、决策权、视角）。
3. 部门章程与协作协议。
4. 管理手册（L4）。
5. 当前任务：目标、验收标准、依赖、产出要求、分工视角。
6. 相关档案：部门/项目/决策/员工片段（按预算）。
7. 会话尾窗：最近消息/工具结果（L1）。
8. 当前输入与工具 schema。
9. 运行时事实：时间、工作区、预算、待审批。

**规则**：

- 核心自己装配/压缩；每个分区有 token 预算与优先级；超预算按 9.9 降级链处理。
- 注入内容带来源标签；模型可引用；context.request 记录实际注入了什么。
- 不把「所有历史」塞进 prompt；按任务检索。
- 工具 schema 只有 5 个，保持稳定，便于缓存。
- 系统提示词保持稳定，便于 KV cache；动态事实放上下文。

### 11.5 工具与沙箱

v0.0.1 只有 5 个工具：

| 工具 | 说明 |
|---|---|
| read_file | 读工作区文件；路径限制；大文件分页/截断 |
| write_file | 共享 WriteTool；写事件、默认全局串行、冲突检测、时间线 |
| bash | 工作区 cwd；超时/输出上限；危险命令审批 |
| web_search | DeepSeek 联网搜索；返回引用 |
| view_change_history | 查看文件变更时间线（最近 30 次，可配置） |

- **沙箱**：工作区根目录、资源限制、超时、命令策略；统一安全语义 + 平台差异矩阵，不承诺行为完全一致。
- **审批**：高风险动作弹审批卡；人类可批准一次/会话/始终；审批结果写审计。
- **工具结果**：大输出截断/落盘，保留引用；错误结构化，便于重试/升级。
- **Bash 与 WriteTool**：Bash 写文件需审批或标记为「不受管变更」；不能静默绕过时间线。

### 11.6 会话与压缩

- 每个 Agent 一个会话；核心拥有会话 ID、事件日志、投影、context.request 快照。
- 事件类型：turn/step、消息、工具调用/结果、压缩、审批、错误。
- **压缩由核心执行**：阈值触发 + 结构化检查点 + 保留尾窗；失败不回滚日志；压缩标记可识别。
- **检查点三屏障**：模型请求前、工具副作用前、每步开始前；持久化成功前不执行。
- **fork**：v0.0.1 不提供；用「新会话 + 交接包」替代。
- 崩溃恢复：已提交前缀保留；中断工具调用标记「结果未知」，不自动重试有副作用的操作；只读/幂等操作可重试。
- 会话不删除；归档/导出；敏感内容可 redact，但审计保留墓碑。

### 11.7 任务、讨论、评审、决策引擎

- 任务状态机（8.2）、DoR/DoD、产出物注册表（8.4）。
- 分工视角：任务分派时写入；员工先确认视角与计划。
- 部门内讨论：员工从各自开发便利出发；部门主管裁决；每人≤5 条、总计≤15 条。
- 跨部门辩论：部门主管代表；助理主持；超过 15 条由助理整理给用户。
- 评审：挑战单、verdict、作者≠评审者、测试独立质量门。
- 决策记录：ADR 式、不可变、可检索、双向链接。
- 升级：L0–L4；升级包一页可读。
- 所有状态转换写事件；状态是事件投影；可重放。

### 11.8 调度与预算

- 任务队列：优先级、依赖、公平性、每 Agent WIP 限制。
- 并发：每部门/全局并发上限；避免 DeepSeek API 限流打爆。
- 预算：人类月上限 > 部门日上限 > 任务预算；任一耗尽触发对应层级暂停并显示「被哪一层暂停」；超 80% 告警，100% 完成当前工具调用后暂停接新任务（不中止有副作用调用），审批保留 24h；人类可追加/一次性放行。
- 暂停/恢复：单 Agent、单部门、全局紧急停止。
- 重试：指数退避 + 抖动；区分可重试/不可重试；死信队列。
- 定时与到期：持久化 timer（due_at / kind / payload / idempotency_key / attempts）；重启补跑；错过窗口按「立即/跳过/合并」策略；用于审批 TTL、SLA、时间盒、简报、预算周期。
- 失败升级：连续失败/超时/预算耗尽/DeepSeek API 不可用 -> 部门主管/助理/人类。

### 11.9 可观测性

- 每次 turn 的 trace + context.request 快照：注入条目/来源、token、模型/超参、工具、延迟、成本、错误。
- 任务指标：周期时间、返工率、评审时长、升级率、证据覆盖率。
- 讨论指标：部门内讨论轮次、跨部门辩论轮次、裁决时长。
- 记忆指标：抽取数、晋升数、冲突数、超限数、注入命中率。
- 成本：按部门/任务/模型/日期。
- 回放：从事件日志重建某次对话/任务；用于调试与审计。
- 日志：结构化、可导出；敏感字段脱敏。

### 11.10 故障恢复

- 消息先落库再投递；Agent 每步 checkpoint；工具副作用前持久化。
- 幂等：消息 client_msg_id、任务状态 version、工具调用 call_id、write event id。
- 进程崩溃：重启后从游标恢复；未完成 turn 标记中断；不重复执行有副作用工具。
- 模型/工具故障：重试/降级/升级；不静默失败。
- 数据损坏：索引重建；数据库备份；事件日志导出。
- 紧急停止：全局暂停所有 Agent，保留消息与状态。
- DeepSeek API 不可用：平台可浏览/检索/导出；Agent 暂停接新任务；恢复后继续，不重复副作用。

### 11.11 扩展点（v0.0.1 不实现）

- 未来可选：更多工具、更多模型供应商（未定）、外部 Agent 运行时（未定）；v0.0.1 不实现。
- v0.0.1 不实现上述扩展，避免复杂度；接口保留但不承诺。


## 12. 协作智能：信息如何流动

### 12.1 视图即权限

不同角色看到不同记忆视图：

| 角色 | 注入什么 | 不注入什么 |
|---|---|---|
| 部门主管 | 部门档案、部门任务、待裁决争议、员工能力证据、管理手册 | 员工私聊原文、人类隐私细节、其他部门私有档案 |
| 助理 | 人类偏好/红线/日程/待办、跨部门待协调项、管理手册 | 技术细节全文（按需检索） |
| 员工 | 本人任务上下文、所需档案片段、项目约束、本部门讨论 | 其他部门档案、员工评价、争议对方立场 |

**不要给所有 Agent 同一份记忆视图**。这既是 token 经济，也是权限模型：靠提示词约束「别乱说」对提示注入没有抵抗力，靠视图隔离才可靠。

### 12.2 交接包

跨 Agent/跨部门交接不靠「读全部聊天」，而靠结构化交接包：

- 任务目标与验收标准。
- 已做决策与理由（链接决策记录）。
- 相关产出物版本与路径。
- 未决问题与风险。
- 证据（测试/命令/日志）。
- 下一步与负责人。

交接包是任务/产出物的投影，不是新的事实源；接收方按需回读原始消息。

### 12.3 共享知识

- **部门私有**：部门档案、内部讨论、员工评价。
- **项目共享**：项目章程、接口契约、术语表、决策记录、产出物。
- **组织共享**：跨部门约定、最佳实践、可复用模板、事故复盘。
- 跨部门共享只给「决策包 + 结论 + 证据引用」，不给过程与原始消息。
- 共享内容也要有 owner、版本、有效期；避免「共享即永久」。

### 12.4 冲突解决

- 先分类：事实争议、方案取舍、优先级、价值判断、资源冲突。
- 事实争议 → 证据/实验；方案取舍 → 选项与 trade-off；优先级/价值 → 人类；资源冲突 → 预算/排期。
- 能靠数据解决的，不开辩论；能靠小实验解决的，不写长文。
- 辩论只用于「有证据、可裁决、值得花时间」的分歧。
- 裁决后：记录 dissent，更新任务/产出物，通知受影响方；不搞「表面一致、私下不执行」。

### 12.5 组织学习

- 任务关闭/返工/事故/里程碑后，部门主管提交「可复用教训」候选。
- 助理定期合并为部门/项目档案，更新管理手册。
- 人类可审阅「本周学到了什么」，纠正错误记忆。
- 组织学习不是「让 Agent 读更多」，而是「把验证过的判断写进正确的地方」。
- 定期清理：过期事实、失效决策、低置信条目、重复条目。

### 12.6 反模式

- **信息囤积**：主管不共享关键上下文，员工重复踩坑。
- **上下文倾倒**：把所有消息/文件塞给 Agent，质量下降、成本上升。
- **过度组织化**：小事也开部门、走评审，人类被流程淹没。
- **表演式辩论**：为了显得认真而争论，没有新证据。
- **记忆即真理**：把档案当不可质疑的教条，不验证。
- **Agent 互捧**：评审变成互相夸奖，质量门失效。

### 12.7 沟通隔离、群聊与用户观察者

**默认沟通拓扑**：

- 部门内：员工之间可以自由群聊/讨论。
- 跨部门：员工不能直接找其他部门员工；由部门主管对部门主管对接。
- 部门主管 ↔ 用户：默认必须经助理转接；主管不能直接私聊用户。
- 助理 ↔ 用户：主通道；助理负责汇总、过滤、升级。
- 项目群聊：所有部门可读的项目级公告/决策；不用于日常部门讨论。
- 跨部门群聊：由助理/部门主管创建，只允许结构化评审/决策消息。
- 临时讨论组：用户/助理/部门主管可建，指定成员与到期时间。

**用户观察者**：

- 用户可查看所有群聊消息（包括部门群聊、临时讨论组、跨部门群聊），但默认不参与部门内讨论。
- 用户可随时加入/退出群聊、@某个 Agent、发消息；加入后 Agent 必须回应。
- 「隔离」只限制 Agent 之间的默认路由，不限制用户的读取权。

**临时桥**：

- 用户可临时开通「跨部门直连」「主管直连用户」「某两个 Agent 直连」。
- 必须指定范围（哪两个主体/哪个群聊）、到期时间、原因。
- 到期自动关闭并通知；桥接期间的消息进入审计；用户可随时手动关闭。
- 桥接不能绕过审批/工具权限/记忆可见性；只改变沟通路由。

**群聊发言控制**：

- 多 Agent 被 @ 时按发言队列依次回复，避免同时刷屏。
- 部门内讨论有轮次上限（每人≤5 条、总计≤15 条），跨部门辩论同。
- 主管/助理可终止讨论并裁决；用户可随时打断/要求收敛。

## 13. 安全、隐私与治理

### 13.1 威胁模型

| 威胁 | 场景 | 影响 | 主要防线 |
|---|---|---|---|
| 本地 Web 被跨站访问 | 恶意网页请求 `127.0.0.1` | 读消息、发指令、改配置 | Origin/Host 校验、SameSite Cookie、自定义 Header、默认 loopback |
| 提示注入 | 网页/文件/Issue/工具输出含恶意指令 | Agent 越权、泄密、执行危险命令 | 不可信内容标记、指令层级、工具白名单、审批、网络/路径限制 |
| 工具滥用 | Agent 执行删除/推送/发布/支付 | 数据丢失、对外事故 | 风险分级、最小权限、双钥匙、人类审批、沙箱 |
| 密钥泄漏 | Key 进入消息/记忆/日志 | 账户被盗、费用损失 | keychain、脱敏、禁止入检索、日志过滤 |
| Agent 冒充 | 伪造 Agent 身份发消息/审批 | 决策污染 | 独立 Token、消息签名/来源、审计 |
| 记忆污染 | 把推断/恶意内容写成档案 | 长期错误决策 | 证据门槛、候选审核、来源、可删除 |
| Agent 串谋 | 互评互捧、绕过质量门 | 低质交付 | 作者≠审批者、轮换、盲评、红队、异常告警 |
| 成本失控 | 无限循环/重复重试/大上下文 | 账单爆炸 | 预算、停止条件、重试上限、便宜模型、上下文压缩 |
| 供应链 | 恶意依赖/工具 | 执行恶意代码 | 来源校验、权限最小化、沙箱、版本锁定 |
| 数据丢失 | 崩溃/误删/磁盘故障 | 工作丢失 | 先写后发、备份、导出、索引可重建、审计 |

### 13.2 本地安全

- 威胁模型边界：v0.0.1 不承诺防御「同一 OS 用户下的恶意本地进程」；目标是进程级隔离 + 数据目录 ACL + 最小令牌。OS 级沙箱（Windows Job Object/AppContainer、macOS sandbox、Linux landlock）为 v0.1 目标。
- 默认只绑 `127.0.0.1`；不默认 `0.0.0.0`。
- 校验 `Origin` / `Host`；拒绝跨站写请求；Cookie `SameSite=Strict`、`HttpOnly`。
- 写操作要求自定义 Header，迫使跨站请求走 preflight。
- 不假设 localhost 是安全边界：任意网页都能向本机端口发请求。
- 远程访问推荐 SSH 端口转发或覆盖网络；不自建公网 TLS，不默认暴露。
- Agent 使用独立 Token，可撤销；人类会话与 Agent 凭证分离。

### 13.3 工具权限

- **最小权限**：每个 Agent 的工具白名单、路径白名单、网络域名白名单、命令策略。
- **风险分级**：只读 / 可逆写 / 不可逆写 / 对外发布 / 花钱；审批策略逐级增强。
- **双钥匙**：不可逆/高风险动作需要作者之外的审批人，必要时人类。
- **沙箱**：工作区根目录、资源限制、超时、网络策略；统一安全语义 + 平台差异矩阵 + 默认拒绝，而不是承诺「行为完全一致」。
- **审计**：每次工具调用记录谁、何时、对什么、参数摘要、结果、审批人；敏感参数脱敏。
- **禁止**：Agent 修改自己的权限、绕过审批、直接写平台库、删除审计。

### 13.4 提示注入

- 明确指令层级：系统安全策略 > 人类指令 > 角色卡/章程 > 自适应提示词 > 档案/网页/文件内容。
- 外部内容（网页、Issue、邮件、文件、工具输出）标记为**不可信数据**；不得让其覆盖系统指令。
- **记忆/L4 也是数据**：管理手册默认仅提议；任何来自记忆/档案的内容都不得被当作系统指令；新增「记忆投毒 → 越权尝试被拒」回归测试。
- 工具调用前检查来源与意图；高风险动作必须人类确认，不因「文档里写了」而自动执行。
- 限制外联：网络域名白名单、上传/下载审批、DLP 式敏感信息检查。
- 输出引用来源；对「根据网页内容执行操作」保持怀疑。
- 红队测试：在 CI/发布前用注入样例测试 Agent 是否越权。

### 13.5 数据保护

- 数据目录权限：POSIX 0700；Windows ACL + DPAPI；支持配置到用户指定位置；不得放网络/同步盘。
- v0.0.1 不做全库加密（明确取舍：磁盘未加密，依赖 OS 账户与磁盘权限）；后续可评估 SQLCipher/OS 级加密。
- 备份：数据库在线备份/导出 + 附件；退出时 checkpoint；备份可加密（用户自选）。
- 导出：消息、任务、产出物、决策、记忆可导出为开放格式；不锁定。
- 删除：消息软删除 + 索引清理；记忆删除留墓碑；审计保留最小必要信息。
- 脱敏：密钥、令牌、身份证号、银行卡等写入前过滤；日志/检索不出现。
- 完整性：审计/任务事件应用层 append-only + 可校验哈希链；不承诺对抗同 OS 用户恶意改库。
- 遥测：默认关闭；不上传任何使用数据；模型调用除外（用户配置的供应商）。

### 13.6 Agent 治理

- **章程**：每个部门有书面章程（目标、范围、权限、预算、升级规则），人类批准。
- **预算**：部门/任务/日/月上限；超限暂停；人类可追加。
- **人事**：创建/解散部门、增减员工、改变角色需人类批准；部门主管可提议。
- **自我修改**：Agent 不能改自己的角色卡/权限/预算；自适应提示词 v0.0.1 默认仅提议，低风险自动应用需显式开启 + diff/冷却/回滚，高风险一律人类批准。
- **职责分离**：作者 ≠ 评审者 ≠ 最终验收者；高风险需第三人；测试有独立质量门。
- **紧急停止**：全局/部门/单 Agent 暂停；停止后保留状态，可恢复。
- **审计**：所有治理动作留痕；定期抽检；异常审批率/成本/失败率告警。

### 13.7 多 Agent 风险

| 风险 | 表现 | 缓解 |
|---|---|---|
| 串谋 | 互评通过、互相包庇 | 作者≠审批者、轮换、盲评、第三人、红队、异常监控 |
| 群体思维 | 很快达成一致，无人异议 | 独立盲评、dissent 字段、魔鬼代言人、rubric |
| 责任扩散 | 出了问题没人负责 | 每个任务/产出物有 owner/approver；决策记录 |
| 无限循环 | 反复争论/重试 | 轮次上限、预算、超时、死锁检测、终止条件 |
| 上下文碎片化 | 各 Agent 信息不一致 | 共享产物注册表、交接包、决策记录、接口契约 |
| 记忆污染 | 错误事实长期传播 | 证据门槛、候选审核、来源、定期清理 |
| 过度代理 | 自行扩权/对外承诺 | 最小权限、双钥匙、人类审批、能力令牌 |

### 13.8 事件响应

1. **暂停**：全局/部门/Agent 紧急停止。
2. **隔离**：撤销 Token、禁用工具、断网。
3. **取证**：导出消息、事件、工具调用、决策、记忆变更。
4. **恢复**：从备份/快照恢复；重建索引；验证数据一致性。
5. **复盘**：写事故报告与决策记录；更新规则/测试；必要时通知受影响方。
6. **改进**：把教训写入部门/组织记忆，更新管理手册与权限策略。

## 14. 质量、成本与可观测性

### 14.1 SLO

| 指标 | 目标（v0.0.1） | 说明 |
|---|---|---|
| 消息持久化 | 「已确认」= 提交返回且按配置同步；v0.0.1 承诺进程崩溃零丢失；断电场景按同步档位（默认可靠档）明确可丢窗口 | 先写后发；崩溃/断电故障注入 |
| 消息可见延迟 | 本地 p95 < 100ms | 写入到 UI 可见 |
| 检索延迟 | 10 万条：中文 2 字 p95 ≤150ms；≥3 字/短语 p95 ≤300ms | 中文 2 字走短词索引，不全表扫描 |
| 索引新鲜度 | 写入后 <100ms 可检索 | 同事务索引 |
| 断线补齐 | 1 小时断线零丢失、零重复显示 | `Last-Event-ID` / 游标 |
| 冷启动 | < 2s（不含模型） | 单机 |
| 崩溃恢复 | 重启后会话/任务状态一致 | 事件日志 + 检查点 |
| Agent 首 token | 取决于模型；本地调度 < 1s | 不含模型延迟 |
| 备份/恢复 | 可验证、可演练 | 至少一次恢复演练 |
| 审计覆盖 | 治理/工具/审批 100% | 可导出 |

### 14.2 指标体系

**产品**：

- T2 首次价值时间（安装 → 组队 + 首个任务创建 ≤30 分钟）；T3 首个交付物被接受 ≤1 个工作日。
- 部门组建时间、首个任务周期。
- 任务吞吐、周期时间、返工率、评审时长、升级率。
- 人类干预次数/天、决策收件箱积压、打扰接受率。
- 记忆命中率（注入后被引用/使用）、检索成功率、搜索后跳转率。
- 7/30 天留存、每周活跃使用天数。

**质量**：

- 缺陷逃逸率（验收后发现的问题）。
- 证据覆盖率（DoD 有证据的任务比例）。
- 决策可追溯率（有决策记录的关键决策比例）。
- 记忆准确率/冲突率（抽检）。
- 评审有效性（评审发现的问题中真实有效的比例）。

**系统**：

- 消息/事件写入成功率、索引延迟、检索 p95。
- Agent turn 成功率、工具错误率、模型错误率、重试率。
- 崩溃恢复时间、数据丢失事件数。
- 每任务 token/费用、每部门日费用、缓存命中率。

**信任**：

- 审计覆盖率、审批合规率、人类抽检通过率。
- 用户主观信任/推荐意愿。
- 安全事故数、越权事件数。

### 14.3 成本控制

- **预算**：任务/部门/日/月；80% 告警、100% 暂停；人类可追加。
- **模型档位**：v0.0.1 全部默认 deepseek-flash；按任务暂停/降级，不做多供应商路由。
- **上下文经济**：压缩、按需检索、工具输出裁剪、工具 schema 按需加载。
- **批处理**：记忆抽取/压缩/摘要批量执行；失败冷却；关闭时冲刷。
- **停止条件**：最大轮次、最大时长、最大 token、无进展检测。
- **缓存**：稳定 system prompt/前缀；相同检索结果；模型供应商缓存（如支持）。
- **成本可见**：按部门/任务/模型/日期；超支归因；异常告警。

### 14.4 评测

- **金标准任务集**：10–20 个典型任务（需求→PRD→实现→测试→评审），每次模型/提示词/运行时升级跑一遍。
- **检索评测**：40–60 条查询，Recall@10/nDCG@10/p95。
- **记忆评测**：给定事件流，检查抽取的准确率、召回率、冲突处理、注入相关性。
- **协作评测**：任务完成率、返工率、升级率、决策质量（人工评分）、串谋/虚假共识抽检。
- **安全评测**：提示注入、越权、密钥泄漏、危险命令、跨部门数据泄漏。
- **回归**：任何协议/状态机/记忆/检索变更都必须有回归用例。

### 14.5 可观测性与回放

- 结构化日志 + 关联 ID（message/task/turn/tool/decision）。
- 每次模型调用的 trace：上下文分区、token、模型、延迟、成本、工具、错误。
- 任务时间线：创建、分派、状态变化、评审、返工、验收、决策。
- 回放：从事件日志重建会话/任务；用于调试、审计、复盘。
- 仪表盘：运行状态、队列、预算、错误、检索、记忆。
- 导出：日志/指标/审计可导出；不锁定。

## 15. 演进路线

> 路线是方向性的，不是详细排期。每一版都必须「可用、可回滚、可验证」。

### 15.1 v0.0.1：可用闭环

**主题**：一个用户 + 一个助理 + 多个部门，跑通「目标 -> 组部门 -> 任务 -> 部门内讨论 -> 评审 -> 跨部门辩论 -> 验收 -> 记忆 -> 检索」。

**必须**：

- 本地对话平台：私聊、群聊、部门群聊、跨部门评审、用户观察者、Agent 管理入口。
- 助理自动创建、访谈、部门蓝图、用户 G1 审批。
- 产品部门 + 研发部门 + 测试部门（每部门主管 + 员工）；可选平台部门。
- 任务状态机（含 discussing）、分工视角、部门内讨论、跨部门辩论（每人≤5 条/总计≤15 条）、决策记录、人类闸门。
- 主管/助理四层记忆；员工 session + 选择性档案；记忆检查器；每 turn context.request 快照。
- 5 个工具：read_file、write_file、bash、web_search、view_change_history；共享 WriteTool + 时间线（默认 30 条/文件）。
- DeepSeek-only：默认 deepseek-flash；不接其他模型供应商、不接 DSH/ACP/Node。
- 审批、预算、暂停、紧急停止、备份/导出、崩溃恢复；DeepSeek API 不可用时平台可浏览/检索/导出。
- 至少一个端到端演示项目与金标准任务；15 个验收场景。

**阶段目标（发布标准以 requirements §4.4 为准）**：

- 15 个端到端验收场景通过。
- T1 安装->助理可对话 ≤10 分钟；T2 ->G1 批准 + 第一个任务创建 ≤30 分钟；T3 ->首个交付物被接受 ≤1 个工作日。
- 10 万条消息检索 p95 < 300ms；中文 2 字词可查。
- 群聊/部门内讨论/跨部门辩论可跑通；用户可查看所有群聊。
- 共享写工具串行、冲突检测、时间线可查；无静默覆盖。
- 记忆可查、可改、可删；决策可追溯；上下文快照可查。
- 无未记录的人类审批；无绕过平台的消息。

### 15.2 v0.1：多项目与组织记忆

**主题**：从「一个项目」到「多个项目/更多部门」。

- 多项目；部门模板；跨部门评审委员会；共享决策日志。
- 记忆图谱/关系检索；向量召回可选；记忆评测体系。
- 员工能力证据、部门负载与预算视图；更聪明的派单。
- 更丰富的讨论/裁决（盲评、独立裁判、红队）。
- 部门复盘、组织学习、模板复用。

### 15.3 v0.2：工具与部门模板

**主题**：在不变复杂的前提下增强生产力。

- 更多内置工具（按需、可审计）；工具权限与审批增强。
- 部门模板市场（本地）、项目模板、交接包模板。
- 模型成本/质量分析；提示词与上下文优化。
- 可选的外部工具接入（未定，不承诺）；不引入本地模型供应商。

### 15.4 v0.3：治理与安全增强

**主题**：从「个人」到「更可信的个人工作台」。

- 更强的审计、预算、权限、密钥管理。
- 备份/恢复/迁移/灾难恢复增强。
- 安全沙箱、依赖审计、供应链安全。

### 15.5 v1.0：AI 组织操作系统

**主题**：从「工具」到「组织基础设施」。

- 领域部门模板（软件、研究、写作、运营、咨询）。
- 组织级分析、学习、治理、合规。
- 开放导出/导入格式；可迁移的组织记忆。
- 跨项目协作（单用户前提）。

### 15.6 长期方向

- **个人 AI 组织**：一个人管理多个部门，助理成为真正的幕僚。
- **可验证的自主性**：从「人审批每一步」到「人设定边界、Agent 在边界内自治」。
- **组织记忆标准**：可导出、可迁移、可审计的记忆格式。
- **开放协作协议**：在用户明确需要时再评估跨组织协作，不提前承诺。


## 16. 成功指标

### 16.1 北极星

**每周被人类接受的可验证交付物数量**，同时满足：

- 质量达标（验收标准 + 证据）。
- 人类干预成本可接受（不是靠人盯出来的）。
- 成本可接受（token/时间）。
- 可追溯（决策/评审/产出物有记录）。

单纯「生成了多少代码/多少消息/多少 Agent」不是成功指标。

### 16.2 分层指标

| 层 | 指标 | 目标方向 |
|---|---|---|
| 价值 | T2 首次价值时间、T3 首个交付物周期 | 越短越好 |
| 交付 | 任务吞吐、周期时间、返工率、评审时长 | 吞吐↑、周期↓、返工↓ |
| 质量 | 缺陷逃逸率、证据覆盖率、决策可追溯率 | 越少/越高越好 |
| 协作 | 升级率、跨部门争议解决时长、人类打扰次数 | 升级合理、时长↓、打扰↓ |
| 记忆 | 记忆命中率、准确率、冲突率、注入相关性 | 命中↑、准确↑、冲突↓ |
| 检索 | p95、Recall@10、搜索后跳转率 | 延迟↓、召回↑ |
| 系统 | 消息丢失、崩溃恢复、索引延迟、Agent 成功率 | 0 丢失、快速恢复 |
| 成本 | 每任务/每交付物成本、预算超支率 | 可控、可预测 |
| 信任 | 审计覆盖、审批合规、抽检通过、推荐意愿 | 越高越好 |

### 16.3 反指标

- 消息数、Agent 数、token 数、自动化率本身不是成功。
- 「无人干预」若以质量/可追溯性为代价，是失败。
- 「辩论轮次多」不是认真，可能是没有证据/没有裁决。
- 「记忆条数多」不是聪明，可能是垃圾堆积。
- 「部门多」不是规模，可能是组织臃肿。

## 17. 非目标

v0.0.1 明确不做（后续版本再评估）：

1. **不是通用聊天机器人**：不以开放域闲聊为核心。
2. **不是全自动公司**：不承诺无人值守地运营业务。
3. **不替代人类判断**：目标、价值、风险、不可逆决策仍由人负责。
4. **不做移动端原生/桌面壳**：浏览器即客户端。
5. **不做 IDE**：不重复造编辑器/调试器；通过工具调用现有环境。
6. **不做 Slack 克隆**：不追求通用 IM 的所有功能。
7. **不做 Agent 市场/插件市场**（v0.0.1）：先证明核心闭环。
8. **不做跨组织 A2A/ACP 互操作**（v0.0.1）：内部协议先稳定。
9. **不做 E2EE/联邦/多机同步**：本地优先，先单机可靠。
10. **不做无限制 Shell/网络**：默认最小权限 + 审批。
11. **不做自我修改核心代码/权限**：Agent 不能改自己的治理规则。
12. **不做 24/7 无人值守**：默认人类在环；高风险需审批。
13. **不做模型训练/微调**：v0.0.1 只接 DeepSeek，默认 deepseek-flash；不做多供应商路由。
14. **不做全库加密**（v0.0.1）：明确磁盘未加密的取舍。
15. **不做逐条已读回执/typing/presence 落库**：界面状态不落库。
16. **不做三级以上线程/富文本编辑器**：Markdown + 两级线程足够。
17. **不做向量检索**（v0.0.1）：先结构化 + 全文；语义作为可选后续。
18. **不做跨部门自由群聊**：跨部门默认走结构化评审/决策；用户可临时开桥。
19. **不做「无限辩论」**：每人≤5 条、总计≤15 条；员工级超限由部门主管裁决，主管级/跨部门由助理整理后反馈用户。

## 18. 风险与开放问题

### 18.1 风险

| 风险 | 影响 | 可能性 | 缓解 |
|---|---|---|---|
| 模型能力不足/不稳定 | 交付质量差、返工多 | 中 | 金标准任务、评审、人工抽检；v0.0.1 固定 deepseek-flash |
| 成本失控 | 用户不敢用 | 中高 | 预算、路由、压缩、停止条件、成本可见 |
| 多 Agent 协作失效 | 漂移、重复、冲突 | 高 | 固定 SOP、角色卡、任务契约、DoR/DoD、独立验证 |
| 记忆污染/膨胀 | 长期错误、检索变差 | 中高 | 证据门槛、候选审核、额度、双时间、可删除 |
| 提示注入/越权 | 安全事故 | 中 | 指令层级、工具白名单、审批、沙箱、红队 |
| 本地 Web 漏洞 | 数据泄漏 | 中 | Origin/Host、Cookie、Token、默认 loopback |
| DeepSeek API 依赖 | 限流/故障/涨价 | 中高 | 超时/重试/预算/降级（只读/暂停）；平台可离线浏览/检索/导出 |
| 中文检索质量 | 搜不到、体验差 | 中 | 金标准查询、trigram+回退、评测、可换分词 |
| 跨平台沙箱差异 | Windows/macOS/Linux 行为不一致 | 中 | 抽象 + 平台测试 + 保守默认 |
| 产品复杂度过高 | 用户不会用 | 高 | 引导式 onboarding、默认模板、渐进披露、演示项目 |
| 人类被流程淹没 | 不愿用 | 中高 | 注意力预算、批量审批、助理过滤、只升级关键 |
| 数据丢失/损坏 | 信任崩塌 | 低但致命 | 先写后发、备份、恢复演练、索引重建 |
| 范围蔓延 | 版本延期 | 高 | 非目标清单、Exit criteria、每版砍功能 |
| 合规/隐私 | 企业不敢用 | 中 | 本地优先、导出、审计、脱敏、后续合规增强 |

### 18.2 开放决策

> v0.0.1 的具体选择（原生 Go/DeepSeek、共享写工具、审计/成本归属、群聊隔离、辩论 5/15、记忆写入）见 requirements §9.6；本表保留长期开放项。

| # | 决策 | 选项 | 建议 | 何时定 |
|---|---|---|---|---|
| 1 | 共享写工具锁粒度 | 单文件串行 / 全工作区串行 | **默认全工作区串行（v0.0.1）；后续可配置按文件并行；分支/提交/批量重构全局锁** | 需求评审 |
| 2 | 部门内讨论上限 | 3 条 / 5 条 / 不限 | **每人≤5 条、总计≤15 条** | 需求评审 |
| 3 | 用户观察者默认 | 全部群聊可见 / 仅加入后可见 | **全部群聊可见，默认不参与** | 需求评审 |
| 4 | 临时桥默认 | 默认关闭 / 默认开启 | **默认关闭；用户显式开通，带范围与到期** | 需求评审 |
| 5 | 默认部门模板 | 三部门 / 加平台 / PM 部门制 | **三部门交付（产品/研发/测试）** | 产品评审 |
| 6 | 记忆写入权 | 全自动 / 全人工 / 分层 | **低风险自动；决策/争议/敏感需部门主管或人类确认** | 需求评审 |
| 7 | 自适应提示词 | Agent 自主 / 仅提议 | **v0.0.1 默认仅提议**；显式开启低风险自动 + 版本/回滚 | 需求评审 |
| 8 | 双时间 | 首版全量 / 仅决策争议 | **决策/争议/能力强制双时间；其他 upsert + 快照** | 数据设计 |
| 9 | 检索方案 | 全文 / 全文+向量 / 图 | **v0.0.1 结构化 + 全文；向量作为可选后续** | 技术设计 |
| 10 | 消息检索是否含 Agent 轨迹 | 含 / 不含 | **不含**（审计可查，搜索不污染） | 产品评审 |
| 11 | 跨部门裁决权 | 部门主管 / 助理 / 人类 | **部门主管先裁决；主管间冲突交助理；助理再反馈用户** | 治理设计 |

| **对话平台** | Go 编写的本地平台：消息、群聊、部门/Agent 管理、检索、通知、审计 |
| **Agent 核心框架** | Go 编写的原生 agent loop：编排/记忆/任务/评审/工具 |
| **项目主管（Owner）** | 登录者、最终决策者 |
| **助理 Agent** | 人类的首席幕僚：澄清、划分部门、协调、注意力过滤、对用户接口 |
| **部门（Department）** | 组织单元；每个部门有部门主管 + 员工 |
| **部门主管（Department Lead）** | 本部门运营核心：分派、部门内讨论裁决、产出核对、跨部门对接 |
| **员工 Agent（Employee）** | 有固定分工视角的专家：页面/接口/数据流/测试等 |
| **分工视角（Perspective）** | 员工在任务中固定站在哪个开发角度讨论与实现 |
| **群聊** | 多 Agent + 用户的会话；部门群聊/项目群聊/临时讨论组 |
| **用户观察者** | 用户可查看所有群聊，默认不参与部门讨论 |
| **临时桥（Bridge）** | 用户临时开通的直连路由，带范围与到期 |
| **项目章程** | 项目目标、部门、角色、权限、预算、协作规则 |
| **任务（Task）** | 有目标、验收标准、owner、状态、视角、证据的工作单元 |
| **产出物（Artifact）** | 不可变版本的交付物：PRD、方案、代码、测试报告等 |
| **评审（Review）** | 对某个产出物版本的挑战、证据与裁决 |
| **部门内讨论** | 员工从各自开发便利出发讨论；部门主管拍板全局取舍 |
| **跨部门辩论** | 部门主管代表部门的结构化分歧解决：立场、证据、轮次、裁决 |
| **决策记录（Decision Record）** | ADR 式的不可变决策：背景、选项、决定、理由、异议 |
| **升级（Escalation）** | 把无法在本地解决的问题按 L0–L4 上交 |
| **会话（Session）** | Agent 的事件日志 + 投影 + 压缩检查点 |
| **短期上下文** | 模型本次调用看到的工作窗口（L0+L1） |
| **触发式记忆** | 事件触发的抽取管道，把过程变成候选事实（L2） |
| **档案记忆** | 跨会话的结构化长期知识（L3） |
| **自适应提示词 / 管理手册** | Agent 可维护的判断规则，注入 system 稳定前缀（L4） |
| **候选记忆** | 尚未晋升为档案的事实提案 |
| **双时间** | 事实的生效时间与失效时间；用于决策/争议审计 |
| **视图即权限** | 不同角色注入不同记忆视图，从结构上避免越权 |
| **共享写工具（WriteTool）** | 所有 Agent 共用的写文件通道：写事件、串行、冲突检测 |
| **变更时间线** | 每个文件最近 N 次变更（默认 30）；模仿 VSCode Timeline |
| **DoR / DoD** | Definition of Ready / Definition of Done |
| **WIP** | Work in Progress，在制品数量限制 |
| **SSE** | Server-Sent Events，服务器推送事件 |
| **seq** | workspace 内单调递增的消息/事件序号，全序权威 |
| **at-least-once** | 至少一次投递；消费端幂等 |
