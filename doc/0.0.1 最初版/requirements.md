## 0. 一页纸摘要

### 0.1 最初版是什么

v0.0.1 不是「多 Agent 平台的演示」，而是一个**可以每天使用的纵向切片（vertical slice）**：

> **一个用户，一个助理，多个部门，把一个真实需求从想法做到验收。**

它必须同时证明三件事：

1. **能开始**：新用户能在 30 分钟内完成安装、认识助理、组建部门、发出第一个任务。
2. **能协作**：任务、产出物、评审、返工、部门内讨论、跨部门挑战、决策记录、人类闸门形成闭环。
3. **能信任**：本地存储、消息不丢、可检索、可审计、可暂停、记忆可查可改可删。

### 0.2 五个必须做成的能力

| # | 能力 | 一句话验收 |
|---|---|---|
| 1 | 本地对话平台 | 人和 Agent 在同一工作台沟通；所有消息落库、可检索、重启不丢 |
| 2 | 助理 Agent | 首登自动获得；能澄清目标、提出项目/部门蓝图、管理主管、过滤注意力 |
| 3 | 完整部门 | 产品 / 研发 / 测试部门，每部门主管 + 员工；有群聊、任务板、产出物、评审、返工 |
| 4 | 跨部门协作 | 至少两个部门；部门内讨论 + 跨部门结构化挑战/辩论、升级用户、决策记录 |
| 5 | 四层记忆 | 部门主管/助理：短期上下文 + 触发式记忆 + 档案记忆 + 自适应提示词；员工：session + 选择性档案 |

### 0.3 明确不做

v0.0.1 不做：公网 SaaS、移动端、Agent 市场、跨组织 A2A、无限自主运行、无限制 Shell、全库加密、向量检索、动态自由组队、跨部门自由群聊、DSH/ACP/外部 Agent 运行时、多模型供应商。

### 0.4 成功的一句话

> **用户愿意把第二个真实需求继续交给这个组织，而不是回到「自己写提示词 + 复制粘贴」。**

## 1. 背景与问题

### 1.1 单 Agent 不够用

编码 Agent 已经能读代码、改代码、跑测试，但真实工作不是「一个会话里完成一个函数」：

- 需求需要澄清，范围需要砍，验收标准需要写。
- 实现需要方案、接口、测试、评审，不是一次生成。
- 项目背景、历史决策、踩过的坑需要跨会话保留。
- 一个人既当产品又当开发又当测试，缺少真正的视角冲突。

### 1.2 工具是碎的

聊天工具、任务板、代码托管、文档、Agent 会话各自为政。人被迫做「人肉总线」：把需求从聊天复制到任务板，把代码链接贴回聊天，把测试结果再复述一遍。

### 1.3 多 Agent 演示不能日常用

现有框架能演示「产品经理 + 程序员 + 测试」的对话，但往往缺少：

- 持久消息与任务状态；
- 产出物版本与评审记录；
- 人类审批、预算、暂停；
- 长期记忆与可检索性；
- 失败恢复与审计。

### 1.4 机会

DeepSeek API 与本地算力已经足够；事件日志、全文检索、本地数据库、Agent 工具链都已成熟。缺的不是「更聪明的模型」，而是**把一个组织运行起来的工作环境**。

## 2. 产品定位与目标

### 2.1 一句话定位

**Lignting Agents 是一个本地优先的 AI 组织工作台：用户作为项目主管，拥有一个助理 Agent，按需组建产品、研发、测试等部门；每个部门由部门主管管理员工，在群聊、任务、产出物、评审、部门内讨论与跨部门辩论中完成真实工作。**

### 2.2 核心价值主张

1. **组织，而不是聊天框**：部门、角色、任务、产出、评审、决策在同一个工作空间。
2. **越用越懂你**：四层记忆保留目标、偏好、决策、教训；员工只沉淀重要事实。
3. **质量来自结构性冲突**：产品挑战需求、测试挑战实现、其他部门挑战接口；部门内讨论 + 跨部门辩论，有格式、有轮次、有证据、有裁决。
4. **数据与权力在你手里**：本地、可导出、可审计；Agent 的权限、预算、记忆都可管。

### 2.3 什么时候不该用

Lignting 不是所有任务的默认答案。以下场景优先用更简单的方案：

- **单轮问答、小脚本、一次性查询**：直接用聊天/编码 Agent 更快，不必组队。
- **任务边界清晰、无需评审**：一个 Agent + 人工检查即可，部门与流程是额外成本。
- **完全不能接受内容发给 DeepSeek API**：不要用；本产品默认会把推理所需内容发给 DeepSeek。
- **需要 24/7 无人值守、自动发布/付款**：v0.0.1 不承诺；人类闸门是产品前提。
- **大型企业多租户/合规/SSO 场景**：v0.0.1 单用户本地版不适用。
- **已经有成熟的人类组织与流程**：先算增量收益；如果「Agent 部门 + 审批」的成本高于直接沟通，就不要上。

判断标准：**部门协作带来的质量/连续性收益，是否大于组织、审批与 token 成本。** 如果答案是否定的，直接用单 Agent。

### 2.4 v0.0.1 的产品原则

| 原则 | 含义 | 反例 |
|---|---|---|
| **可用优先** | 先跑通一条真实闭环，再谈规模 | 做十个半成品功能 |
| **人类在环** | 关键节点必须有人类闸门 | 全自动组队、自动合并、自动发布 |
| **结构优于闲聊** | 任务/产出/评审/决策是对象，聊天只是传播层 | 所有状态都在聊天里 |
| **证据优先** | 验收看证据，不看「我觉得完成了」 | 测试报告没有日志 |
| **默认最小权限** | Agent 只能做被授权的事 | 默认给全盘 Shell |
| **本地优先** | 数据、检索、界面都在本机 | 默认上传云端 |
| **记忆克制** | 只记可复用、可验证的事实 | 把整段聊天写进档案 |
| **渐进披露** | 新用户先看到简单流程，复杂能力按需展开 | 首屏堆满配置 |

## 3. 目标用户与核心场景

### 3.1 主用户画像

**「阿哲」— 技术型独立开发者 / 小项目组 Tech Lead**

- 有 5–10 年开发经验，自己维护一个项目或带 2–3 人小项目组。
- 已经在用编码 Agent，但觉得「每次都要重新解释背景」「代码没人 review」「测试靠自觉」。
- 希望有一个「虚拟产品 + 研发 + 测试」部门组织，但不想搭一整套云服务。
- 在意数据、成本、可控性；愿意花 30 分钟配置，但不愿意学复杂框架。

**他的原话**：

> 「我不需要另一个聊天机器人。我需要一个能接住需求、拆任务、写代码、做测试、还能跟我解释为什么这么做的组织。最好都在我电脑上。」

### 3.2 次要用户

| 用户 | 场景 | v0.0.1 支持程度 |
|---|---|---|
| 研究者 / 写作者 | 多角色调研、写作、事实核查 | 可用通用部门模板，非重点优化 |
| 个人知识工作者 | 长期项目、日常助理 | 助理 + 记忆 + 检索可用，部门能力可选 |

### 3.3 非目标用户

- 想要一个通用聊天机器人、不愿意管理 Agent 的用户。
- 希望「一句话全自动上线」的用户。
- 不愿意提供 DeepSeek API Key 的用户。

### 3.4 核心场景

| 场景 | 描述 | 最初版优先级 |
|---|---|---|
| **S1 需求交付** | 从一句需求到 PRD、实现、测试、评审、验收 | P0 |
| **S2 跨部门挑战** | 平台部门挑战研发部门的接口/质量/范围，形成决策 | P0 |
| **S3 单次问答** | 不需要组队的问题，助理直接回答并引用 | P0 |
| **S4 记忆连续性** | 新会话记得上次决策、偏好、教训 | P0 |
| **S5 检索与审计** | 找到某条消息/决策/产出物，追溯为什么 | P0 |
| **S6 失败恢复** | 模型超时/进程崩溃/断线后继续工作 | P0 |
| **S7 多项目并行** | 同时推进多个项目 | P2（v0.0.1 单项目） |

## 4. 版本目标与成功标准

### 4.1 版本目标

**让一个技术型用户，在本地完成「助理划分部门 → 真实需求交付 → 部门内讨论 → 跨部门挑战 → 记忆沉淀 → 检索复盘」的完整闭环，并愿意继续使用。**

### 4.2 「可用」的定义

v0.0.1 的「可用」不是「能启动」，而是：

1. 用户知道下一步该做什么（引导、默认值、示例）。
2. 部门能接住一个真实需求，而不是只回答演示问题。
3. 出错时用户知道发生了什么、能恢复、不丢数据。
4. 用户能检查 Agent 做了什么、为什么这么做。
5. 成本可预期、可暂停、可追加预算。

### 4.3 成功指标（v0.0.1）

| 指标 | 目标 | 衡量方式 |
|---|---|---|
| T1 安装 → 助理可对话 | ≤ 10 分钟 | 首次向导完成 → 助理首次有效回复 |
| T2 → G1 批准 + 第一个任务创建 | ≤ 30 分钟 | 安装完成 → 部门 active + 首个任务 ready |
| T3 → 首个交付物被人类接受 | ≤ 1 个工作日（示例需求） | 首个任务创建 → G3 验收 |
| 端到端演示 | 100% 通过 | 金标准场景（见 14） |
| 消息丢失 | 0 | 崩溃/重启测试 |
| 检索 p95 | ≤ 300ms（10 万条） | 基准测试 |
| 中文 2 字检索 | 可命中 | 金标准查询集 |
| 未记录审批 | 0 | 审计抽查 |
| 记忆可纠正 | 100% 可编辑/删除 | 记忆检查器测试 |
| 跨部门挑战 | 至少 1 次产生决策记录 | 验收场景 |
| T3 交付物单任务成本 | ≤ 预算上限（抽样 ≥10 个任务） | 成本账本 |
| 每交付物人类干预次数 | ≤ 5 次（基线，可调） | 审计/决策记录 |

**反指标（不得用其证明成功）**：消息数、Agent 数、token 数、无人干预率、辩论轮次、记忆条数、部门数。任一反指标异常升高时触发「停工复盘」，而不是继续加 Agent。

### 4.4 Exit Criteria（版本可发布）

- [ ] 新用户按 Quickstart 完成 T1/T2（安装、组队、首个任务创建），无需开发者协助；T3 用示例需求验证。
- [ ] 15 个端到端验收场景全部通过（见 14）。
- [ ] 无绕过平台写入的人类可见消息；所有消息可在平台检索。
- [ ] 消息、任务、评审、决策、记忆在重启后完整恢复。
- [ ] 检索金标准集 Recall@10 ≥ 0.8，p95 ≤ 300ms。
- [ ] 所有高风险工具动作都有审批记录；无未记录的人类批准。
- [ ] 至少一次跨部门挑战走完「立场 → 回应 → 裁决 → 决策记录」。
- [ ] 记忆可查看、编辑、删除；自适应提示词有版本与回滚。
- [ ] 备份/恢复演练通过；导出格式可读。
- [ ] 安全基线检查通过（loopback、Origin、Token、脱敏、审计）。
- [ ] 文档齐全：Quickstart、概念、FAQ、故障排查、演示脚本。
- [ ] Beta：至少 3 名真实用户完成 T1/T2，2 名完成 T3；有验证记录与改进清单。

## 5. 范围

### 5.1 P0（必须做，不做就不能发布）

| 领域 | P0 内容 |
|---|---|
| 启动与引导 | 本地启动、首次向导、助理创建、10–15 分钟引导、DeepSeek API 不可用降级 |
| 对话平台 | 助理私聊、群聊、部门群聊、跨部门评审、线程、提及、附件、流式、停止、Agent 管理入口 |
| 消息与检索 | 全量落库、重启恢复、中文/英文全文检索、过滤、跳转、索引重建 |
| 助理 | 澄清、意图卡、项目/部门蓝图、provisioning、简报、决策收件箱、记忆策展 |
| 部门 | 产品/研发/测试部门（每部门主管 + 员工）+ 可选平台部门、角色卡、分工视角、暂停 |
| 任务 | 状态机（含 discussing）、DoR/DoD、依赖、owner/reviewer/approver、WIP、时间线、验收核对表 |
| 产出物 | 注册表、不可变版本、哈希、任务/评审/决策关联、查看/对比 |
| 评审 | 挑战单、verdict、返工、作者≠评审者、测试质量门、人类抽检 |
| 跨部门 | 决策包、每人≤5 条/总提交≤15、时间盒、死锁检测、升级、决策记录 |
| 部门内讨论 | 分工视角、讨论轮次、主管裁决、讨论记录 |
| 人类控制 | 3 个人类闸门、不可逆审批、预算、暂停/紧急停止 |
| 记忆 | 四层（部门主管/助理）、员工 session + 候选档案、检查器、待审队列 |
| 文件写入 | 共享 WriteTool、默认全局串行、冲突检测、变更时间线（默认 30 条/文件） |
| 可靠性 | 先写后发、崩溃恢复、幂等、备份/恢复、导出、定时与到期 |
| 安全 | 本地访问、Origin/Host、Agent Token、工具权限、密钥脱敏、审计 |
| 可观测 | Agent 状态、成本视图、审计日志、上下文快照/回放；任务指标为 P1 |

**P0 分三档，避免「P0 无限膨胀」**：

| 档 | 含义 | 主要内容 |
|---|---|---|
| **P0a 闭环** | 不做就没有可演示的端到端 | 安装/助理/组部门/群聊/任务/产出物/评审/部门内讨论/跨部门辩论/决策/3 个人类闸门/记忆最小闭环/检索基础/共享写工具 |
| **P0b 信任** | 不做就不敢用 | 先写后发、崩溃恢复、审批、审计、备份、成本上限、权限隔离 |
| **P0c 体验** | 可降级、可后补 | 组织负载增强、任务板保存视图、定时简报、增强 diff、命令面板、可访问性 |

> P0c 的具体条目可以降为 P1，但必须在 §5.2 与本表保持一致；P0a/P0b 不允许降级。

### 5.2 P1（应该做，可降级）

- 定时简报（P0 只做按需简报；定时生成为 P1）。
- 任务板保存视图（P0 支持过滤/排序；保存视图为 P1）。
- 产出物行级评论/增强 diff（P0 支持基础查看与评论）。
- 评审 SLA 提醒。
- 高级成本告警/预测（基础 80%/100% 告警为 P0）。
- 命令面板/快捷键。
- 保存搜索/最近搜索。
- 记忆待审队列的批量操作。
- 部门能力矩阵/负载历史（P0 只做基础组织图/状态/基础负载）。
- 审计导出增强（基础导出为 P0）。
- 示例项目一键重置。

### 5.3 P2（v0.0.1 不做）

- 公网 SaaS、SSO。
- 移动端、桌面壳。
- Agent 市场、插件市场。
- 跨组织 A2A、AgentCard。
- 向量检索、图数据库。
- 动态自由组队、Agent 自荐/竞聘。
- 跨部门自由群聊/无限辩论（跨部门默认走主管+结构化评审）。
- 自动合并/自动发布/自动付款。
- 全库加密、E2EE。
- 跨设备同步、云备份。
- 模型训练/微调。
- 多项目并行（v0.0.1 单项目）。
- 外部系统深度集成（Jira、Slack、GitHub 等，先做文件/Git/Web 基础）。

### 5.4 范围护栏

- **单用户 owner**：v0.0.1 只支持一个登录者；Agent 数量可多。
- **单项目**：一个工作区一个项目；部门可多，项目一个。
- **单机**：默认只在本机；远程访问靠 SSH/覆盖网络，不做公网部署方案。
- **真实闭环优先**：任何功能如果不能让「需求 → 交付 → 验收」更顺，就砍。
- **可降级**：P1 功能缺失时，核心闭环仍能跑通；发布前用 P1-off 配置跑一遍最小闭环，证明 P0 不依赖 P1。

## 6. 角色与组织

### 6.1 角色

| 角色 | 身份 | 使命 | 决策权 | 不能做什么 |
|---|---|---|---|---|
| **项目主管（用户）** | 登录者 | 目标、预算、风险、最终裁决 | 最终决定权 | — |
| **助理 Agent** | 每用户一个 | 澄清、划分部门、协调、注意力过滤、对用户接口 | 建议/主持/执行；无最终裁决 | 代替用户批准预算/章程；改自己权限；删除审计；绕过部门主管直接派活（紧急除外） |
| **PM 部门（可选）** | 一个部门 | 全局产品/计划/优先级；可由助理委托 | 全局产品判断（经助理/用户确认） | 直接指挥其他部门员工；绕过助理找用户 |
| **部门主管 Agent** | 每部门一个 | 本部门拆解、分派、部门内讨论裁决、产出核对、跨部门对接 | 本部门内调度；部门内讨论裁决 | 改用户目标/项目预算/部门结构；批准自己产出；绕过测试质量门；直接找用户 |
| **员工 Agent** | 部门成员 | 按固定视角执行：页面/接口/数据流/测试等 | 本视角内的实现建议 | 替全局做决定；直接联系其他部门/用户 |
| **系统** | 平台+核心 | 持久化、路由、审计、预算、恢复 | — | — |

**术语说明**：用户是「项目主管」；每个部门有自己的「部门主管 Agent」；员工是部门成员。没有「一个主管统管所有部门」的角色；全局职责由助理或独立 PM 部门承担。

### 6.2 权限矩阵

| 事项 | 项目主管 | 助理 | 部门主管 | 员工 |
|---|---|---|---|---|
| 设定目标/优先级 | **A** | R | C | I |
| 批准项目章程/预算 | **A** | R（准备） | C | I |
| 创建/解散部门 | **A** | R | C | I |
| 增减部门成员/改角色 | **A** | R | R（提议） | I |
| 部门内任务拆解/分派 | C（可干预） | C | **A/R** | C |
| 跨部门任务协调 | C | **A/R** | R（对接） | I |
| 技术方案（本部门） | I | I | A | **R** |
| 质量门/验收 | **A**（G3 最终） | I | R（核对/部门内小任务） | R（测试质量判定） |
| 部门内讨论裁决 | I | I | **A** | C |
| 跨部门争议 | A（不可逆/高风险） | R（主持） | C | I |
| 组织级记忆写入 | A | **A/R** | R（提议） | R（候选） |
| 暂停/终止 Agent | **A** | R（可紧急暂停，通知人类） | R（本部门内） | I |
| 不可逆工具动作 | **A** | I | R（申请） | R（申请） |

A = 最终负责；R = 执行；C = 被咨询；I = 被通知。

### 6.3 人类闸门与验收权责

v0.0.1 设 3 个必须的人类闸门：

| 闸门 | 时机 | 人类要确认什么 | 可否委托 |
|---|---|---|---|
| **G1 项目/部门蓝图** | 组部门前 | 目标、部门、角色、人数、预算、节奏、风险；蓝图即章程草案 | 否 |
| **G2 技术方案/范围** | 高风险需求开工前 | 方案、接口、依赖、风险、范围变更 | 低风险任务可委托部门主管 |
| **G3 最终验收** | 功能/里程碑/高风险交付前 | 验收核对表、证据、遗留风险、是否交付 | 否 |

**验收权责**：人类 G3 = 最终验收人；部门主管 = 逐条核对并提交验收核对表；测试 = 质量判定。小任务可由部门主管在授权范围内验收；功能/里程碑/高风险必须 G3。

**高风险分类表**（命中任一即高风险）：

| 维度 | 高风险条件 | 默认处理 |
|---|---|---|
| 数据 | 客户数据、密钥、隐私、生产数据 | G2 + 双钥匙 |
| 可逆性 | 不可回滚、force push、删除、对外发布、付款 | 人类审批 + 双钥匙 |
| 影响范围 | 跨部门接口、对外承诺、第三方系统、公开发布 | G2 + 平台部门评审 |
| 成本 | 单任务/单次动作超过人类阈值 | 人类审批 |
| 合规/伦理 | 法律、隐私、安全、歧视/误导风险 | 人类审批 |

**审批默认值**：

- 实时打扰 ≤3 次/天（可配置）；只有阻塞/不可逆/高风险可打断。
- 审批 TTL 默认 24h；到期标记阻塞 + 提醒，不自动执行。
- 用户 24h 无响应 -> 部门降级为只读/暂停接新任务 + 日报（可配置）。
- 批量审批不适用于双钥匙/不可逆动作；授权给助理/部门主管必须有范围与到期。

外加不可逆动作审批（删除、force push、对外发布、付款、权限变更）。

### 6.4 默认部门模板

v0.0.1 验收使用「三部门交付」：

| 部门 | 角色 | 职责 |
|---|---|---|
| **产品部门** | 1 主管 + 1 产品员工 | 需求、PRD、验收标准、范围 |
| **研发部门** | 1 主管 + 员工（页面/接口/数据流） | 方案、实现、联调、自测 |
| **测试部门** | 1 主管 + 1 测试员工 | 测试计划、用例、证据、质量门 |

可选加**平台部门**（主管 + 架构评审）制造跨部门挑战；可选 **PM 部门**承担全局产品判断。

### 6.5 术语

| 术语 | 含义 |
|---|---|
| 项目主管 | 登录用户、最终决策者 |
| 助理 Agent | 全局幕僚与用户接口 |
| PM 部门 | 可选；承担全局产品/计划判断 |
| 部门 | 组织单元；有部门主管 + 员工 |
| 部门主管 | 本部门运营核心 |
| 员工 | 有固定分工视角的专家 |
| 分工视角 | 页面/接口/数据流/测试等；讨论时从自己开发便利出发 |
| 部门内讨论 | 员工各自陈述视角；主管裁决全局取舍 |
| 跨部门辩论 | 部门主管代表部门；助理主持；5/15 上限 |
| 共享写工具 | 所有 Agent 共用写文件通道；串行 + 时间线 |
| 变更时间线 | 每个文件最近 N 次改动（默认 30） |
| 用户观察者 | 用户可看所有群聊，默认不参与 |
| 临时桥 | 用户临时开通的直连路由，带范围与到期 |

### 6.6 沟通隔离与用户观察者

- 部门内：员工之间可自由群聊/讨论。
- 跨部门：员工不能直接找其他部门员工；由部门主管对部门主管对接。
- 部门主管 ↔ 用户：默认必须经助理转接；主管不能直接私聊用户。
- 用户观察者：用户可查看所有群聊消息（部门群聊/跨部门群聊/临时组），默认不参与；加入后可发言。
- 临时桥：用户可临时开通跨部门直连/主管直连用户/两个 Agent 直连，必须指定范围与到期；到期自动关闭并通知；桥接消息留审计。
- 隔离只限制 Agent 的默认沟通路由，不限制用户读取；用户始终可查看全部群聊记录。


## 7. 用户旅程

### 7.1 J1：第一次启动（T1 + T2，≤30 分钟）

1. 用户运行一个命令/双击启动，浏览器打开本地地址。
2. 首次向导：数据目录、DeepSeek API Key、预算、称呼。
3. 系统创建助理 Agent，私聊自我介绍：能做什么、不做什么、如何暂停。
4. 助理用 5–8 分钟做引导：解释「你是项目主管、我是幕僚、部门主管管员工、员工有分工视角」。
5. 助理生成项目意图卡，请用户确认。
6. 助理提出项目/部门蓝图；用户批准（G1）。
7. 系统 provision 产品/研发/测试部门；各部门主管 kickoff；用户看到群聊、任务板与第一个任务。
8. 引导结束，用户知道下一步：把需求发给助理，或进群聊围观。

**成功判据**：T1/T2 内完成；助理未在确认前创建部门；所有配置可修改。T3 见 J3。

### 7.2 J2：组建部门

1. 用户说「我想做一个 X」。
2. 助理问：目标用户、必须有的功能、明确不做、期限、预算、质量要求。
3. 助理提出项目蓝图 + 部门蓝图：产品/研发/测试部门，各几个主管/员工，分工视角、接口、预算、节奏。
4. 用户改人数/角色/预算，批准（G1）。
5. 系统创建部门、主管、员工、部门群聊、任务板、产出物空间、记忆命名空间。
6. 各部门主管 kickoff；助理做项目级 kickoff。

**失败处理**：provisioning 失败不能留半个部门；可重试/回滚；用户看到明确错误。

### 7.3 J3：需求交付与部门内讨论

1. 用户把需求发给助理/产品部门。
2. 产品部门写 PRD 与验收标准；研发/测试部门主管参与评审。
3. 按高风险分类表判断；命中高风险时用户 G2。
4. 研发部门主管拆任务，写明每个员工的分工视角（页面/接口/数据流）。
5. 员工先确认视角与计划；有分歧进入部门内讨论；主管裁决后实现。
6. 测试部门写用例/跑测试；同部门/跨部门评审提交挑战单；研发返工；重新提交。
7. 部门主管逐条填写验收核对表；用户 G3 验收。
8. 任务完成；产出物归档；记忆候选提交；文件写入进入时间线。

**成功判据**：任务状态合法；作者≠评审者；每条验收标准有证据；缺证据时 G3 不可提交；讨论有轮次记录。

### 7.4 J4：跨部门挑战

1. 平台/测试部门发现研发部门的接口/质量/安全问题，发起挑战单。
2. 双方部门主管在跨部门评审群聊提交决策包（stance/现状/提案/影响/evidence_ids/替代方案）。
3. 助理主持；每人≤5 条、总计≤15 条；超限或死锁 -> 助理整理给用户。
4. 用户/领域 owner 裁决；写决策记录；更新任务/产出物。
5. 用户可搜索挑战、辩论、决策的完整链路；所有群聊用户可见。

**成功判据**：挑战有证据；5/15 上限生效；决策可追溯；异议保留；主管间争论最终反馈用户。

### 7.5 J5：记忆回忆与纠正

1. 一周后，用户问「上次为什么没上 GraphQL？」。
2. 助理检索决策记录、辩论、任务，给出答案与来源链接。
3. 用户发现一条偏好过时，打开记忆检查器修改。
4. 助理下一轮使用新版本；旧版本保留。
5. 用户删除错误记忆；删除后不再注入。

**成功判据**：回答有来源；修改立即生效；删除可验证；员工不能读不该读的记忆。

### 7.6 J6：检索、群聊与审计

1. 用户搜索「登录 限流」。
2. 结果按部门/群聊/会话聚合，支持部门/作者/时间/类型过滤；片段高亮。
3. 点击跳到原消息/任务/决策；可继续看上下文。
4. 用户打开任意部门群聊围观；也可 @某个 Agent 发言。
5. 用户打开审计，看到某次工具调用/写文件是谁批准的；导出记录。

**成功判据**：中文 2 字可查；删除消息搜不到；权限过滤不泄漏；p95 达标；用户可查看所有群聊。

### 7.7 J7：故障与恢复

1. DeepSeek API 超时/限流；Agent 显示失败与重试；用户可暂停。
2. 进程崩溃；重启后消息、任务、评审、记忆、文件变更时间线恢复；未完成 turn 标记中断。
3. 工具执行到一半崩溃；系统标记「结果未知」，不自动重试有副作用的操作。
4. 用户从备份恢复；索引重建；数据一致。
5. 用户看到故障报告与下一步。

**成功判据**：不丢已确认消息；不重复副作用；恢复有明确状态；DeepSeek API 不可用时平台可浏览/检索/导出。

### 7.8 J8：并发写入与时间线

1. 两个员工同时对同一文件提交写事件。
2. 第一个写入被消费前，第二个写入被拒绝/排队；第二个 Agent 收到冲突提示，重新读取/变基。
3. 写入成功后，view_change_history 显示最近变更（Agent、diff、任务、分支、commit）。
4. 用户切分支/提交；时间线把提交前的多次改动合并为 commit 组；每个文件保留最近 30 条（可配置）。

**成功判据**：无静默覆盖；冲突可恢复；时间线可查；提交/分支事件被记录。


## 8. 功能需求

> 优先级：**P0** = v0.0.1 必须；**P1** = 应做，可降级；**P2** = 本版不做。  
> 每条需求的「验收」是产品行为判据，不是实现方案。

### 8.1 A. 启动与首次使用

#### FR-ONB-01 本地启动与访问（P0）

系统应支持用户在本机通过一个明确入口启动全部核心服务，并在浏览器中打开工作台；默认只允许本机访问。

**验收**：

- 用户按 Quickstart 一条命令/一次双击即可启动；启动后打印可点击的本地地址。
- 默认不监听公网地址；局域网/公网访问需要用户显式配置，并有风险提示。
- 启动失败时给出可读原因（端口占用、数据目录不可写、模型配置缺失等）与下一步建议。
- 启动不依赖外部数据库/搜索引擎服务。

#### FR-ONB-02 首次向导（P0）

首次启动应引导用户完成最小配置：数据目录、DeepSeek API Key、预算上限、称呼/语言；v0.0.1 只接 DeepSeek。

**验收**：

- 必填项校验清晰；密钥输入不明文回显；保存后不可读回明文。
- 预算可设置日/月上限；允许稍后修改；提供「试用/标准」两档默认值与参考每任务成本区间，避免让新用户凭空填数。
- 支持「先跳过组部门，只和助理聊」；但创建部门前必须补齐必要配置。
- 配置失败不产生半初始化状态；可重试/重置。

#### FR-ONB-03 助理自动创建（P0）

首次配置完成后，系统应自动创建一个助理 Agent，并在私聊中主动介绍自己。

**验收**：

- 助理自我介绍包含：能做什么、不做什么、如何暂停、如何查看它的行为。
- 助理不主动创建部门、不主动调用高风险工具；先询问用户目标。
- 用户可重命名助理、查看角色卡、暂停/恢复。
- 同一用户只有一个默认助理；重复启动不重复创建。

#### FR-ONB-04 引导式首课（P0）

系统应提供一个 10–15 分钟的交互式引导，让用户理解核心心智模型并完成一次最小闭环。

**验收**：

- 引导覆盖：项目主管 / 助理 / 部门主管 / 员工 / 分工视角；对话、群聊、任务、产出物、评审、记忆、检索。
- 引导可使用示例项目或用户自己的仓库；可跳过、可重来；演示 workspace 与真实 workspace 隔离，演示数据不得进入真实记忆/组织记忆。
- 引导结束时用户至少完成：一次助理问答、一次项目/部门蓝图审批、一个任务创建。
- 引导不产生无法清理的垃圾数据；提供「重置演示数据」。

#### FR-ONB-05 帮助、诊断与重置（P1）

系统应提供应用内帮助、故障诊断与安全重置能力。

**验收**：

- 帮助包含 Quickstart、概念、FAQ、常见错误、隐私说明。
- 诊断包包含版本、配置摘要（脱敏）、日志、最近错误；用户可导出。
- 重置支持：仅重置引导、清空演示数据、完整重置（需二次确认 + 导出提醒）。

#### FR-ONB-06 DeepSeek API / 工具不可用时的降级（P0）

当 DeepSeek API 不可用、限流或工具执行不可用时，平台仍应可启动、浏览、搜索、导出，并给出修复指引；不能产生半个部门或静默失败。

**验收**：

- 平台本体可启动；助理可解释「DeepSeek API/工具不可用」并给出检测/修复步骤。
- 历史消息/任务/产出物/记忆可读可搜可导出；新 Agent 任务暂停并提示。
- 不产生半 provisioning 的部门/员工/频道；重试幂等。
- DeepSeek API 恢复后可继续未完成任务；不重复副作用。
- 工具执行失败/超时可重试/升级；不自动执行有副作用操作。
- 主进程崩溃/重启的恢复范围必须可测试。

### 8.2 B. 对话平台

#### FR-CHAT-01 会话结构（P0）

平台应提供以下会话类型：助理私聊、项目群聊、部门群聊、跨部门评审群聊、临时讨论组、决策日志、任务线程、产出物讨论线程。

**验收**：

- 用户可在左侧导航快速切换；未读/提及有清晰标记。
- 左侧导航包含「收件箱（待决定/稍后/FYI）」「审批中心（等待中/已处理/超时）」「Agent 管理」。
- 通知是推送，收件箱是持久对象；同一升级包只有一个收件箱条目。
- 部门群聊默认只对部门成员、部门主管、助理可见；跨部门群聊只允许结构化评审/决策消息。
- 用户可查看所有群聊（观察者），默认不参与；加入后可发言。
- 决策日志为只读流，按时间倒序，可搜索、可跳转。
- 任务/产出物创建时自动生成关联线程，不需要用户手动建群。

#### FR-CHAT-02 消息、线程、提及、引用与附件（P0）

用户与 Agent 应能发送文本/Markdown 消息，支持两级线程、@提及、引用、附件与代码块。

**验收**：

- 消息发送有即时反馈；失败可重试；重复发送不产生重复消息。
- 线程最多两级；从线程可跳回主频道上下文。
- @提及会通知对应人或 Agent；Agent 被 @ 时按路由规则处理。
- 附件支持常见图片/文档/压缩包；有大小/解压上限与类型限制；下载需权限校验，强制 `attachment` + `nosniff`，SVG/HTML 不同源渲染。
- 消息可编辑/删除（受权限与时间限制）；删除留审计墓碑，索引同步移除；不静默改写历史。
- 代码块/表格/Markdown 渲染正确；不执行消息中的脚本。

#### FR-CHAT-03 流式回复、停止与重试（P0）

Agent 回复应流式呈现；用户可停止、重试、查看工具调用状态。

**验收**：

- 首 token 到达后逐步显示，不要求整段完成才展示。
- 停止后保留已生成内容，并标记「已停止」；不产生半条重复消息。
- 重试创建新的回复，不覆盖历史；用户可对比。
- 工具调用显示为卡片：进行中/成功/失败/等待审批；可展开查看摘要。
- 模型/工具失败时显示可读错误、重试入口、是否产生副作用。

#### FR-CHAT-04 结构化消息卡片（P0）

任务、评审、决策、审批、产出物应以结构化卡片呈现，并支持在卡片上执行关键动作。

**验收**：

- 任务卡：标题、状态、owner、验收标准、截止、关联产出物；可认领/提交/验收（按权限）。
- 评审卡：挑战级别、证据、影响、建议；可通过/返工/升级（按权限）。
- 决策卡：背景、选项、决定、理由、异议；可跳转关联任务/产出物。
- 审批卡：动作、风险、范围（一次/会话/始终）、批准/拒绝；拒绝需理由。
- 卡片与底层对象双向链接；卡片内容变化有历史。
- 卡片是核心对象的**只读投影**；认领/提交/验收等动作调用核心 API，不直接改平台卡片状态。

#### FR-CHAT-05 消息持久化与重启恢复（P0）

所有人类可见消息、任务事件、评审、决策、审批必须持久化；重启/崩溃后完整恢复。

**验收**：

- 消息发送成功后，即使立即崩溃也不丢失。
- 重启后打开会话，历史顺序、线程、附件、卡片状态一致。
- 断线重连后补齐缺失消息，不重复显示。
- 未完成回复标记「中断」，不伪装成完成。
- 删除/编辑有事件记录；审计可查。

#### FR-CHAT-06 通知、未读与注意力分级（P0）

系统应提供通知与未读管理，并把打扰分级：FYI / 需要知道 / 需要决定 / 阻塞。

**验收**：

- 用户可按会话/部门静音；免打扰时段可配置。
- 默认实时打扰 ≤3 次/天（可配置）；只有「需要决定/阻塞/不可逆」实时打扰；其余进入摘要/收件箱。
- 提及、任务分配、审批、阻塞、预算告警是主要通知触发。
- 未读以最后已读位置为准，不做逐条回执。
- 助理可聚合通知，不直接把所有部门消息推给人类。

#### FR-CHAT-07 任务板（P0）

平台应提供任务板视图，支持看板/列表、过滤、排序、任务详情与时间线。

**验收**：

- 按部门、状态、owner、优先级、截止过滤；保存视图为 P1。
- 任务详情展示：描述、验收标准、依赖、产出物、评审、评论、时间线、成本。
- 拖拽/操作状态转换受权限与状态机约束；非法转换有明确提示；状态变更由核心写模型落库，平台只更新投影。
- 任务板与频道/线程双向跳转。
- 任务数量大时有分页/虚拟滚动，不卡顿。

#### FR-CHAT-08 产出物视图（P0）

平台应提供产出物列表与详情：版本、内容、关联、评审、评论、对比。

**验收**：

- 支持 PRD/方案/代码/测试报告/评审/决策等类型；不同类型有合适渲染。
- 版本只增不改；可查看历史版本与 diff；可标记 supersedes。
- 产出物与任务/评审/决策双向链接；可复制引用链接到消息。
- 代码类产出物可显示 commit/diff/测试摘要；不要求内置完整 IDE。

#### FR-CHAT-09 组织与 Agent 基础视图（P0）

平台应展示组织图、Agent 角色卡、状态与暂停/恢复；负载、成本、最近行为的增强视图为 P1。

**验收**：

- 组织图显示项目主管、助理、部门主管、员工；可点击查看角色卡。
- 状态：运行中/空闲/等待审批/暂停/失败/预算阻塞/失联；可暂停/恢复（按权限）。
- 显示当前任务与预算余量；负载/成本/最近行为增强为 P1（见 FR-TEAM-07；基础状态见 FR-OBS-01）。
- 支持从组织图发起私聊/任务/评审。

#### FR-CHAT-10 记忆快捷入口（P1）

平台应在工作台提供记忆检查器入口与快捷视图；**记忆检查器的完整行为以 FR-MEM-09（P0）为准**，此处不重复定义。

**验收**：

- 可从助理私聊、组织视图、任务详情跳转到记忆检查器。
- 入口显示待审数量与最近变更；不复制 FR-MEM-09 的字段定义。

#### FR-CHAT-11 搜索界面（P0）

平台应提供统一搜索入口，支持消息、任务、决策、产出物的检索与过滤。

**验收**：

- 输入即搜/回车搜；支持中文 2 字及以上、英文、代码标识符。
- 过滤：部门、会话、作者、Agent、时间、类型、任务、产出物、标签。
- 结果按会话/对象聚合；片段高亮；点击跳转并保留上下文。
- 支持空结果建议；保存搜索/最近搜索为 P1。
- 搜索无权限的内容不出现，也不泄漏其存在。

#### FR-CHAT-12 成本/审计聚合视图（P2）

v0.0.1 不单独做聚合页；成本视图见 FR-OPS-05/FR-OBS-03，审计视图见 FR-SEC-06。后续版本再做统一聚合。

#### FR-CHAT-13 可访问性与效率（P1）

平台应支持键盘操作、命令面板、基本屏幕阅读器与对比度要求。

**验收**：

- 常用操作（切换会话、搜索、发消息、审批、暂停）有快捷键。
- 命令面板可搜索操作与对象。
- 键盘可完成核心流程；焦点可见；对比度符合基本可访问性要求。
- 中文文案清晰；日期/时间/数字格式一致。

#### FR-CHAT-14 群聊与多 Agent 发言（P0）

平台应支持多 Agent + 用户的群聊：部门群聊、项目群聊、跨部门评审群聊、临时讨论组。

**验收**：

- 群聊有成员、可见性、创建者、主题、置顶、@提及、引用、附件、搜索。
- 多 Agent 被 @ 时按发言队列依次回复；可配置单轮最多发言数，避免刷屏。
- 部门群聊默认只对部门成员/主管/助理可见；跨部门群聊只允许结构化评审/决策消息；临时讨论组指定成员与到期。
- 用户可查看所有群聊消息（观察者），默认不参与；加入后可发言。
- 群聊消息全量落库、可检索、断线补齐；支持导出。

#### FR-CHAT-15 Agent 生命周期管理入口（P0）

所有 Agent 应能通过对话平台启动、暂停、恢复、停止与配置；平台是 Agent 能力的统一操作面。

**验收**：

- 可从平台创建/查看/启动/暂停/恢复/停止 Agent；状态与原因可见（运行/空闲/等待审批/预算阻塞/暂停/失败/失联）。
- 可查看角色卡、部门、分工视角、工具权限、预算、最近行为；可调整模型参数（v0.0.1 默认 deepseek-flash）。
- 启动/暂停/停止由核心执行，平台展示状态投影；失败有错误与重试。
- 高风险配置变更需人类审批；操作留审计。
- 平台不是仅聊天入口：群聊、任务、Agent 管理、审批、记忆、审计在同一工作台。

#### FR-CHAT-16 通信隔离与临时桥（P0）

默认通信必须隔离：部门内自由；跨部门由部门主管对接；部门主管与用户经助理；用户可看全部群聊，并可临时开桥。

**验收**：

- 员工默认不能私聊其他部门员工；跨部门消息必须经部门主管转接。
- 部门主管默认不能直接私聊用户；对用户汇报/审批经助理。
- 用户可查看所有群聊；可加入/退出、@Agent、发消息。
- 用户可临时开通直连桥（跨部门/主管-用户/两个 Agent），必须指定范围与到期；到期自动关闭并通知。
- 桥接消息留审计；桥接不能绕过工具权限/审批/记忆可见性。
- 违反默认隔离的路由被拒绝并提示可用路径（找主管/找助理/开桥）。

### 8.3 C. 助理 Agent

#### FR-ASST-01 澄清与项目意图卡（P0）

助理应通过结构化提问把模糊想法变成可执行目标，并产出一页「项目意图卡」。

**验收**：

- 首轮可用「快速模式」只问 3 个必答问题（目标、必须有的功能、预算档位），其余用默认值后续补全；也支持完整访谈。
- 完整提问覆盖：目标、用户、范围、约束、质量、预算、期限、风险、现有资产。
- 意图卡包含：目标、成功标准、必须做/不做、约束、预算、风险、待确认问题。
- 用户确认后才进入组部门；未确认时助理不得创建部门。
- 意图卡可编辑、版本化，并作为部门章程输入。

#### FR-ASST-02 单次问答（P0）

对于不需要部门的问题，助理应直接回答，并给出是否需要建任务的建议。

**验收**：

- 回答可引用消息/文件/决策；无来源时明确说明不确定性。
- 不因单次问答自动创建部门/任务；可建议「要不要我建个任务跟踪」。
- 涉及高风险动作（改代码、发布、付款）时，助理不直接执行，转为任务/审批。
- 回答受记忆与权限约束；不泄漏不可见内容。

#### FR-ASST-03 项目/部门蓝图（P0）

助理应提出可审批的项目/部门蓝图，而不是直接创建部门。

**验收**：

- 蓝图包含：使命、成功标准、部门模板、角色卡、人数、接口、节奏、质量门、工具/权限、模型策略、记忆范围、成本估算、前三风险。
- 至少提供两个可选方案（如「精简版」「完整版」）及取舍。
- 用户可修改角色/人数/预算；修改后助理重新估算成本与风险。
- 蓝图批准（G1）后才 provisioning。

#### FR-ASST-04 组队与 Provisioning（P0）

系统应按批准的蓝图创建部门、Agent、部门群聊、任务板、产出物空间、记忆空间与权限。

**验收**：

- Provisioning 状态机：planned → platform_created → core_created → verified；每步幂等键 = `provisioning_id + step`。
- Provisioning 幂等：重复执行不产生重复部门/员工。
- 失败可重试/回滚；列出补偿顺序；不留下半支部门/孤儿频道；提供孤儿报告与对账。
- 创建后各部门主管自动做 kickoff；用户收到摘要。
- 部门进入 active 前，用户可检查员工角色卡、分工视角与权限。
- 创建/变更记录进审计。

#### FR-ASST-05 状态聚合与按需简报（P0）

助理应聚合部门状态，提供按需简报与风险提示，而不是转发所有消息；定时生成是 P1。

**验收**：

- 简报包含：进展、阻塞、待决策、风险、成本、下一步。
- P0 支持用户按需生成；P1 支持按频率/渠道自动生成。
- 简报中的每一项可跳转到原始任务/消息/决策。
- 无变化时可省略或极简，不制造噪音。
- 人类可标记「不需要这类简报」，助理学习偏好。

#### FR-ASST-06 决策收件箱（P0）

需要人类决定的事项应进入决策收件箱；升级包的内容与升级层级以 FR-ESC-01 为准。

**验收**：

- 收件箱按「需要决定 / 稍后 / FYI」分组；同一事项只有一个持久条目。
- 升级包格式引用 FR-ESC-01，不在此重复定义。
- 支持批量审批、稍后处理、授权给助理/主管（有范围与期限）。
- 只有「需要决定/阻塞」实时打扰；其余进收件箱。
- 决策后自动记录决策记录并通知受影响方。
- 人类可追问，助理补充证据而不是重复立场。

#### FR-ASST-07 跨部门协调与主持（P0）

助理应主持跨部门评审/辩论，管理流程但不替双方投票；部门主管之间的争论由助理整理后反馈用户。

**验收**：

- 发起评审时确认：议题、双方代表、证据、时限、裁决人。
- 控制轮次（每人≤5 条、总提交≤15）、时间盒、死锁检测；无新证据时停止。
- 汇总「共识/分歧/新证据」，生成决策简报。
- 不偏向任何部门；不伪造共识；异议保留。
- 裁决后更新任务/产出物并通知。

#### FR-ASST-08 记忆策展（P0）

助理应维护人类偏好、项目决策、跨部门约定，并审核员工提交的候选记忆。

**验收**：

- 低风险候选可自动合并；决策/争议/敏感信息需人类或主管确认。
- 合并时去重、补证据、处理冲突；记录来源与操作者。
- 定期清理过期/低置信/重复条目；可提醒人类复核。
- 人类可查看「助理最近记住了什么」，并纠正。
- 不把推测写成事实；不把秘密写入记忆。

#### FR-ASST-09 助理边界（P0）

助理不得越权：不代替人类批准预算/章程，不修改自己权限，不删除审计，不冒充人类。

**验收**：

- 所有高风险动作走审批；助理不能自批。
- 助理的角色卡/权限只能由人类修改；修改留审计。
- 助理不能以人类名义发消息；消息 sender 明确标注 Agent。
- 助理不能在未确认时创建/解散部门。
- 违反边界的尝试被拒绝并记录。

### 8.4 D. 部门

> 说明：组织单元为「部门」；FR-TEAM 编号保留以兼容早期草稿，语义为 Department。

#### FR-TEAM-01 部门模板（P0）

系统应提供至少两种部门模板：三部门交付（产品/研发/测试）、三部门 + 平台部门；可选 PM 部门。

**验收**：

- 模板定义部门使命、角色、分工视角、接口、默认质量门、推荐工具。
- 用户可在模板基础上增删角色/员工；不能删掉必要职责（如测试质量门）。
- 部门创建后显示模板来源与偏离项。
- v0.0.1 验收使用「三部门交付」；跨部门挑战时加平台部门。

#### FR-TEAM-02 角色卡与分工视角（P0）

每个 Agent 应有可查看、可审计的角色卡，并写明部门与固定分工视角。

**验收**：

- 角色卡包含：部门、使命、职责、非目标、分工视角、输入/输出、工具/权限、沟通范围、决策权、记忆范围、模型策略（默认 deepseek-flash）、升级规则。
- 人类/部门主管可查看；修改需权限与审计。
- 角色卡与任务分派、评审权限、记忆视图一致。
- Agent 不能修改自己的角色卡/权限。

#### FR-TEAM-03 部门生命周期（P0）

部门应支持 active / paused / archived 状态；暂停后停止接新任务，保留状态与记忆。

**验收**：

- 暂停：当前任务可完成或中止；新任务不进入；通知相关人。
- 恢复：任务/会话/记忆完整恢复；不重复执行副作用。
- 归档：只读；可检索/导出；不再消耗模型。
- 解散：先收尾、移交产出与记忆、关闭权限；不能直接删除审计。
- 生命周期操作需权限与审计。

#### FR-TEAM-04 员工管理（P0）

部门应支持增减员工、调整角色/视角/预算；高风险变更需人类批准。

**验收**：

- 部门主管可提议；人类批准后生效。
- 新员工有角色卡、视角、权限、记忆范围、预算；不能继承前任私有记忆。
- 移除员工：收回权限；未完成任务转交/取消；保留历史产出与审计。
- 变更历史可查；不能复用已删除员工的名字。
- 员工数量/预算有上限，超限提示。

#### FR-TEAM-05 部门章程与 Kickoff（P0）

每个部门应有章程，并在启动时完成 kickoff。

**验收**：

- 章程包含：目标、范围、成功标准、角色、分工视角、接口、质量门、协作节奏、预算、升级规则、记忆边界。
- Kickoff 输出：目标复述、前三风险、第一里程碑、待确认问题（≤3）。
- 人类确认项目/部门蓝图（G1）后进入 active；kickoff 不再单独审批。
- 章程变更需版本与审批。

#### FR-TEAM-06 部门隔离与可见性（P0）

部门之间应有清晰的可见性边界；跨部门默认通过部门主管对接；用户可查看全部群聊。

**验收**：

- 部门群聊默认仅部门员工/主管/助理可见。
- 跨部门群聊只允许结构化消息；不允许自由闲聊。
- 员工默认不能读其他部门私有档案/员工评价/争议对方立场。
- 用户可查看全部群聊；查看行为留审计。
- 越权读取被拒绝并记录。

#### FR-TEAM-07 组织图与负载（P1）

系统应展示组织图、员工负载、当前任务、预算与健康状态。

**验收**：

- 组织图可按部门折叠/展开；显示用户 -> 助理 -> 部门主管 -> 员工；显示角色、视角与状态。
- 负载：进行中任务数、WIP 上限、最近失败/返工。
- 预算：今日/本周花费与余量。
- 可从此视图发起暂停/私聊/任务/评审。

#### FR-TEAM-08 多部门与接口（P0）

系统应支持创建多个部门，并定义部门间接口与评审关系。

**验收**：

- 每个部门有独立主管、员工、群聊、任务板、记忆空间。
- 可定义接口：交付物、依赖、SLA、评审对象、对接主管。
- 跨部门评审可发起、可追踪、可升级；超过 15 条由助理反馈用户。
- 部门间不能直接改对方任务/产出物；通过评审/决策。
- 验收场景至少包含一次跨部门挑战。


### 8.5 E. 任务与产出物

#### FR-TASK-01 任务创建与拆解（P0）

部门主管/助理应能把目标拆成任务，写清目标、验收标准、owner、分工视角、依赖、预算与时限。

**验收**：

- 支持从消息/意图卡/PRD 创建任务；保留来源链接。
- 任务可父子/依赖；拆解不丢失原目标。
- 必填：标题、目标、验收标准、owner、reviewer、approver、perspective、优先级、预算。
- 不满足 DoR 的任务不能进入执行；可创建 spike 任务补齐信息。
- 任务创建/变更进审计与时间线。

#### FR-TASK-02 任务状态机（P0）

任务应遵循明确状态机：proposed → ready → discussing → in_progress → in_review → approved → done；支持 blocked、changes_requested、canceled、failed；escalated 为标记。

**验收**：

- 非法转换被拒绝并说明原因。
- 每次转换记录：谁、何时、从哪到哪、理由、关联证据。
- 状态是事件投影，可重放；不能直接改数据库状态。
- 作者不能审批自己的任务；评审者不能是 owner。
- 任务完成后不可静默重开；重开最多 1 次，第二次必须人类批准。
- 任务状态与审计采用 append-only + 可校验哈希链（或等价完整性校验），不承诺对抗同 OS 用户恶意改库。

#### FR-TASK-03 DoR 与 DoD（P0）

系统应强制 DoR/DoD，避免「没想清楚就开工」「没证据就完成」。

**验收**：

- DoR：目标、验收标准、owner、reviewer、approver、分工视角、依赖、预算、时限。
- DoD：验收标准逐条有证据、产出物已登记、评审通过、无 blocker、必要人类闸门已签、遗留风险已记录。
- 不满足 DoR/DoD 时有明确提示与缺失项；可由人类豁免（需决策记录）。
- 任务详情展示 DoR/DoD 检查结果。

#### FR-TASK-04 依赖、阻塞与升级（P0）

任务应支持依赖/阻塞关系，并在超时/无进展时升级。

**验收**：

- 依赖可视化；被依赖任务未完成时不能进入执行（除非人类豁免）。
- 创建/更新依赖时拒绝成环，给出循环路径；跨部门依赖同样校验。
- 阻塞需记录原因、owner、下一步、预计解除时间。
- 阻塞超时自动提醒/升级；无进展检测（可配置）。
- 升级保留原状态与升级原因；不丢失上下文。

#### FR-TASK-05 WIP、预算与时限（P0）

系统应限制在制品数量、任务预算与时限，防止过载与成本失控。

**验收**：

- 每 Agent/部门可设 WIP 上限；超限不能认领新任务。
- 任务预算（token/费用/时间）可设；80% 告警、100% 暂停并升级。
- 超时/超预算任务标记 at_risk；可延期/追加/取消（需权限）。
- 成本视图可按任务归因。

#### FR-TASK-06 任务时间线与审计（P0）

每个任务应有完整时间线：创建、分派、状态变化、评审、返工、决策、验收、成本。

**验收**：

- 时间线按时间排序，可过滤；每项可跳转。
- 显示操作者（人/Agent）、原因、证据链接。
- append-only + 可校验哈希链；不承诺对抗同 OS 用户恶意改库；修正以追加事件表达。
- 可导出。

#### FR-TASK-07 验收核对表（P0）

每个功能/里程碑/高风险任务应有「验收标准 → 证据 → 部门主管结论 → 人类决定」四段核对表；G3 不能在没有核对表的情况下通过。

**验收**：

- 每条 acceptance criterion 显示：证据链接（测试/命令/产出物版本）、部门主管结论（通过/不通过/需人类判断）、人类决定。
- 任一条「不通过」时不得提交 G3；「需人类判断」必须进入 G3。
- G3 卡片展示：核对表、未决风险、成本、受影响产出物版本。
- 小任务可由主管在授权范围内验收，但必须留核对表与审计；功能/里程碑/高风险必须人类 G3。
- 核对表不可事后篡改；修正以追加记录表达。

#### FR-TASK-08 分工视角与部门内讨论（P0）

部门主管分派任务时必须写明每个员工的分工视角；员工先确认视角与计划；有分歧进入部门内讨论。

**验收**：

- 任务必填 department_id 与每个执行者的 perspective（页面/接口/数据流/测试等）。
- 员工在 discussing 状态提交「视角 + 计划 + 风险」；主管确认后进入 in_progress。
- 员工讨论时以「方便自己开发」为第一原则；不得假装全局中立。
- 部门内讨论每人≤5 条、总计≤15 条（两人参与时实际最多 10 条；多人参与时可用到 15）；超过由部门主管裁决或升级。
- 讨论记录进入任务线程；影响接口/范围/质量的裁决写决策记录。
- 部门内讨论的全局权衡由本部门主管拍板；涉及项目级约束时主管可向 PM/助理索取约束，但不把裁决权交给员工；跨部门冲突升级助理/用户。

#### FR-ART-01 产出物注册与版本（P0）

所有交付物应登记到产出物注册表，版本不可变，带内容哈希与来源。

**验收**：

- 类型：PRD、技术方案、代码、测试报告、评审记录、决策记录、其他。
- 字段：id、类型、标题、版本、内容哈希、存储位置、作者、任务、部门、依赖、评审、决策、状态、来源。
- 版本只增不改；修正产生新版本并用 supersedes 关联。
- 代码类可关联 commit；文档类可存内容/文件；均需不可变引用。
- 产出物可被任务/评审/决策/消息引用。

#### FR-ART-02 产出物关联（P0）

产出物应与任务、评审、决策、消息双向关联。

**验收**：

- 任务详情显示产出物版本；产出物显示关联任务/评审/决策。
- 评审针对具体版本，不针对「最新文件」。
- 决策记录链接受影响产出物；产出物显示决策。
- 关联可追溯；删除/归档不破坏引用。

#### FR-ART-03 产出物呈现与评论（P0）

平台应能查看不同类型产出物，并支持评论/挑战。

**验收**：

- Markdown 渲染；代码 diff 高亮；测试报告结构化；图片可预览。
- P0 支持基础评论；P1 支持行级/字段级评论与增强 diff。
- 版本对比清晰；不要求内置 IDE。
- 大文件/大 diff 有分页/懒加载。

#### FR-ART-04 产出物对比与回滚（P1）

用户应能对比版本并回滚到历史版本（以新版本表达）。

**验收**：

- 并排/统一 diff；显示变更摘要。
- 回滚创建新版本，不删除历史；需权限与理由。
- 回滚后关联任务/评审提示「基于旧版本」，需重新确认。

#### FR-ART-05 产出物权限（P0）

产出物应遵守部门/项目可见性；跨部门只共享必要版本。

**验收**：

- 私有/部门/项目/组织四级可见性。
- 跨部门评审只共享被评审版本及必要上下文。
- 下载/复制/导出受权限；审计记录。
- 敏感内容可 redact；redaction 留痕。

### 8.6 F. 评审、辩论、决策、升级与审批

#### FR-REV-01 评审请求与挑战单（P0）

任何受影响的人/部门应能对产出物版本发起结构化挑战，而不是在聊天里说「我觉得不行」。

**验收**：

- 挑战单包含：来源部门、目标部门、产出物 ID/版本、严重级别（blocker/major/minor/question）、一句话主张、证据、影响、建议、owner、截止、状态、讨论线程。
- blocker/major 必须有证据（产物位置、命令输出、测试结果、验收标准引用）；无证据自动降级为 question。
- 挑战可针对段落/行/字段；可从消息/评论一键转为挑战单。
- 挑战状态可追踪：open / responded / resolved / escalated / withdrawn。
- 挑战与产出物版本绑定，不能漂移到「最新版」。

#### FR-REV-02 裁决与返工（P0）

评审人应给出结构化裁决；作者应能回应、修复、重新提交；返工必须可追踪。

**验收**：

- 裁决类型：approve / approve_with_comments / request_changes / escalate。
- 裁决包含：实际检查了什么、理由、条件、遗留风险、评审人、时间、关联决策。
- request_changes 必须列出必须修改项；作者逐项回应（接受/拒绝/降级）。
- 返工产生新产出物版本；旧裁决仍可追溯；同一 blocker 复现 2 次即升级，返工最多 2 轮。
- 作者不能批准自己的产出物；评审人不能是 owner。

#### FR-REV-03 独立评审与测试质量门（P0）

质量门必须独立：作者 ≠ 评审者；测试有独立判定权；高风险需要第三人/人类。

**验收**：

- 代码类产出物至少一名非作者评审 + 测试证据。
- 测试 Agent 可独立提交 blocker，不被研发/主管静默关闭。
- 高风险变更（按 §6.3 高风险分类表）需要额外审批人。
- 评审人轮换/盲评可按配置启用；同一对 Agent 互审需第三人（P1）。
- 质量豁免必须有人类确认 + 决策记录 + 风险说明。

#### FR-REV-04 评审 SLA 与提醒（P1）

评审应有 SLA、提醒与升级，避免任务卡在「等评审」。

**验收**：

- blocker 24h、major 48h、minor 可批量（可配置）。
- 超时提醒评审人/主管；超 SLA 自动升级。
- 评审人不可用时主管可改派（留记录）。
- 评审负载可见，避免集中到一个人。

#### FR-REV-05 人类抽检与异常通过率提示（P0）

系统应支持人类对评审/裁决做最小抽检，并提示异常通过率，作为反虚假共识/反串谋的产品入口。

**验收**：

- 人类可从评审/裁决列表随机抽取一条，查看证据与 dissent，标记「有效 / 无效 / 证据不足」。
- 抽检结果进入质量指标（评审有效率），并可写入一条部门记忆。
- 同一对 Agent 互审 ≥5 次且通过率 100% 时，提示人类抽检；不自动判定串谋。
- 抽检不阻塞交付；未抽检不视为失败。

#### FR-DEB-01 跨部门评审触发（P0）

当接口、范围、质量、资源、架构出现跨部门分歧时，应能发起结构化跨部门评审；部门内讨论见 FR-TASK-08。

**验收**：

- 触发：接口变更、依赖冲突、验收标准歧义、质量豁免、范围变更、架构选择。
- 发起者填写：议题、双方部门/代表、证据、期望裁决、时限。
- 助理确认后进入评审；不是所有分歧都自动升级为辩论。
- 纯偏好/优先级/价值判断不进辩论，直接升级人类。

#### FR-DEB-02 决策包与立场（P0）

双方应以「决策包」表达立场，而不是长篇自由辩论。

**验收**：

- 决策包包含：`stance`（一句话立场）、现状、提案、影响、`evidence_ids[]`、替代方案、请求裁决点。
- 双方各提交一次；证据必须可核查（链接/命令/测试/文档）；没有 evidence id 的断言不作为裁决依据。
- 不允许人身攻击、重复立场、无证据断言；主持人可要求补充证据，但不得代替双方写立场。
- 决策包可被人类/裁决人一页读完。

#### FR-DEB-03 轮次、时间盒与死锁（P0）

跨部门辩论必须有硬边界：总提交上限、时间盒、死锁检测、超限升级。

**验收**：

- 每人最多 5 条提交、总提交 ≤15：R1 双方各 1 条立场 + 各 1 条回应；R2 双方各 1 条反驳；双方各 1 人时实际最多 10 条，多代表/多轮可用到 15 条。
- 每条提交必须有 `stance` 与 `evidence_ids[]`；无新 evidence id 的重复提交不计轮次，主持人退回。
- 时间盒：异步 24h（可配置）；v0.0.1 同步机制用「立即运行」按钮，不做实时会议；超时自动升级。
- 死锁判定：连续两次提交 stance 相同且 evidence_ids 无新增 → 记录并升级，不自行裁决。
- 新证据重开最多 1 次；第二次必须人类批准。预算耗尽/无进展 → 停止并升级。
- 所有轮次与证据可检索。

#### FR-DEB-04 主持与裁决（P0）

助理主持流程；领域 owner 裁决；不可逆/高风险升级人类；裁决必须可执行。

**验收**：

- 主持人管流程（轮次、时限、记录），不投票、不偏向、不代替双方写立场。
- 裁决人不能是争议作者；领域 owner 枚举：产品（what/why）、研发主管（how）、测试（质量）、架构评审（接口/安全）、人类（跨领域/不可逆/高风险）。
- 裁决输出：决定、理由、影响、异议、后续动作、复查条件。
- 裁决后更新任务/产出物；通知受影响方；不执行「表面一致、私下不改」。
- 异议保留在决策记录中，不被删除。

#### FR-DEC-01 决策记录（P0）

范围变更、质量豁免、架构选择、跨部门裁决、预算调整必须产生不可变决策记录。

**验收**：

- 记录包含：id、标题、状态、背景、选项、决定、理由、证据、异议、决策人/咨询/知情、受影响任务/产出物、复查触发、supersedes、人类确认、时间。
- 决策记录只增不改；修正用新记录 supersede。
- 决策记录与任务/产出物双向链接；可从消息/搜索跳转。
- 人类可确认/否决；未确认的高风险决策不能执行。
- 决策记录可导出。

#### FR-DEC-02 决策检索与异议（P0）

决策记录应可检索、可引用、可追溯；异议不能被隐藏。

**验收**：

- 按关键词、部门、时间、状态、受影响对象检索。
- 决策卡显示：决定、理由、异议、复查条件。
- 异议可展开查看；不能只显示「一致通过」。
- 决策被 supersede 后，旧记录仍可查，并标注替代关系。
- 决策变更通知受影响方。

#### FR-ESC-01 升级阶梯与升级包（P0）

无法在本地解决的问题应按 L0–L4 升级，并带一页可读的升级包。

**验收**：

- L0 自检/测试；L1 部门内；L2 跨部门（助理主持）；L3 人类（预算/范围/不可逆/质量豁免）；L4 死锁/重大风险。
- 升级包：争议点、双方证据、选项、推荐、不决策的后果、需要谁在何时前决定。
- 升级保留原状态与原因；可回到原流程。
- 人类可批量处理/授权；授权有范围与期限。
- 升级 SLA 可配置；超时提醒。

#### FR-APPR-01 人类闸门（P0）

v0.0.1 必须有人类闸门：G1 项目/部门蓝图、G2 高风险技术方案/范围、G3 最终验收。

**验收**：

- G1：未批准不能创建部门。
- G2：高风险需求未批准不能开工；低风险可委托给部门主管（留记录）。
- G3：功能/里程碑/高风险交付未批准不能标记 done/发布；小任务可由主管在授权范围内验收。
- **发布定义**：v0.0.1 的「发布」= 系统把交付物交付到工作区并给出部署说明，由用户自行部署；不做自动发布/自动合并/自动付款。
- 每个闸门显示：要确认什么、证据、风险、选项、推荐；G3 必须显示验收核对表。
- 闸门可拒绝/要求修改；拒绝需理由；修改后重新提交。
- 闸门操作留审计。

#### FR-APPR-02 不可逆动作审批（P0）

删除、force push、对外发布、付款、权限变更等不可逆动作必须人类审批。

**验收**：

- 动作发起时显示：动作、目标、影响、可逆性、风险、建议。
- 支持一次/会话/始终（始终需范围与期限）；默认一次。
- 拒绝后 Agent 不能绕过；尝试绕过被拒绝并记录。
- 审批结果写审计；高风险动作双钥匙（作者+审批人）。
- 审批 TTL 默认 24h；超时未审批 → 标记阻塞/提醒/升级，不自动执行。
- 批量审批不适用于双钥匙/不可逆动作；授权给助理/主管必须有范围与到期时间。

### 8.7 G. 记忆

#### FR-MEM-01 主管/助理四层记忆（P0）

部门主管 Agent 与助理 Agent 必须具备四层记忆：短期上下文、触发式记忆、档案记忆、自适应提示词。

**验收**：

- 短期上下文：当前会话/任务窗口；由核心装配/压缩，并记录 `context.request` 快照；关键事实固定注入。
- 触发式记忆：任务关闭/返工/评审裁决/人类拍板/冲突裁决等事件触发抽取；产出候选记忆。
- 档案记忆：跨会话的结构化实体（人/员工/部门/项目/任务/决策/争议/能力）；可检索、可编辑、可删除。
- 自适应提示词：分章节的管理手册；注入 system 稳定前缀；有版本、diff、回滚。
- 四层可分别开关/配置；失败不阻塞主流程。

#### FR-MEM-02 员工 session + 选择性档案（P0）

员工 Agent 应使用完整会话记忆，但只允许少量重要信息进入档案。日常员工管理（任务分配、负载、反馈、返工）由部门主管 Agent 负责；结构性变更（增减员工、改角色、改预算）需人类批准。

**验收**：

- 每个员工有独立会话；可恢复、可压缩、可审计。
- 员工只能提交候选记忆，不能直接写组织级档案。
- 每任务候选 ≤ 5 条、每条 ≤ 200 字、至少 1 条证据（可配置）。
- 员工默认不能读其他部门私有档案/员工评价/争议对方立场。
- 员工会话不因任务结束而删除；可按保留策略归档。

#### FR-MEM-03 触发规则（P0）

触发式记忆应以事件为主、消息量兜底，而不是只按条数。

**验收**：

- 事件触发：任务关闭/返工/取消、评审裁决、跨部门裁决、人类拍板/偏好/红线、员工变更、里程碑、事故复盘。
- 兜底：每 N 条消息或每 24 小时轻量扫描（可配置）。
- 触发有单飞、冷却、超时预算；失败可重试；部分成功不重复写。
- 用户可手动「记住这个」/「忘记这个」。
- 触发/抽取/写入/拒绝可在管理界面查看。

#### FR-MEM-04 写入规则与额度（P0）

记忆写入必须满足可复用、可验证、决策相关、归属明确；不满足不写。

**验收**：

- 四道门槛在 UI/文档中可见；低置信/无证据的候选被拒绝或标「待验证」。
- 不写：完整对话、模型推理、临时调试、第三方隐私、无法归因的推断。
- 每任务/每日写入额度可配置；超限拒绝并提示。
- 去重/冲突检测：同实体同键合并/标失效/提示冲突。
- 写入留审计：谁、何时、依据、合并到哪条。

#### FR-MEM-05 档案结构与双时间（P0）

档案应结构化存储八类实体；决策/争议/能力必须保留生效/失效时间与证据。

**验收**：

- 实体：人/员工/部门/项目/任务/决策/争议/能力。
- 字段：实体/键、内容、摘要、标签、置信度、证据、敏感度、生效/失效时间、supersedes、版本、状态。
- 决策/争议：双方立场不可覆盖；失效非删除；可回答「当时为什么」。
- 其他实体：upsert + 版本/快照。
- 档案可导出为可读格式。

#### FR-MEM-06 容量治理、压缩与快照（P0）

档案必须有容量预算、压缩、快照、失败恢复，避免膨胀与静默截断。

**验收**：

- 区分「渲染上限」与「存储上限」；两者独立配置。
- 超限：先完整落库再异步压缩，或拒绝并给压缩指引；不能静默截断。
- 压缩基于全文，保留事实/证据/关键标识；压缩后自校验字数。
- 压缩失败恢复原文；压缩前快照；同一键单飞。
- 超限条目可枚举；内部元数据表豁免。
- 快照有保留上限；可查看压缩历史。

#### FR-MEM-07 自适应提示词（P0）

主管/助理应能维护分章节的管理手册，作为自适应提示词；有版本、审计与审批。

**验收**：

- 章节：角色/目标、管理原则、红线/升级、人类偏好、部门现状速记。
- 长度有上限（建议 800–1500 字）；超限压缩/拒绝。
- 每条规则可带来源事件；不写一次性任务细节。
- v0.0.1 默认仅提议；低风险自动应用需显式开启，并有 diff/冷却/回滚；高风险（红线/权限/对外承诺）一律人类批准。
- 版本 diff、回滚、禁用；人类可直接编辑。
- 与系统/角色卡冲突时按优先级裁决。

#### FR-MEM-08 记忆检索与注入（P0）

系统应按任务/角色/权限检索记忆，并按预算注入；不能全量倾倒。

**验收**：

- 结构化优先、全文兜底、语义可选。
- 注入预算 = `min(百分比 × 有效输入预算, 绝对上限)`；按模型窗口预设归一化；核心自己计数/估算，保留 5–10% 安全边际。
- 注入分区：系统/手册、当前任务、相关档案、近期会话；超预算按降级链。
- 默认稀疏：档案先给摘要 + 取数路径；**必须提供受权限约束的「记忆读取」工具**，否则不得声称按需读取。
- 每次注入记录到 `context.request`：注入了哪些档案/任务/消息、来源、token 估算、模型/超参、turn id；用户可查看「本次回答用了哪些记忆」。
- 每条注入带来源标签；可解释「为什么这么判断」。
- 检索失败时降级到「手册 + 当前任务」，仍能工作。

#### FR-MEM-09 记忆检查器与待审队列（P0）

用户应能查看、搜索、编辑、删除、钉住记忆，并处理待审候选。

**验收**：

- 按实体/部门/项目/时间/类型浏览；搜索。
- 显示来源、置信度、生效/失效、版本、可见性、最近使用。
- 编辑/删除/钉住；删除留墓碑；删除后不再注入。
- 待审队列：批准/拒绝/合并/编辑；拒绝需理由；批量操作（P1）。
- 管理手册编辑器：章节、diff、回滚、审批状态。

#### FR-MEM-10 记忆权限与隐私（P0）

记忆必须按可见性隔离，敏感信息不得写入/注入；读取留痕。

**验收**：

- 四级可见性：agent-private / team / org / human-only。
- 员工/部门/助理按视图注入；跨部门只共享决策包与结论。
- 密钥、令牌、身份证号等写入前过滤；日志/检索不出现。
- 人类可导出/删除；删除传播到索引/缓存/快照（墓碑保留）。
- 读取留痕：谁读了哪条；用于审计与解释。
- 越权读取被拒绝并记录。

#### FR-MEM-11 记忆失败处理（P0）

记忆系统失败不能丢消息、不能阻塞主流程、不能静默半成品。

**验收**：

- 单飞锁：同一实体/键同时只有一个写入/压缩。
- 失败退避 + 冷却；可重试；部分成功单独记账。
- 关闭时冲刷未处理队列；超时不取消在途；未处理保留到下次。
- 模型不可用时降级：记录待处理，不阻塞对话。
- 管理界面显示：待处理、失败、超限、压缩中、上次成功时间。

#### FR-MEM-12 记忆导出与备份（P0）

记忆应可导出/备份/恢复，不锁定在应用内。

**验收**：

- 导出格式：JSON/Markdown（结构化 + 叙事）；含来源与版本。
- 备份包含记忆与索引元数据；恢复后可检索。
- 导入需校验 schema/版本；冲突有提示。
- 导出/导入受权限；审计记录。

### 8.8 H. 检索

#### FR-SRCH-01 全文检索与中文支持（P0）

系统应支持消息、任务、决策、产出物的全文检索，中文 2 字及以上片段可命中。

**验收**：

- 中文 2 字词（测试/部署/返工）、3 字词、短语、中英混排、代码标识符、路径可搜。
- 英文大小写不敏感；常见全半角/零宽字符规范化。
- 结果相关；不是只按时间倒序。
- 空结果有建议（放宽过滤/换关键词/搜索范围）。
- 删除消息不可被任何检索路径命中。

#### FR-SRCH-02 过滤、排序与片段（P0）

检索应支持结构化过滤、相关度排序、片段高亮与会话聚合。

**验收**：

- 过滤：部门、会话、作者、Agent、时间、类型、任务、产出物、标签、是否有附件。
- 排序：相关度 + 时间衰减 + 会话聚合 + 权威度（决策/钉住加权）。
- 片段高亮命中词；显示上下文；点击跳转。
- 结果按会话/对象聚合；可分页/加载更多。
- 保存搜索/最近搜索为 P1，不计入 P0 验收。

#### FR-SRCH-03 跨对象检索（P0）

检索应覆盖消息、任务、决策、产出物元数据，而不只是聊天。

**验收**：

- 可按对象类型过滤；结果卡片显示类型与关键字段。
- 任务可按标题/描述/验收标准/owner；决策按标题/理由/异议；产出物按标题/版本/类型。
- 默认不索引原始模型轨迹/工具日志；可在消息详情中查看。
- 跨对象结果可跳转到详情并保持上下文。

#### FR-SRCH-04 权限过滤（P0）

检索必须在查询/排序前应用权限，不能先查全量再删。

**验收**：

- 无权限的会话/部门/档案不出现；不泄漏数量/存在性。
- 对象级权限由 Agent 核心的单一 Policy 判定；平台只做会话级过滤 + 调用 Policy 做对象级预过滤；权限变更后索引失效/刷新有明确延迟。
- 搜索结果计数与分页一致；不会出现「这页只剩 3 条」。
- 共享/跨部门内容按授权显示；审计记录敏感搜索（P1）。
- 权限变更后索引/结果即时生效或明确延迟。

#### FR-SRCH-05 索引重建与状态（P0）

索引应可重建；重建期间有明确状态；不能因索引损坏丢失源数据。

**验收**：

- 提供「重建索引」操作；可全量/按范围。
- 重建期间搜索显示「索引更新中」，可降级到基础扫描/旧索引。
- 重建完成校验数量/抽样；失败可重试。
- 删除/编辑/权限变更同步到索引。
- 索引版本不兼容时自动提示重建。

#### FR-SRCH-06 性能与质量（P0）

检索应满足本地性能与质量目标。

**验收**：

- 10 万条消息、常见过滤组合下 p95 ≤ 300ms；目标 150ms。
- 中文 2 字查询单列 p95 预算（建议 ≤150ms，10 万条），必须使用短词索引，不允许退化为全表扫描。
- 消息写入后 ≤ 100ms 可被检索到。
- 金标准查询集 Recall@10 ≥ 0.8；nDCG@10 有基线并持续跟踪。
- 冷启动后首次搜索 ≤ 2s（不含索引重建）。
- 性能回归有基准测试。

#### FR-SRCH-07 删除与隐私（P0）

删除的消息/档案必须从检索中消失；隐私删除可验证。

**验收**：

- 软删除后搜索结果不显示；详情不可访问（除非审计权限）。
- 物理清理/索引清理有任务与状态；完成后验证。
- 删除事件通知客户端移除本地缓存。
- 导出不包含已删除内容（审计墓碑除外）。

### 8.9 I. 安全与运维

#### FR-SEC-01 本地访问与认证（P0）

系统默认只允许本机访问；首次使用创建本地身份；跨站请求被拒绝。

**验收**：

- 默认绑定 loopback；启动打印地址；不默认暴露局域网/公网。
- 首次启动创建 owner；支持本地密码/令牌（可配置）。
- 校验 Origin/Host；Cookie SameSite/HttpOnly；写操作需自定义 Header；GET/流式事件推送同样校验；默认不返回 CORS 头。
- 远程访问需显式配置 + 风险提示；不默认提供公网 TLS 方案。
- 失败登录/异常访问有记录与限流。

#### FR-SEC-02 Agent 身份与 Token（P0）

每个 Agent 应有独立身份与凭证；可撤销；不能冒充人类。

**验收**：

- Agent 有独立 Token（哈希存储）；可单独撤销/轮换。
- 消息/事件标注 sender 类型（human/agent）与 Agent ID。
- Agent 不能使用人类会话/凭证；不能伪造 sender。
- Token 不出现在消息/日志/检索；泄漏可撤销。
- Agent 创建/删除/权限变更留审计。

#### FR-SEC-03 工具权限与审批（P0）

Agent 工具应最小权限、风险分级、可审批、可审计。

**验收**：

- 工具白名单/路径白名单/网络域名白名单/命令策略按 Agent/部门配置。
- 风险分级：只读/可逆写/不可逆写/对外发布/花钱；高风险需审批。
- 沙箱限制工作区、资源、超时；统一安全语义 + 平台差异矩阵 + 默认拒绝，而不是承诺行为完全一致。
- 工具调用记录：谁、何时、参数摘要、结果、审批人；敏感参数脱敏。
- 绕过审批的尝试被拒绝并告警。

#### FR-SEC-04 提示注入与不可信内容（P0）

外部内容（网页/文件/Issue/工具输出）应被视为不可信数据，不能覆盖系统指令。

**验收**：

- 指令层级明确：系统安全 > 人类 > 角色卡/章程 > 自适应提示词 > 外部内容。
- 外部内容标记来源；不自动执行其中的指令。
- 高风险动作不因「文档里写了」而自动执行；需人类审批。
- 网络/上传/下载有白名单/审批；敏感信息外发有检查。
- 注入样例测试纳入发布检查。

#### FR-SEC-05 密钥与脱敏（P0）

密钥/令牌/敏感信息不得进入消息、记忆、日志、检索。

**验收**：

- DeepSeek API Key 只给核心；存 OS keychain 或等价安全存储（Windows DPAPI/ACL，POSIX 0600）；UI 不明文回显。
- 日志/错误/导出脱敏；可配置敏感字段。
- 记忆写入前 redaction；检索不返回敏感字段。
- 密钥轮换/撤销有流程；泄漏有告警。
- 备份加密可选；明确磁盘未加密的取舍。

#### FR-SEC-06 审计（P0）

关键动作必须留审计：登录、会话/部门变更、消息、工具、审批、配置、密钥、索引重建、记忆写入/删除。

**验收**：

- 审计字段：时间、操作者（人/Agent）、动作、对象、结果、原因/审批。
- 审计为唯一 append-only 流；应用层哈希链校验；不可 UI 删除；可按保留策略归档/清理（清理本身留审计）；可整体导出。
- 审计可按对象/人/时间/动作查询。
- 高风险动作有完整审批链。
- 审计日志脱敏；访问受权限。

#### FR-SEC-07 暂停、恢复与紧急停止（P0）

人类应能暂停单个 Agent/部门或全局停止；暂停后保留状态，可恢复。

**验收**：

- 暂停：停止接新任务/新 turn；当前 turn 可完成或中止（可选）。
- 恢复：从暂停点继续；不重复副作用；未完成任务保持状态。
- 全局紧急停止：一键停止所有 Agent；显示影响范围；需确认。
- 暂停/停止留审计；通知相关人。
- 预算耗尽自动暂停（可配置）。

#### FR-OPS-01 备份与恢复（P0）

系统应支持备份/恢复，且恢复后消息、任务、评审、决策、记忆一致。

**验收**：

- 备份包含数据库/文件/配置（脱敏）、会话/记忆/任务/文件变更时间线；可手动/定时。
- 恢复前校验版本/完整性；恢复后索引重建/校验。
- 恢复演练有文档；至少一次成功演练。
- 备份不破坏运行中的数据库；不需要停机（或明确停机窗口）。
- 恢复失败可回滚；不丢现有数据。

#### FR-OPS-02 导出与导入（P0）

用户应能导出工作区数据；导入用于迁移/恢复/演示。

**验收**：

- 导出：消息、任务、产出物、评审、决策、记忆、审计（脱敏可配置）。
- 格式：开放、可读（JSON/Markdown/CSV）；大导出有进度/分片。
- 导入：校验 schema/版本；冲突/重复有策略；不覆盖现有数据除非确认。
- 导出/导入受权限；审计。
- 不锁定在应用内。

#### FR-OPS-03 日志与诊断（P1）

系统应提供结构化日志、诊断包与故障排查入口。

**验收**：

- 日志分级；关键路径有 correlation ID。
- 诊断包：版本、配置摘要（脱敏）、最近错误、数据库/索引状态、Agent 状态。
- 用户可一键导出诊断包；不包含密钥。
- 常见故障有自检与修复建议（端口、数据目录、DeepSeek Key、索引）。

#### FR-OPS-04 版本与迁移（P1）

系统应支持版本升级与数据迁移；迁移失败可回滚。

**验收**：

- 启动检测数据版本；需要时提示迁移。
- 迁移前自动备份；迁移有进度/日志。
- 迁移失败回滚；不启动半迁移状态。
- 版本兼容性说明；破坏性变更需确认。
- 导出格式有版本号。

#### FR-OPS-05 成本与预算（P0）

系统应提供成本可见、预算控制、超支处理。

**验收**：

- 按部门/任务/模型/日期显示 token、调用数、估算费用。
- 预算优先级：人类月上限 > 部门日上限 > 任务预算；任一耗尽即触发对应层级暂停，并显示「被哪一层暂停」。
- 80% 告警；100% 时完成当前工具调用后暂停接新任务（不中止有副作用的调用），保留审批 24h；人类可追加/一次性放行。
- 人类可追加预算/提高上限；留审计。
- 超支任务标记 at_risk；不能静默继续。
- DeepSeek 档位/预算降级可配置（P1）；不做多供应商路由。

#### FR-OPS-06 崩溃恢复与幂等（P0）

系统应在崩溃/重启后恢复，且不重复产生副作用。

**验收**：

- 已确认消息不丢；未完成回复标记中断。
- 未完成任务/评审/决策状态一致；可继续。
- 工具副作用：中断后标记「结果未知」，不自动重试有副作用操作；只读/幂等可重试。
- 重复投递不产生重复消息/任务/评审；幂等键生效。
- 恢复过程有日志与用户可见状态。

#### FR-OPS-07 定时与到期（P0）

系统应有持久化的定时/到期机制，支持审批 TTL、评审 SLA、时间盒、简报、预算周期与重启补跑。

**验收**：

- 定时任务持久化；进程重启后未到期任务仍生效，错过的任务按策略补跑/合并/跳过。
- 到期动作幂等：重复触发不产生重复审批/通知/升级。
- 支持取消/改期；取消留记录。
- 用户可在界面看到「等待中/已到期/已处理/已跳过」。
- 失败可重试；连续失败告警。

### 8.10 J. 可观测性

#### FR-OBS-01 Agent 状态与基础负载（P0）

系统应显示每个 Agent 的状态、当前任务、基础负载、预算余量与最近成功/失败；成本明细/历史负载为 P1。

**验收**：

- 状态：运行/空闲/等待审批/等待依赖/预算阻塞/暂停/失败/失联；每个状态给出用户操作（追加预算、改派、重启、解除依赖）。
- 当前任务、WIP、最近成功/失败、预算余量。
- 成本明细/历史负载/平均响应为 P1。
- 可暂停/恢复/私聊/查看角色卡。
- 异常状态（长时间无响应/连续失败）告警。

#### FR-OBS-02 任务与评审指标（P1）

系统应提供任务/评审/辩论的统计视图。

**验收**：

- 任务：吞吐、周期、返工率、阻塞时长、升级率。
- 评审：评审时长、blocker 数、通过率、返工原因分布。
- 辩论：轮次、解决时长、升级率、决策数。
- 可按部门/时间过滤；可导出。
- 指标用于改进，不作为惩罚 Agent 的唯一依据。

#### FR-OBS-03 成本与用量（P0）

系统应提供成本/用量视图，支持归因与告警。

**验收**：

- 按部门/任务/Agent/模型/日期聚合。
- 显示 token、调用数、估算费用、缓存命中（如可得）。
- 预算进度条/告警；超支原因可下钻。
- 可导出 CSV/JSON。
- 成本数据保留可配置。

#### FR-OBS-04 回放、上下文快照与审计（P0）

系统应支持从事件重建会话/任务，并查看每 turn 的上下文快照，用于调试、审计与解释。

**验收**：

- 选择会话/任务，查看按时间排序的事件/消息/工具调用/决策。
- 查看每 turn 的 `context.request`：注入了哪些档案/任务/消息、来源、token 估算、模型/超参、turn id。
- 回放不修改数据；只读。
- 可导出回放包（脱敏）。
- 回放能回答「当时模型看到了什么/谁批准了什么」。
- 敏感内容受权限；查看行为留审计。
- 若快照不是最终 prompt，明确标注「快照为注入包，实际 prompt 由核心装配」。

#### FR-OBS-05 告警（P1）

系统应对异常主动告警：预算、失败、阻塞、队列积压、索引/备份失败。

**验收**：

- 告警分级；可配置渠道（应用内/桌面通知）。
- 去重/抑制；避免告警风暴。
- 告警包含：是什么、影响、建议动作、跳转。
- 可静音/确认；处理留记录。

### 8.11 K. 文件写入与变更时间线

#### FR-WRITE-01 共享写工具（P0）

所有 Agent 必须共用一套 write_file 工具写入工作区文件；不允许各自直接写文件。

**验收**：

- 每次写入提交 write event：agent_id、path、base_hash、diff/content、reason、task_id、branch。
- **默认全局串行**：任一写入事件未消费前，其他 Agent 的写入被拒绝/排队；后续可配置按文件并行；分支切换/提交/批量重构用全局锁。
- 写入前校验 base_hash；冲突时拒绝并提示重新读取/变基，不静默覆盖。
- 写入结果返回变更 ID；失败可重试；超时有明确错误。

#### FR-WRITE-02 变更时间线（P0）

系统应为每个文件维护变更时间线，模仿 VSCode Timeline。

**验收**：

- 每个文件保留最近 30 次变更（配置项 write_timeline_limit，用户可调），超出淘汰最旧。
- 每条记录：文件、时间、Agent、diff、任务、分支、commit、原因。
- 新增工具 view_change_history：可按文件/分支/提交/Agent/时间查看。
- 时间线只读；删除文件/重命名/分支切换也记录事件。

#### FR-WRITE-03 Git 分支/提交监听（P0）

写工具应监听 Git 分支切换与提交，并把多次改动合并为 commit 组。

**验收**：

- 分支切换记录事件；切换期间禁止写入或要求确认。
- 提交时把自上次提交以来的多次改动合并为一个 commit 组；时间线仍保留最近 30 条。
- 已提交改动可在时间线查看；提交信息、commit SHA、作者可关联。
- 监听失败有告警；不阻塞手动 Git 操作。

#### FR-WRITE-04 并发与冲突验收（P0）

系统必须可验证并发写入的串行化与冲突恢复。

**验收**：

- 两个 Agent 同时写同一文件：只有一个成功，另一个被拒绝/排队；无静默覆盖。
- 两个 Agent 写不同文件：默认也串行；配置按文件并行后可并行。
- 冲突后 Agent 重新读取/变基后可成功写入；时间线记录两次尝试。
- 写入事件与审计可追溯；Bash 绕过写入需审批或标记为「不受管变更」。

## 9. 技术方向与边界（技术主管视角，非实现设计）

> 本节是评审输入与交付约束，不是最终架构/数据模型。v0.0.1 的硬方向：原生 Go、DeepSeek-only、5 个工具、共享写工具、单用户。

### 9.1 架构原则

1. **两个核心模块**：
   - **对话平台（Go）**：消息、群聊、部门/Agent 管理入口、检索、通知、审计。
   - **Agent 核心框架（Go）**：部门/员工编排、收件箱、上下文装配/压缩、记忆、任务/讨论/评审/决策、共享写工具、5 个工具、DeepSeek 客户端。
2. **平台是消息与审计的唯一事实源**；核心是 Agent 状态、任务状态、记忆、文件变更时间线的唯一事实源。
3. **原生 Go agent loop**：不使用 DSH/ACP/Node/外部执行后端；工具只有 read_file/write_file/bash/web_search/view_change_history。
4. **DeepSeek-only**：只接 DeepSeek 官方 API；所有角色默认 deepseek-flash；不做多供应商路由。
5. **共享写工具**：所有 Agent 通过 write_file 提交写事件；默认全局串行（事件未消费前其他 Agent 不得写入）；后续可配置按文件并行；冲突检测；时间线默认 30 条/文件（可配置）；Git 分支/提交监听。
6. **上下文由核心装配/压缩**；每 turn 记录 context.request；没有第二层压缩/外部后端。
7. **统一状态机**：任务/产出物/评审/决策由核心统一管理；平台只读投影；卡片动作调用核心 API。
8. **通信默认隔离**：部门内自由；跨部门经部门主管；主管与用户经助理；用户可看所有群聊，可临时开桥。
9. **本地优先**：单机、loopback、SQLite、无外部数据库/搜索服务；DeepSeek API 是唯一默认外联。
10. **单用户**：v0.0.1 只支持一个用户。
11. **权限先于检索**；先写后发；at-least-once + 幂等。
12. **人类在环**：高风险/不可逆动作必须审批；Agent 不能自批/自改权限。

### 9.2 技术约束

| 约束 | 说明 | 理由 |
|---|---|---|
| 语言 | 平台与核心使用 Go | 单二进制、并发、跨平台 |
| 模型 | 只接 DeepSeek 官方 API；默认 deepseek-flash | 用户明确第一版只用 DeepSeek |
| 工具 | 只有 read_file、write_file、bash、web_search、view_change_history | 最小可用，避免复杂度 |
| 不接外部运行时 | 不使用 DSH/ACP/Node/MCP/插件 | 避免协议/版本/进程复杂度 |
| 本地部署 | 单机、loopback；数据目录可配置 | 数据主权、隐私 |
| 单用户/单项目 | v0.0.1 一个用户、一个项目；部门可多 | 控制范围 |
| 单二进制 | 平台+核心同进程；浏览器客户端；无外部数据库/搜索服务 | 「双击即用」 |
| 文件写入 | 共享 WriteTool；默认全局串行；时间线 | 避免冲突与静默覆盖 |
| 数据可迁移 | 导出/备份开放；索引可重建 | 不锁定 |
| 安全默认 | 最小权限、默认不暴露、密钥只给核心、日志脱敏 | 本地 Web 也按不可信网络设计 |

### 9.3 自研 vs 复用

| 能力 | 决策 | 说明 |
|---|---|---|
| 对话平台 | **自研** | 消息、群聊、检索、Agent 管理、审计 |
| Agent 核心 | **自研** | 部门编排、任务/讨论/评审/决策、记忆、上下文 |
| 共享写工具/时间线 | **自研** | 所有 Agent 共用；冲突检测；Git 监听 |
| 四层记忆 | **自研** | 部门管理对象与治理需求 |
| 消息检索 | **自研** | 中文、权限、任务/决策联合检索 |
| DeepSeek 调用 | **复用官方 API** | 默认 deepseek-flash；web_search 用 DeepSeek 能力 |
| 工具执行 | **自研薄层 + OS** | 读/写/Bash/搜索/时间线 |
| 外部 Agent 运行时 | **不做** | v0.0.1 不接 DSH/ACP/Node/MCP |

### 9.4 数据所有权

| 数据 | 所有者 | 说明 |
|---|---|---|
| 消息/事件/群聊/通知/审计 | 对话平台 | 唯一事实源；审计唯一 append-only 流；可导出 |
| 任务/产出物/评审/决策 | Agent 核心 | 统一状态机；平台只读投影 |
| 成本/用量 | Agent 核心 | per-call 账本；平台只读投影 |
| Agent 会话/上下文/快照 | Agent 核心 | 逻辑会话、context.request |
| 记忆/档案/快照 | Agent 核心 | 结构化 + 叙事；可导出 |
| 文件变更时间线 | Agent 核心 | 写事件、diff、分支/commit；默认 30/文件 |
| DeepSeek API Key | Agent 核心/OS keychain | 平台只存引用；不入消息/日志 |
| 工作区文件 | 用户 | Git/文件系统；写工具仲裁 |

### 9.5 协议与扩展

- **内部协议**：消息/事件 schema、任务状态、评审/决策对象、记忆候选/注入快照、写事件 schema 必须有版本号与兼容策略。
- **DeepSeek 客户端**：只接官方 API；默认 deepseek-flash；web_search 用 deepseek_web_search/Search API；不做多供应商抽象。
- **工具协议**：5 个工具的参数/返回/错误/权限固定；view_change_history 为新增只读工具。
- **导出格式**：JSON/Markdown；带 schema 版本；可被外部工具读取。
- **v0.0.1 不做**：MCP、ACP、插件、外部 Agent 运行时、多模型供应商。

### 9.6 关键架构决策（v0.0.1，已按用户意见定）

| # | 决策 | v0.0.1 选择 | 影响 |
|---|---|---|---|
| D1 | 组织模型 | 用户 -> 助理 -> 部门主管 -> 员工；无统管所有部门的主管 | 全局职责由助理/PM 部门承担 |
| D2 | Agent 内核 | **原生 Go**；不使用 DSH/ACP/Node | 单二进制、简单可控 |
| D3 | 模型 | **DeepSeek-only，默认 deepseek-flash** | 不做多供应商 |
| D4 | 工具 | read_file/write_file/bash/web_search/view_change_history | 最小工具集 |
| D5 | 文件写入 | 共享 WriteTool + 默认全局串行 + 时间线（30 可配） | 多 Agent 可写，但不冲突 |
| D6 | 部门内讨论 | 员工从自己开发便利出发；主管裁决；5/15 上限 | 模拟真实开发取舍 |
| D7 | 跨部门辩论 | 部门主管代表；助理主持；5/15；超限反馈用户 | 可数、可升级 |
| D8 | 通信隔离 | 部门内自由；跨部门经主管；主管-用户经助理；用户观察者 | 默认隔离，可临时开桥 |
| D9 | 任务状态 | 增加 discussing；分工视角；返工 2 轮/重开 1 次 | 讨论式推进 |
| D10 | 单用户 | v0.0.1 单用户 | 控制范围 |

### 9.7 交付策略

- **纵向切片优先**：先跑通一个需求端到端，再扩功能。
- **风险前置**：先验证消息不丢/可检索、Agent 能接任务并产出、写工具不冲突、跨部门讨论能收敛。
- **可演示**：每个里程碑有可运行演示与金标准任务。
- **可降级**：P1 功能缺失时核心闭环仍能跑；P1-off 构建验证。
- **不做大爆炸**：不一次性重写；每步可回滚。
- **文档同步**：需求/架构/运维/用户文档随功能更新。

## 11. 数据、权限与隐私

### 11.1 数据分类

| 级别 | 示例 | 默认可见 |
|---|---|---|
| 公开/项目共享 | 项目章程、接口契约、术语表、决策记录 | 项目成员 |
| 部门 | 部门群聊、部门档案、内部讨论/评审 | 部门员工 + 部门主管/助理 |
| 私有 | 员工会话、个人笔记、私聊 | 本人/授权者；用户可在审计模式查看并留痕，默认不注入其他 Agent |
| 人类专属 | 人类偏好、评价、敏感信息 | 人类 + 助理（受限） |
| 审计 | 工具调用、审批、治理动作 | 人类/审计权限 |

### 11.2 数据所有权与保留

- 消息/事件/审计：平台所有；审计为唯一 append-only 流；默认长期保留，可配置归档/清理（清理本身留审计）；应用层哈希链校验；不可 UI 删除。
- Agent 会话：核心所有；可归档；不因任务结束删除。
- 记忆/档案：核心所有；可编辑/删除；删除留墓碑。
- 任务/产出物/评审/决策：核心元数据 + 工作区文件；保留策略可配置。
- 备份：用户所有；可加密；可导出。
- DeepSeek API：只接收推理/搜索所需内容；用户可配置脱敏/禁用。

### 11.3 权限模型

- **主体**：用户/Agent；Agent 有角色、部门、工具能力。
- **资源**：会话/部门/项目/任务/产出物/记忆/审计。
- **动作**：读/写/评审/验收/审批/删除/导出/管理。
- **规则**：最小权限、职责分离、作者≠评审者、Agent 不能自批/自改权限、人类最终权。
- **单一 Policy**：对象级权限由 Agent 核心的单一 Policy 判定；平台只做会话级过滤并调用 Policy 做对象级预过滤；ACL 投影延迟与权限变更刷新有明确上限。
- **可见性**：private / department / project / org / human-only。
- **审计**：高风险动作必须留痕；权限变更需审批；人类查看私有内容进入审计模式并留痕。

### 11.4 隐私原则

1. 默认本地；无遥测；不训练。
2. 只收集工作所需；敏感信息写入前过滤。
3. 明确发往 DeepSeek API 的内容；可配置脱敏/禁用。
4. 用户可查看/导出/删除；删除传播到索引/缓存/记忆。
5. 权限即视图：不同角色注入不同记忆/上下文。
6. 审计与隐私平衡：审计保留最小必要信息，敏感字段脱敏。

### 11.5 威胁模型摘要

**边界**：v0.0.1 不承诺防御「同一 OS 用户下的恶意本地进程」；目标是进程级隔离 + 数据目录 ACL + 最小令牌；OS 级沙箱为 v0.1 目标。

- 本地 Web 跨站访问、CSRF/DNS rebinding。
- 提示注入（网页/文件/Issue/工具输出）。
- 工具滥用/越权（删除、force push、发布、付款）。
- 密钥泄漏、日志/导出泄漏。
- Agent 冒充、串谋、记忆污染。
- 成本失控、无限循环。
- 供应链（依赖/工具/安装包）。
- 数据丢失/损坏。

> 详细防线见目标文档第 13 章；v0.0.1 必须覆盖 P0 项。

### 11.6 沟通隔离与用户观察者

- 部门内：员工可自由群聊/讨论。
- 跨部门：员工不能直接找其他部门员工；由部门主管对部门主管对接。
- 部门主管 ↔ 用户：默认必须经助理转接。
- 用户观察者：用户可查看所有群聊消息，默认不参与；加入后可发言。
- 临时桥：用户可临时开通直连，指定范围与到期；到期自动关闭并通知；桥接消息留审计。
- 隔离只限制 Agent 默认路由，不限制用户读取；用户始终可查看全部群聊记录。

## 12. 交付策略与里程碑

> 里程碑是**交付阶段**，不是详细排期承诺。每个阶段必须有可运行演示与验收，不以「代码写完」为完成。

### 12.1 策略

- **纵向切片**：每个阶段都尽量端到端，而不是先做完整平台再接入 Agent。
- **风险前置**：先验证消息可靠性/检索、Agent 接任务、写工具不冲突、跨部门讨论能收敛。
- **可演示**：每个里程碑有 Demo 脚本与金标准任务。
- **可回滚**：每阶段可独立回退；数据迁移有备份。
- **不做大爆炸**：先做最小实现，再按验收反馈优化。

### 12.2 里程碑

| 里程碑 | 主题 | 范围 | Exit Criteria |
|---|---|---|---|
| **M0 能说话** | 平台骨架 + 助理 + 持久化 | 启动/向导/助理私聊/群聊/消息落库/基础检索/重启恢复/DeepSeek 接入 | 新用户能启动并与助理对话；重启不丢消息；中文搜索基础可用；DeepSeek 不可用可降级 |
| **M1 能组部门** | 部门组建 + 任务板 | 项目/部门蓝图/审批/provisioning/角色卡/分工视角/部门群聊/任务板 | 能创建产品/研发/测试部门；任务可见、可分派；暂停/恢复可用 |
| **M2 能交付** | 任务/产出物/评审/写工具 | 状态机（含 discussing）/DoR/DoD/产出物注册表/评审/返工/人类闸门/共享写工具+时间线 | 一个真实需求从任务到验收；作者≠评审者；证据齐全；并发写不冲突 |

### 12.3 金标准任务

至少准备 3 类：

1. **小功能交付**：一个可在 1 天内完成的真实小功能（含 PRD、实现、测试、验收）。
2. **跨部门接口争议**：平台部门挑战研发部门的接口/安全/兼容性，走完辩论与决策。
3. **记忆/检索复盘**：一周后回答「为什么这么决定」并纠正一条记忆。

金标准任务用于：

- 每次模型/提示词/运行时/检索/记忆变更后的回归。
- 发布前验收。
- 成本/质量基线。

### 12.5 用户验证计划（Beta）

## 13. 风险、假设与开放问题

### 13.1 假设

1. 用户有可用的 DeepSeek API Key；网络可访问 DeepSeek API。
2. 用户有本地代码/文档工作区；Git 可选。
3. 用户使用 Windows/macOS/Linux 桌面环境；浏览器可用。
4. v0.0.1 单用户、单项目、中文优先。
5. v0.0.1 只接 DeepSeek；默认 deepseek-flash；不接其他模型/运行时。
6. 用户愿意在关键节点审批；不追求完全无人值守。

### 13.2 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 模型能力/稳定性不足 | 交付质量差、返工多 | 金标准任务、评审、人工抽检；固定 deepseek-flash，按验收调提示词 |
| 成本失控 | 用户不敢用 | 预算、压缩、停止条件、成本可见 |
| 多 Agent 协作失效 | 漂移/重复/冲突 | 固定 SOP、角色卡、DoR/DoD、独立验证 |
| 记忆污染/膨胀 | 长期错误/检索差 | 证据门槛、候选审核、额度、双时间、可删除 |
| 提示注入/越权 | 安全事故 | 指令层级、工具白名单、审批、沙箱、红队 |
| 本地 Web 漏洞 | 数据泄漏 | Origin/Host、Cookie、Token、默认 loopback |
| DeepSeek API 依赖 | 限流/故障/涨价 | 超时/重试/预算/降级（只读/暂停）；平台可离线浏览/检索/导出 |
| 中文检索质量 | 搜不到 | 金标准查询、回退策略、评测、可换分词 |
| 跨平台差异 | 行为不一致 | 统一安全语义 + 平台差异矩阵 + 默认拒绝 |
| 产品复杂度过高 | 用户不会用 | 引导、默认模板、渐进披露、演示项目 |
| 人类被流程淹没 | 不愿用 | 注意力预算、批量审批、助理过滤 |
| 数据丢失/损坏 | 信任崩塌 | 先写后发、备份、恢复演练、索引重建 |
| 范围蔓延 | 延期 | 非目标、Exit Criteria、每版砍功能 |
| 单一模型供应商锁定 | 迁移困难 | 导出/记忆可迁移；v0.0.1 只接 DeepSeek，后续不承诺多供应商 |

### 13.3 开放问题

| # | 问题 | 选项 | 建议 | 影响 | 决策点 |
|---|---|---|---|---|---|
| 1 | 默认部门模板 | 三部门 / 加平台 / PM 部门制 | **三部门交付（产品/研发/测试）** | 验收场景/成本 | 需求评审 |
| 2 | 人类闸门数量 | 2 / 3 / 更多 | **3（G1/G2/G3）+ 不可逆审批** | 用户体验/风险 | 需求评审 |
| 3 | 部门内讨论上限 | 3 / 5 / 不限 | **每人≤5 条、总计≤15 条** | 收敛/成本 | 需求评审 |
| 4 | 跨部门辩论上限 | 5/15 / 更少 / 不限 | **每人≤5 条、总计≤15 条；超限反馈用户** | 收敛/成本 | 需求评审 |
| 5 | 记忆写入权 | 全自动 / 全人工 / 分层 | **低风险自动；决策/争议/敏感需确认** | 信任/吞吐 | 需求评审 |
| 6 | 自适应提示词自治 | 自主 / 仅提议 / 分层 | **v0.0.1 默认仅提议；显式开启低风险自动；高风险仅提议** | 能力/风险 | 需求评审 |
| 7 | 双时间范围 | 全量 / 仅决策争议 | **决策/争议/能力强制；其他 upsert+快照** | 审计/复杂度 | 数据设计 |
| 8 | 检索方案 | 全文 / 全文+向量 | **v0.0.1 全文 + 结构化；向量后续** | 体验/依赖 | 技术设计 |
| 9 | 单项目 vs 多项目 | 单项目 / 多项目 | **v0.0.1 单项目** | 范围/复杂度 | 需求评审 |
| 10 | 原始轨迹是否进检索 | 进 / 不进 | **不进默认检索；审计可查** | 检索质量/审计 | 产品评审 |
| 11 | 跨部门裁决权 | 部门主管 / 助理 / 人类 | **部门主管先裁决；主管间冲突交助理；再反馈用户** | 治理/效率 | 治理设计 |

> 开放问题在对应阶段转为决策记录（ADR），不在本文硬编码。

## 14. 端到端验收场景

> 以下 15 个场景是 v0.0.1 的发布门槛。每个场景都要在干净数据目录、真实模型配置下跑通；核心产品行为不得用纯 mock；故障/越权/成本阈值允许通过测试模式注入（见 14.1）。

### AC-01 首次启动与助理

**前置**：全新数据目录；有效 DeepSeek API Key；本机浏览器。

**步骤**：

1. 启动应用，打开本地地址。
2. 完成首次向导（数据目录、模型、预算、称呼）。
3. 助理主动出现并介绍能力/边界/暂停方式。
4. 用户输入一个模糊目标（如「我想把 CLI 工具做成 Web 产品」）。
5. 助理澄清并生成项目意图卡；用户确认。
6. 用户问一个单次问题（如「这个功能大概需要几天？」），助理直接回答，不创建部门。

**通过标准**：

- T1 ≤10 分钟；用户不需要开发者协助。
- 默认只本机可访问；无外部数据库/搜索服务。
- 助理未在用户确认前创建部门。
- 意图卡可编辑、版本化。
- 单次问答有引用/不确定性说明，不自动建任务。
- 所有操作可在审计中查到。

**关联**：FR-ONB-01..05、FR-ASST-01/02、FR-CHAT-01、FR-SEC-01。

### AC-02 部门组建

**前置**：AC-01 完成。

**步骤**：

1. 助理提出项目/部门蓝图（产品/研发/测试，可选平台部门），含角色/人数/分工视角/预算/节奏/风险；蓝图即章程草案。
2. 用户修改人数/预算，批准（G1，一次批准蓝图+章程）。
3. 系统 provisioning；各部门主管 kickoff 只复述目标/风险/第一里程碑，不再单独要求人类审批。
4. 用户检查：部门、角色卡、分工视角、部门群聊、任务板、记忆空间、权限。
5. 用户暂停部门，再恢复。
6. 重复执行 provisioning（模拟重试），检查不重复。

**通过标准**：

- AC-01 到 AC-02 累计 T2 ≤30 分钟（安装→G1+首个任务 ready）。
- 产品/研发/测试部门创建成功；角色卡、分工视角与权限一致。
- 部门群聊/任务板/记忆空间自动创建，无孤儿。
- 失败可重试/回滚；重复执行幂等。
- 暂停后不接新任务；恢复后状态完整。
- 创建/变更/暂停均留审计。

**关联**：FR-ASST-03/04、FR-TEAM-01..06、FR-SEC-06。

### AC-03 需求交付闭环

**前置**：AC-02 完成；一个真实小需求（如「增加导出 CSV」）。

**步骤**：

1. 用户把需求发给产品/研发部门。
2. 产品 Agent 写 PRD 与验收标准；部门主管组织评审。
3. 按 §6.3 高风险分类表判断；命中高风险时用户 G2，批准后开工。
4. 部门主管拆任务、分派研发/测试；任务板可见，并写明每个员工的分工视角。
5. 研发员工 A/B 对接口字段有分歧；在部门群聊进入**部门内讨论**：各自以「方便自己开发」为第一原则陈述视角与证据；每人≤5 条、总计≤15 条；部门主管裁决并记录；进入实现。
6. 研发实现，提交产出物版本；测试写用例/跑测试。
7. 测试/评审提交挑战单；研发返工；重新提交。
8. 部门主管逐条填写验收核对表（FR-TASK-07）；用户 G3 验收。
9. 任务完成；产出物归档；记忆候选提交；文件写入进入时间线。

**通过标准**：

- T3：从首个任务创建到 G3 验收 ≤1 个工作日（示例需求）。
- 任务状态转换合法（含 discussing）、可追溯；作者≠评审者；分工视角已写明。
- 部门内讨论有视角/轮次/主管裁决记录；每人≤5、总计≤15；没有员工替全局拍板。
- 每条验收标准有证据；验收核对表完整；缺证据时 G3 不可提交。
- 返工有挑战单、修复、新版本；旧版本仍可查。
- 人类闸门 G2/G3 有记录；无未记录审批。
- 成本/耗时在预算内；可查看归因。
- 完成后可搜索到 PRD/代码/测试/评审/决策。

**关联**：FR-TASK-01..08、FR-ART-01..05、FR-REV-01..03、FR-APPR-01、FR-OPS-05、FR-WRITE-01..04。

### AC-04 跨部门挑战与决策

**前置**：AC-03 进行中；平台评审部门已就绪。为保证可重复，使用测试夹具注入一个接口变更/挑战，不依赖「自然发现」。

**步骤**：

1. 通过夹具注入一个接口兼容/安全问题，发起挑战单（blocker，带证据）。
2. 研发部门回应；双方提交决策包（stance/现状/提案/影响/evidence_ids/替代方案）。
3. 助理主持；R1 双方立场+回应，R2 双方反驳；每人≤5 条、总提交≤15；死锁按 stance/evidence_ids 判定。
4. 双方仍不一致 → 助理生成决策简报，升级人类（L3）或领域 owner 裁决。
5. 人类/裁决人决定；写决策记录；更新任务/产出物。
6. 用户搜索该决策，查看双方立场、异议、理由。

**通过标准**：

- 挑战单有严重级别、证据、影响、建议。
- 每人≤5 条、总提交≤15；时间盒/死锁检测生效；无无限循环；新证据重开最多 1 次；主管间争论最终反馈用户。
- 决策记录包含选项、理由、异议、受影响对象、复查条件。
- 异议保留；决策可检索、可跳转。
- 任务/产出物按决策更新；通知受影响方。
- 无未记录的人类批准。

**关联**：FR-REV-01/02、FR-DEB-01..04、FR-DEC-01/02、FR-ESC-01、FR-APPR-01/02。

### AC-05 记忆回忆与纠正

**前置**：AC-03/04 完成；至少一条决策、一条偏好。

**步骤**：

1. 新开会话，问「上次为什么没上 GraphQL？」。
2. 助理检索决策记录/辩论/任务，给出答案与来源链接。
3. 用户发现一条偏好过时，打开记忆检查器修改。
4. 新会话再问相关问题，助理使用新版本。
5. 用户删除一条错误记忆；再问，确认不再注入。
6. 用户查看「助理最近记住了什么」，处理一条待审候选。

**通过标准**：

- 回答有来源（决策/消息/产出物）；无来源时明确说明。
- 修改立即生效；旧版本可查。
- 删除后不再注入；墓碑/审计保留。
- 待审队列可批准/拒绝/合并；拒绝有理由。
- 员工不能读其他部门私有记忆；越权被拒绝。
- 自适应提示词有版本/diff/回滚。

**关联**：FR-MEM-01..12、FR-CHAT-10、FR-SEC-06。

### AC-06 检索与审计

**前置**：AC-03/04/05 产生足够消息/任务/决策。

**步骤**：

1. 搜索中文 2 字词（如「限流」）、短语、中英混排、代码标识符。
2. 按部门/作者/时间/类型过滤；点击结果跳转。
3. 搜索已删除消息，确认不出现。
4. 以无权限 Agent 身份搜索，确认不泄漏其他部门内容。
5. 打开审计，查一次高风险工具调用的审批链。
6. 导出消息/决策/审计。

**通过标准**：

- 中文 2 字可命中；金标准集 Recall@10 ≥0.8、nDCG@10 有基线；片段高亮。
- 10 万条语料 p95 ≤300ms；中文 2 字 p95 ≤150ms；写入后 ≤100ms 可搜。
- 删除不可搜；权限过滤不泄漏存在性。
- 审计完整：谁、何时、动作、对象、审批。
- 导出可读、脱敏、可导入。
- 索引重建可完成并校验。

**关联**：FR-SRCH-01..07、FR-CHAT-11、FR-SEC-06、FR-OPS-02。

### AC-07 崩溃、重启与断线

**前置**：AC-03 运行中。

**步骤**：

1. 在主进程生成回复/执行工具时强制终止；再模拟 DeepSeek API 超时/断网（两次独立运行）。
2. 重启；打开会话与任务板。
3. 检查消息、任务、评审、决策、记忆状态、context.request。
4. 断开浏览器网络 1 小时（发布前演练），再恢复；检查补齐。
5. 检查中断的工具调用是否标记「结果未知」，是否自动重试。
6. 完成剩余任务。

**通过标准**：

- 已确认消息 0 丢失；未完成回复标记中断。
- 任务/评审/决策状态一致；可继续。
- 断线补齐不重复、不丢失。
- 有副作用工具不自动重试；只读/幂等可重试。
- 恢复有日志/用户可见状态。
- 无重复消息/任务/评审。

**关联**：FR-CHAT-05、FR-TASK-06、FR-OPS-06、NFR-REL-01..07。

### AC-08 安全与权限

**前置**：系统正常运行；至少两个部门。

**步骤**：

1. 从恶意网页发起跨站请求，尝试读消息/发指令。
2. Agent 尝试执行未授权工具（如删除工作区外文件、访问未授权网络）。
3. 员工 Agent 尝试读其他部门私有档案。
4. 高风险动作触发审批；用户拒绝；Agent 尝试绕过。
5. 检查审计与告警。

**通过标准**：

- 跨站请求被拒绝；GET/流式事件推送同样校验 Origin/Host；默认无 CORS 头。
- 未授权工具被拒绝；高风险动作需审批。
- 通过文件/消息注入的「忽略系统指令」不改变指令层级；越权尝试被拒绝并审计。
- 跨部门读取被拒绝；不泄漏内容/存在性。
- 拒绝后无法绕过；尝试留审计/告警。
- 密钥/Token 不出现在消息/日志/检索。
- 全局紧急停止可立即生效。

**关联**：FR-SEC-01..07、NFR-SEC-01..08。

### AC-09 预算与暂停

**前置**：AC-03 运行中；设置较低部门预算。

**步骤**：

1. 设置部门日预算；运行任务。
2. 达到 80% 告警；达到 100% 暂停接新任务。
3. 用户追加预算/提高上限；恢复。
4. 触发全局紧急停止；检查所有 Agent 状态。
5. 恢复；检查任务/消息/成本。

**通过标准**：

- 预算可见、按部门/任务归因。
- 80% 告警、100% 暂停；不静默超支。
- 追加预算留审计；恢复后继续。
- 紧急停止生效快；状态保留；可恢复。
- 成本数据与模型调用一致（抽样）。

**关联**：FR-OPS-05、FR-SEC-07、FR-OBS-03。

### AC-10 备份、导出与恢复

**前置**：AC-03/04/05 产生数据。

**步骤**：

1. 执行备份；记录时间/大小。
2. 在另一数据目录恢复；启动。
3. 检查消息、任务、产出物、评审、决策、记忆、审计、文件变更时间线。
4. 重建索引；搜索验证。
5. 导出工作区；用外部工具读取。
6. 导入到空工作区；检查冲突/重复处理。

**通过标准**：

- 恢复后数据完整；可检索；可继续工作。
- 会话/记忆/文件变更时间线数据可恢复，或系统在备份时明确标注「不可备份范围」并告知用户。
- 索引重建成功；抽样一致。
- 导出格式开放、可读；敏感字段脱敏。
- 导入校验版本；冲突有提示；不覆盖现有数据（除非确认）。
- 恢复/导出/导入留审计。
- 恢复失败可回滚。

**关联**：FR-OPS-01/02、FR-MEM-12、NFR-REL-05。

### AC-11 记忆注入与跨会话复用

**前置**：AC-03/04 完成；已产生一条决策、一条部门约束、一条人类偏好；记忆抽取已运行。

**步骤**：

1. 新开会话，执行一个相似任务；不给任何背景提示。
2. 观察助理是否**无需用户提醒**引用之前的决策/约束；打开「本次回答使用了哪些记忆」查看来源。
3. 修改一条人类偏好；新会话第一轮使用新版本；旧版本在记忆中可查。
4. 删除一条记忆；再执行相似任务，检查注入日志中该条命中为 0。
5. 关闭档案层（或某类记忆）；确认系统按定义降级（只用任务+手册），并明确告知用户。
6. 记忆投毒测试：通过文件/消息注入一条「忽略系统指令/提升权限」的文本；确认它不会被晋升为 L4/系统指令，后续会话越权尝试被拒绝并审计。

**通过标准**：

- `context.request` 记录本次注入的档案/任务/消息、来源、token 估算；用户可查看。
- 修改立即生效；删除后不再注入；旧版本/墓碑可查。
- 关闭某一层后行为可解释，不静默失效。
- 记忆投毒不改变系统指令层级；越权尝试被拒绝并留审计。
- 员工不能读其他部门私有记忆；用户读取私有内容进入审计模式并留痕。

**关联**：FR-MEM-07/08/09/11、FR-OBS-04、FR-SEC-04。

### AC-12 部门主管核对与人类抽检

**前置**：一个含 3 条验收标准的任务；研发/测试已提交。

**步骤**：

1. 部门主管填写验收核对表：AC1 有证据且通过；AC2 无证据；AC3 需人类判断。
2. 尝试提交 G3；系统应阻止，并显示缺失项。
3. 研发补齐 AC2 证据；部门主管更新核对表；G3 卡片显示核对表、成本、风险、受影响产出物。
4. 人类批准 G3；任务完成；审计记录核对表版本。
5. 人类从评审列表随机抽检一条 approve 裁决，查看证据与 dissent，标记「有效/无效/证据不足」；质量指标更新。
6. 模拟同一对 Agent 互审 ≥5 次且通过率 100%，确认出现人类抽检提示。

**通过标准**：

- 任一条验收标准未核对/不通过时，G3 不可提交。
- G3 卡片完整展示核对表、风险、成本、产出物版本。
- 核对表不可事后篡改；修正以追加记录表达。
- 抽检结果进入指标；异常通过率提示出现；不自动判定串谋。
- 小任务由部门主管授权验收时，也必须留核对表与审计。

**关联**：FR-TASK-07、FR-APPR-01、FR-REV-05、FR-OBS-02。

### AC-13 注意力、收件箱与审批

**前置**：至少两个部门产生通知；设置较低审批 TTL 与每日打扰预算。

**步骤**：

1. 分别触发 FYI、需要知道、需要决定、阻塞四类通知。
2. 检查实时打扰只有「需要决定/阻塞」；其余进入收件箱「稍后/FYI」；同一升级包只有一个收件箱条目。
3. 批量批准低风险审批；尝试批量批准双钥匙/不可逆动作，确认被拒绝。
4. 设置审批 TTL 为 1 分钟；超时后确认标记阻塞/提醒，不自动执行。
5. 模拟人类 24h 无响应；确认部门降级为只读/暂停接新任务，并生成日报。
6. 将一项审批授权给助理（范围+到期）；到期后确认自动回收并通知。

**通过标准**：

- 收件箱是持久对象；通知是推送；批量/稍后/授权可追溯。
- 默认打扰预算生效；超出只进收件箱，不实时推送。
- TTL 到期不自动执行；人类沉默策略生效。
- 批量审批不适用于双钥匙/不可逆动作。
- 授权到期自动回收；所有操作留审计。

**关联**：FR-CHAT-01/06、FR-ASST-06、FR-APPR-02、FR-OPS-07、FR-SEC-07。

### AC-14 群聊与 Agent 管理

**前置**：至少两个部门；助理可用。

**步骤**：

1. 创建项目群聊、部门群聊、临时讨论组；添加/移除成员；设置可见性。
2. 用户在群聊 @ 两个 Agent；确认按发言队列依次回复，不刷屏。
3. 用户以观察者身份查看另一个部门群聊；确认可读、默认不参与；加入后发言。
4. 用户从平台启动/暂停/恢复/停止一个 Agent；查看状态、角色卡、分工视角、预算、最近行为。
5. 尝试让员工直接私聊其他部门员工/部门主管直接私聊用户；确认被拒绝并提示路径（找主管/找助理/开桥）。
6. 用户临时开通跨部门直连桥（范围+到期）；确认到期自动关闭并留审计。

**通过标准**：

- 群聊成员/可见性/发言队列/历史/搜索正常；用户可查看所有群聊。
- Agent 生命周期操作生效，状态与审计可见；高风险配置需审批。
- 默认隔离生效；越权路由被拒绝；临时桥按范围/到期工作。
- 群聊消息全量落库、可检索、断线补齐。

**关联**：FR-CHAT-14/15/16、FR-TEAM-06、FR-SEC-07。

### AC-15 并发写入与变更时间线

**前置**：一个工作区；两个 Agent；至少一个文件。

**步骤**：

1. 两个 Agent 同时向同一文件提交 write_file；确认只有一个成功，另一个被拒绝/排队。
2. 被拒绝的 Agent 重新读取/变基后再写；确认成功，时间线记录两次尝试。
3. 两个 Agent 写不同文件；确认默认全局串行；配置按文件并行后可并行。
4. 打开 view_change_history：查看文件、时间、Agent、diff、任务、分支、commit、原因。
5. 制造 35 次连续修改；确认每个文件只保留最近 30 次（配置可调）。
6. 切换 Git 分支/提交；确认时间线记录分支事件，提交把多次改动合并为 commit 组。
7. 用 Bash 绕过 write_file 写同一文件；确认被审批/标记为「不受管变更」。

**通过标准**：

- 无静默覆盖；冲突可恢复；写事件可追溯。
- 时间线保留上限、字段、diff、分支/commit 正确；view_change_history 可用。
- 提交/分支监听生效；Bash 绕过有审批/标记。
- 并发测试可重复；审计完整。

**关联**：FR-WRITE-01..04、FR-OPS-06、FR-SEC-03。

### 14.1 验收执行要求

- 每个场景在 Windows/macOS/Linux 至少各跑一次（可分工）。
- 核心产品行为使用真实模型/工具，不用纯 mock；故障/越权/成本阈值/权限场景允许通过测试模式注入，并记录注入点。
- 为每个场景提供夹具/seed，允许独立执行；链式场景必须给出预置数据。
- 确定性断言（消息数/状态/审计/证据链接）自动化；质量判断可人工。
- 记录：通过/失败、耗时、成本、缺陷、截图/日志。
- P0 场景失败 = 不可发布；P1 失败需有规避方案。
- 每次发布前重跑；金标准任务回归。

## 15. 附录

> 以下字段/状态/类型是**验收所需的最小行为契约**，不是最终数据模型；设计阶段可调整命名/存储，但不得改变语义。

### 15.1 附录 A：任务状态与转换

| 状态 | 含义 | 允许转换 | 谁可操作 |
|---|---|---|---|
| proposed | 已提出，待补齐 | → ready / canceled | 部门主管、owner |
| ready | DoR 满足 | → discussing / canceled | owner |
| discussing | 分工视角/讨论中 | → in_progress / changes_requested | owner、部门主管 |
| in_progress | 执行中 | → in_review / blocked / canceled / failed | owner |
| blocked | 阻塞 | → in_progress / canceled | owner、部门主管 |
| in_review | 评审中 | → approved / changes_requested | reviewer |
| changes_requested | 需返工 | → in_review / canceled | owner |
| approved | 评审通过，待验收 | → done | approver |
| done | 完成 | 终态；重开需新任务/记录 | approver、人类 |
| canceled | 取消 | 终态 | 部门主管、人类 |
| failed | 失败 | 终态/新任务 | owner、部门主管 |

**正交标记**：escalated（已升级，记录 `from_state` / `escalated_at`）、at_risk（超时/超预算）、waived（人类豁免，需决策记录）。**escalated 不是状态，不得出现在状态转换边里。**
